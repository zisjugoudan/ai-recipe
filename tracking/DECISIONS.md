## ADR-0001：本地仓库作为协作事实源

### 背景

当前团队由项目负责人和 Codex 组成，不需要依赖云端项目管理或设计协作平台。

### 决策

产品、进度、设计、技术探索、代码和测试全部保存在项目目录；聊天只负责提出请求和说明结果。

### 影响

- 新会话可以通过本地文档恢复上下文。
- 所有有效决定必须落盘。
- 不得用云平台链接替代本地交付文件。

## ADR-0008：移动端统一采用 Flutter

- 日期：2026-07-27
- 状态：生效
- 关联任务：SPK-001、ARCH-001

### 背景

产品以移动端为主，需要同时支持 iOS 和 Android，并具备 Local-first、分享入口、后台任务、安全存储、本地 OCR 插件和自定义 API 能力。项目负责人已明确选择 Flutter。

### 决策

移动客户端统一使用 Flutter，不再投入时间进行 React Native 二选一。`SPK-001` 改为 Flutter 关键能力基线验证，负责发现平台阻塞，而不是重新决定框架。

### 原因

- 与用户明确技术方向一致。
- Dart/Flutter 可共享大部分业务、领域和 UI 代码。
- Platform Channels 与 federated plugin 能隔离必要的 iOS/Android 原生能力。
- 当前开发机已安装 Flutter 3.38.5 stable 和 Dart 3.10.4。

### 影响与代价

- 需要维护少量 Swift/Objective-C 与 Kotlin/Java 插件代码。
- Windows 无法完成 iOS 构建，必须在后续 macOS/iPhone 环境补验。
- 不能因为框架已选定而跳过分享、后台任务、通知、安全存储和 OCR 桥接实测。

### 验证方式

执行 `SPK-001` 和 `ARCH-001`，验收标准见 `docs/architecture/MOBILE_ARCHITECTURE.md`。

## ADR-0009：本地 OCR 首选 PaddleOCR PP-OCRv5 mobile

- 日期：2026-07-27
- 状态：生效
- 关联任务：SPK-002、OCR-001

### 背景

输入包含中文菜谱截图、食材列表、中英文单位、长步骤和平台水印。游客应能在不调用云服务的情况下使用 OCR，模型还需按需安装、升级和删除。

### 候选方案

- PaddleOCR PP-OCRv5 mobile + ONNX Runtime Mobile。
- 系统原生/Google ML Kit OCR。
- 仅使用云 OCR。

### 决策

首选 PaddleOCR PP-OCRv5 mobile，并使用 ONNX Runtime Mobile 在 Android/iOS 推理；通过 Flutter federated plugin 暴露统一 `OcrProvider`。模型作为带 Manifest 和 SHA-256 的资源包按需下载。

### 原因

更贴合中文、长文本和复杂截图；两端可复用模型；支持离线和游客模式；不把业务层绑定到单一平台或云供应商。

### 影响与代价

需要承担模型转换、前后处理、原生运行时和设备优化成本。`SPK-002` 若证明内存、速度、体积或 iOS 集成不可接受，必须更新本 ADR；系统/ML Kit 是 MVP 降级候选。

### 验证方式

执行 `SPK-002` 的 Android/iOS 性能、准确率、模型下载和异常测试，细节见 `docs/architecture/OCR_PLUGIN.md`。

## ADR-0010：本地 LLM 的三种网络连接模式

- 日期：2026-07-27
- 状态：被 `ADR-0011` 取代
- 关联任务：SPK-003、AI-001

### 背景

游客不能使用平台托管 AI，但可以连接电脑、NAS 或家庭服务器上的 Ollama/OpenAI-compatible API。移动网络存在局域网权限、明文 HTTP、网络隔离、动态 IP、证书和密钥泄露风险。

### 决策

1. `lan_http`：同一局域网私网地址，用户显式开启不安全 HTTP。
2. `private_network`：Tailscale/WireGuard 等加密私有网络，作为远程访问首选。
3. `https`：带认证的 HTTPS 反向代理，面向高级自托管用户。

业务协议优先采用 OpenAI-compatible API；Ollama 原生 API 通过 Adapter 支持。禁止默认允许公网 HTTP，禁止建议用户裸露 Ollama 端口。

### 原因

LAN 降低 MVP 门槛；私有网络兼顾远程访问和加密；HTTPS 适合已有 NAS/域名基础设施的用户。

### 影响与代价

客户端需要 URL 分类、DNS 解析复核、重定向限制、超时/取消和敏感日志过滤。iOS/Android 分别处理本地网络和明文策略。API Key 只能进入 Keychain/Keystore。

### 验证方式

执行 `SPK-003`，按 `docs/architecture/LOCAL_LLM_NETWORK_SECURITY.md` 完成真机实验。

## ADR-0011：自定义 LLM 使用单一 API 配置与协议 Adapter

- 日期：2026-07-27
- 状态：生效
- 关联任务：SPK-001、SPK-003、AI-001
- 取代：ADR-0010

### 背景

项目负责人明确：移动端不需要让用户选择 LAN、VPN 或 HTTPS 等网络方案。用户只需要配置 API 地址和 Key；OpenAI、Gemini 等接口差异由应用内部适配。

### 决策

自定义 LLM 的统一配置为协议类型、API Base URL、API Key 和模型。API 地址所在网络不形成不同产品模式。首版实现 OpenAI-compatible 与 Gemini Adapter，页面和菜谱业务只依赖统一 `LlmProvider`。

### 原因

这符合用户心智，减少配置复杂度，并将供应商路径、鉴权、请求体和响应格式差异隔离在可测试的 Adapter 中。

### 影响与代价

需要为每种协议维护独立 Adapter 和契约测试。HTTP 地址仍需显示明文风险；API Key 仍只能存入 Keychain/Keystore。原先针对三种网络拓扑的产品配置和验收项全部取消。

### 验证方式

`SPK-001` 实现 Flutter 基础骨架和两个 Adapter 的单元测试；`SPK-003` 使用真实服务完成多协议兼容性矩阵。

## ADR-0016：公开内容“无可用内容”按目标笔记是否返回分类提示

- 日期：2026-08-02
- 状态：生效
- 关联任务：BUG-003、IMPORT-003

### 背景

真实小红书 `explore/<note-id>` 链接在没有完整分享参数（如 `xsec_token`）时，平台可能返回推荐 feed、风控或验证页，而不是目标笔记详情；页面解析后可能既无文本也无媒体。原 Adapter 把这类情况统一映射为 `invalidPayload` 并直接透传英文原文 `The public page did not expose usable text or media.`，用户无法理解，也无法知道下一步该做什么。

### 候选方案

1. 保持统一 `invalidPayload` 和英文原文。
2. 无内容时从推荐 feed 中猜测选取目标笔记或任意内容。
3. 无内容时先判断“响应是否包含目标笔记 ID”，再分类给出可操作中文错误。

### 决策

采用方案 3：

- 页面无文本且无媒体时，先从请求后的 `resolvedUri`（必要时回退到规范化链接）提取目标笔记 ID，并检测响应正文是否包含该 ID：
  - 包含目标 ID：目标页已获取但解析失败，映射 `invalidPayload`，不可重试，提示稍后重试或粘贴正文降级。
  - 不包含目标 ID：平台未返回目标内容，映射 `contentUnavailable` 且允许重试，提示检查链接（可能需要完整带参数的分享链接）、稍后重试或粘贴正文降级。
- 页面状态标记扩展：登录墙、内容不存在/已删除、风控/限流（`captcha`、安全验证、访问过于频繁等）分别映射 `authorizationRequired`、`contentUnavailable`、`networkUnavailable`（可重试）。
- 真实调试证据确认平台可能把请求重定向到 `/404/` 安全验证页（如 `/404/sec_...`，HTTP 200 但为验证/失效壳页）：当 `resolvedUri.path` 为 `/404` 或 `/404/...` 时，在判空之前映射为可重试 `networkUnavailable`，文案“平台未返回笔记内容（可能正在执行安全验证，或笔记已失效）…”，避免把 404 壳页误判为“已获取目标页”。
- 错误文案使用中文可操作表述，不直接透传平台原始英文；不显示目标 ID 之外的敏感参数。
- 调试信息（HTTP 状态、content-type、页面体积、`__INITIAL_STATE__`/noteData/OG/JSON-LD 结构特征、`/404/` 路径、重定向次数、目标 ID 是否出现）只通过 `debugPrint` 输出控制台/Logcat，不进入用户可见错误消息。
- 不从推荐 feed 中猜测选取非目标内容，继续保持不错误选取对象的安全边界。

### 原因

区分“目标页解析失败”与“未返回目标内容”能让用户采取正确的下一步操作；风控类限制通常是临时的，可重试符合平台行为特征；中文文案降低理解成本，避免用户把平台风控误认为产品故障。

### 影响与代价

- 判空错误语义变化会影响既有 Adapter 测试与失败页文案；相关测试定义已同步更新。
- “未返回目标内容”设为可重试后，任务会占用未完成列表直到尝试耗尽或用户主动结束（`BUG-005`）。
- 仅凭“正文是否包含目标 ID”无法区分“笔记已删除”与“临时风控”，两者统一按可重试处理，由重试次数与用户主动结束兜底。

### 验证方式

- Adapter 单测定义覆盖：无内容且不含目标 ID（`contentUnavailable`、可重试）、无内容但含目标 ID（`invalidPayload`、不可重试）、风控标记页（`networkUnavailable`、可重试）。
- Android 真实复测按更新后的 `BUG-003` 验收方法执行，由项目负责人反馈稳定文案、阶段与进度。

## ADR-0017：链接导入默认启用本地 OCR（能力就绪时），图文与正文整合后交给 AI

- 日期：2026-08-03
- 状态：生效
- 关联任务：IMPORT-007、OCR-001、OCR-002、BUG-003

### 背景

小红书/抖音笔记几乎总是图文混排，菜谱信息（食材、用量、步骤）可能同时存在于页面正文与配图。此前链接导入执行计划默认为 `ocr: disabled`，配图从未进入 OCR 阶段：有图片且正文不足的内容会直接失败“需要先完成图片文字识别”，有正文的图文内容则只使用正文、丢弃图片信息。

### 候选方案

1. 链接导入固定启用 `ocr: local`，未安装 OCR 时整体失败并引导安装。
2. 保持 `ocr: disabled`，图片信息继续丢弃。
3. 执行计划自动解析：本地 OCR 能力就绪时启用 `ocr: local`，未就绪时回退纯文本路径。

### 决策

采用方案 3：

- `AiRecipeBackendFacade.runImportTask` / `dispatchPendingImports` 的执行计划参数改为可空；为 null 时读取 `AppCapability.localOcr` 能力快照自动解析：就绪 → `ImportExecutionPlan(llm: custom, ocr: local)`；未就绪或快照不可读 → `ImportExecutionPlan()`（纯文本路径）。
- OCR 阶段复用既有 `OcrEnrichingImportContentProcessor` + `RemoteStagingOcrProvider`：远程图片经 OCR-002 安全暂存后由本地 OCR 识别，OCR 文本片段与页面正文片段按顺序合并为同一批 `textFragments` 证据，再统一交给 `LlmRecipeGenerationProcessor`。
- 回退语义：OCR 未安装时，有正文的图文内容仍可纯文本生成；只有图片无正文的内容由 LLM Processor 报“需要先完成图片文字识别”，提示用户安装 OCR 模型后重试。
- 无图（纯文字）内容不触发 OCR 调用（装饰器按 `requiresOcr` 警告透传）。
- OCR 链路（模型未安装、识别不可用、图片无效、网络/超时等）的用户可见错误文案全部固定为中文可操作表述，不再透传底层英文。

### 原因

方案 3 在“充分利用图片信息”和“不因 OCR 安装状态阻塞纯文字内容”之间取得平衡：设备安装 OCR 模型后，图文链接自动把图片与正文整合交给 AI；未安装时不制造新的阻塞，同时为纯图片内容给出明确安装指引。固定中文文案延续 ADR-0016 的“不直接透传底层英文”原则。

### 影响与代价

- `runImportTask` 默认行为变化：OCR 就绪的设备上，链接导入自动多一次 OCR 阶段（耗电、耗时、需模型）；行为随能力快照动态变化。
- 真实 PP-OCRv5 模型质量与性能仍未验证（`SPK-002`），识别质量由后续 Spike 验收。
- 能力快照读取失败时静默回退纯文本路径，不阻塞导入主流程。

### 验证方式

- Facade 测试定义：OCR 就绪自动启用、OCR 未安装降级、纯图片失败提示、无图内容不触发 OCR。
- Android 复测按 `tests/acceptance/IMPORT-007-link-import-ocr-2026-08-03.md` 执行，由项目负责人反馈 OCR 阶段推进、图文整合效果与错误文案。

## ADR-0018：链接导入改用内置浏览器内核（WebView）抓取，通用任意网页

- 日期：2026-08-03
- 状态：生效
- 关联任务：IMPORT-008、IMPORT-006、IMPORT-007、BUG-003
- 替代：`PublicPageImportContentAdapter` 直连抓取路径（BUG-003 相关 Adapter 不再作为链接导入主路径）

### 背景

链接导入一直采用直连 HTTP 抓取小红书/抖音页面并解析的方式（`PublicPageImportContentAdapter`）。真机实测发现：小红书图片 CDN（sns-webpic-qc.xhscdn.com 等）对客户端请求返回 403（IPv6 边缘节点），而用户在真机浏览器中可正常打开；同时平台存在登录墙、安全验证、`/404/` 风控壳页，直连解析频繁失败且难以穷尽平台反爬变化。项目负责人提出：改用内置浏览器环境加载网页并在浏览器环境中保存网页文本与图片（更符合平台访问方式），并希望后续支持其他平台。

### 候选方案

1. 保留直连 Adapter，继续优化请求（IPv4 优先、UA/Referer、故障转移）应对 403 与风控。
2. 全面替换为内置浏览器内核（Android WebView / iOS WKWebView）加载页面，从 DOM 与浏览器会话提取文本与图片字节。
3. 混合：直连优先，失败时回退浏览器内核。

### 决策

采用方案 2（全面替换），按项目负责人确认：

- 链接导入主路径改为：后台隐藏 WebView/WKWebView 加载目标网页 → 页面渲染完成后从 DOM 提取标题、正文、作者、`og:` 元数据与图片地址 → 图片字节通过浏览器会话请求获得（与真实浏览器访问行为一致，不绕过平台访问控制）→ 复用现有 `ImportContent` 领域模型与 OCR/LLM/草稿流程。
- 文本与图片均来自网页真实内容（DOM/网络资源），不做截图后 OCR 兜底（除用户主动上传截图外）。
- 架构按"任意 URL 网页"设计，小红书/抖音优先适配，后续平台无需改造主链路；平台特化仅限可选的页面选择器与降级文案。
- 后台隐藏加载：用户无感，仅通过现有导入进度展示阶段；不引入可见浏览器 UI（WebView 仅用于数据获取，不用于界面呈现，与 ADR-0013 边界一致）。
- 浏览器内核加载失败/登录墙/验证码/内容为空时，按产品文档 5.3.7 分类给出中文可操作提示与降级入口。

### 原因

- 浏览器会话（真实 Cookie/JS 执行/TLS 指纹）能访问用户浏览器可访问的内容，规避直连 403 与平台风控的对抗成本。
- 从 DOM 提取文本比直连 HTML 解析更贴近用户所见，比截图 OCR 更准确且无 OCR 依赖。
- 通用网页架构一次投入，覆盖后续新增平台。
- 符合"合法访问"取向：以真实浏览器方式获取公开页面内容，不绕过平台访问控制。

### 影响与代价

- 新增 Android WebView 平台通道（Kotlin），封装：后台加载、页面完成回调、DOM 提取（注入 JavaScript）、图片字节拦截（`shouldInterceptRequest` 同会话请求）、超时/取消、登录墙与验证码识别。
- iOS 需要 WKWebView 等价实现，本轮暂缓（iOS 全程未验证）。
- WebView 会携带系统 Cookie/会话：只用于请求目标页面资源，不得采集、存储或外传 Cookie 与登录态；隐私设置中"允许获取网页内容"授权联动。
- 图片仍经 OCR-002 安全暂存层校验（格式/大小/公网地址），字节来源改为浏览器会话。
- 小红书/抖音页面可能要求登录（正文/图片部分可见）或触发验证码，需在错误分类与降级中体现；页面 SPA 渲染需要等待与超时控制。
- 直连 Adapter 不再作为链接导入主路径；其测试与错误文案（ADR-0016）保留为降级/人工粘贴场景参考，不删除既有交付。
- Codex 沙箱无法构建/运行 Android；实现按 ADR-0015 由项目负责人构建真机复测。

### 验证方式

- 单元/组件测试定义：WebView 抓取结果到 `ImportContent` 映射、失败分类、超时/取消、图片字节校验。
- Android 真机复测：导入小红书/抖音/普通网页链接，确认文本与图片提取、草稿生成、配图轮播、登录墙与验证码提示、断网降级。按 `tests/acceptance/IMPORT-008-webview-import-*.md` 执行。

## ADR-0013：HTML 原型作为 Flutter UI 唯一视觉事实源

- 日期：2026-08-01
- 状态：生效
- 关联任务：UI-001

### 背景

项目已经在 `design/prototypes/` 中形成可离线运行的高保真 HTML 原型，但实际 Flutter 页面曾只复用业务结构，未完整遵循原型的纸张色板、像素阶梯缺角、硬边阴影、三栏导航和页面层级。项目负责人明确要求实际产品完全使用 Flutter 复刻原型效果，不能使用 WebView 代替原生界面。

### 决策

1. `design/prototypes/index.html`、`prototype.css`、`app.js` 是当前 Flutter UI 的唯一视觉事实源；视觉变化先更新原型或形成明确设计决策，再同步 Flutter。
2. 生产界面只使用 Flutter Widget、`CustomPainter`、`CustomClipper`、Animation 和本地资源实现，不引入 WebView，也不在应用内运行 HTML/CSS/JavaScript 原型。
3. HTML 中的像素阶梯缺角、纸张色板、硬边阴影、等宽眉题、三栏导航、右下悬浮添加入口和状态反馈应通过共享 Flutter Token/组件实现，避免各页面独立近似。
4. 视觉实现继续遵守业务边界：页面只调用 `AiRecipeBackendFacade` / Application，不因复刻原型而直接访问 SQLite、Repository、SharedPreferences、安全存储或 Provider。
5. Android 视觉切片使用固定截图矩阵验收；iOS 必须单独验证，不得从 Android 结果推断完成。

### 原因

- 避免设计原型和可运行产品形成两套长期分叉的视觉事实。
- Flutter 原生实现能够保留跨平台可维护性、无障碍、导航和业务状态管理能力。
- 共享像素组件可以减少后续页面扩展时的视觉漂移。

### 影响与代价

- CSS `clip-path`、steps 动效和浏览器字体需要在 Flutter 中等价实现，不能直接复用网页渲染结果。
- Android 与 iOS 的系统字形和像素密度可能存在细微差异，需要分别截图验收。
- 视觉修改必须同时检查共享组件和全部关键状态，不能只修单页理想态。

### 验证方式

以 `tests/acceptance/UI-001-flutter-native-prototype-replication-2026-08-01.md` 和 `tests/acceptance/artifacts/UI-001-2026-08-01/` 为 Android 证据；同时执行 Flutter 静态分析、全量测试和 WebView 依赖扫描。`UI-001` 只有在项目负责人完成最终视觉确认后才能从 `VERIFY` 进入 `DONE`。

## ADR-0014：导入取消采用 localVersion CAS 与草稿补偿清理

- 日期：2026-08-01
- 状态：生效
- 关联任务：BUG-002、IMPORT-001、IMPORT-002、AI-002、AI-003、SPK-003

### 背景

导入 Runner 与用户取消可以从同一旧任务快照并发执行。仅依赖内存取消 Token 或普通 upsert 时，后到的 Provider 成功、Schema 错误或失败状态可能覆盖已经持久化的取消；若草稿先保存而任务取消获胜，还可能留下孤立草稿。

### 候选方案

1. 继续最后写入者获胜，只在错误分支检查内存 Token。
2. 为所有任务操作加进程内互斥锁。
3. 使用持久化 `localVersion` Compare-and-Set，冲突后重读，并对迟到草稿执行受限补偿清理。

### 决策

采用方案 3：

- 已存在 ImportTask 的写入必须携带读取时的 `expectedLocalVersion`。
- SQLite 通过 `id + local_version` 条件原子更新，0 行更新转换为明确写冲突。
- 冲突后以数据库最新状态为事实源；`cancelled` 优先于后到成功和失败。
- 草稿已经写入但任务取消获胜时，执行幂等补偿删除。
- 补偿删除只允许作用于结果 ID、来源匹配且仍为草稿的 Recipe，禁止删除正式菜谱。

### 原因

CAS 同时覆盖进程内并发和未来多执行器场景，不依赖单个 Runner 实例的锁；冲突重读能保留真实用户操作顺序。受限补偿清理解决跨聚合提交无法一次事务完成的问题，同时把误删风险限制在可验证范围内。

### 影响与代价

- Repository Fake、SQLite 实现和所有写用例必须遵守期望版本契约。
- Runner 需要在成功和失败边界重读任务，并处理补偿失败。
- 当前不是跨数据库/跨服务分布式事务；未来云端任务必须重新设计服务端版本和幂等键。
- Android 真实点击取消仍是发布前验收条件，自动化测试不能代替 UI→Application 的真机链路。

### 验证方式

- SQLite 真实文件中并发取消与后到 Schema 错误。
- SQLite 真实文件中并发取消与后到成功、草稿补偿删除和数据库重开。
- ImportTask Runner、Use Case、Repository、Facade 定向回归和 Flutter 全量质量门。
- Android OpenAI-compatible 请求中的真实点击取消、迟到返回和 App 重启验收。

## ADR-0015：测试由项目负责人执行，Codex 负责提供方法并归档结果

- 日期：2026-08-02
- 状态：生效
- 关联任务：OPS-004、BUG-004

### 旧流程

Codex 在实现后默认运行自动测试、模拟器或真机验收，并把测试结果直接写入任务与验收记录。

项目负责人已经启动并掌握 Android 模拟器，希望由本人统一执行实际测试，避免 Codex 代测造成环境差异、重复操作或错误归档；Codex 的职责改为提供清晰可复现的测试步骤，并在收到真实结果后维护长期事实源。

## ADR-0019：WebView 抓取重构为阶段状态机 + 图片顶层导航取图（高级工程师方向）

- 日期：2026-08-03
- 状态：生效（代码实现按此方向；图片顶层导航同源读取需真机 Spike 验证，Spike 成功前不得视为已解决）
- 关联任务：IMPORT-008、IMPORT-006、SPK-007
- 替代：IMPORT-008 首版"`onPageFinished` + 固定延迟 + JS 跨域 fetch 并发下载全部图片"的实现

### 背景

IMPORT-008 首版真机复测出现两类独立故障：①"网页加载超时"——单一 45s 超时覆盖页面导航、DOM 提取、30 张图片并发下载、Base64 转换、跨桥传输和写盘，无法定位实际停在哪一阶段；②图片 403——客户端/应用网络栈被小红书 CDN 拒绝，应继续坚持"图片请求必须由 WebView/Chromium 发起"。

高级工程师评审结论（`修复方案.md`）：
- `shouldInterceptRequest` 不是抓取 WebView 已下载响应体的接口（返回 null 拿不到字节，返回 WebResourceResponse 则回到应用网络栈），不能作为取图主方案。
- 推荐路线：页面 WebView 提取文本和图片 URL → 停止页面继续加载 → 把每张图片 URL 作为 WebView 顶层页面逐张打开 → 在图片所属同源环境中读取图片字节 → 单张回传原生并立即落盘。
- 顶层图片同源读取是否可用，取决于 Android WebView 对顶层图片文档的具体实现，必须先做最小真机 Spike，不能在验证前假设可用。

### 决策

1. **阶段状态机**：WebView 抓取改为显式阶段 `NAVIGATING → WAITING_CONTENT → EXTRACTING → FETCHING_IMAGES`；不再依赖 `onPageFinished` 作为"完成"信号。主框架首次提交用 `onPageCommitVisible`（旧版本以 `onPageFinished` 兜底）；`WAITING_CONTENT` 每 300–500ms 轻量 DOM 探测（标题/正文长度、图片候选、结构化状态、登录墙/风控特征），满足任一条件即进入提取；各阶段独立超时：导航 15–20s、内容等待硬上限 10–15s（含 5s 软空闲）、提取 3–5s、单图 8–10s、图片阶段总 20–30s。
2. **结果分类**：至少区分 NAVIGATION_TIMEOUT、CONTENT_NOT_READY、RISK_CONTROL_OR_LOGIN_REQUIRED、DOM_EXTRACTION_FAILED、IMAGE_PARTIAL、IMAGE_ALL_FAILED、RENDERER_GONE、CANCELLED、SUCCESS，映射为既有中文错误/成功语义；不再用笼统"网页加载超时"掩盖真实阶段。
3. **图片逐张顶层导航取图**：正文与图片 URL 提取成功后立即 `stopLoading()`；逐张把图片 URL 作为 WebView 顶层页面打开（复用同一 WebView/Profile）；等待图片文档 `<img>` `complete && naturalWidth>0`；按优先级读取——路径 A 同源 `fetch(location.href)`（图片成为顶层文档后与自身 URL 同源，不再跨域）→ ArrayBuffer/Base64 回传；路径 B Canvas 导出 JPEG/WebP 兜底；每张独立超时、失败继续下一张、最多尝试 12 个候选、成功保存最多 9 张、每张完成立即回传原生并写盘。
4. **删除取图放大因素**：不再 30 张并发 + `Promise.all` + 整包 Base64 一次过桥；逐张传输、逐张写盘、单张字节/尺寸上限，原生侧校验 MIME/魔数/宽高/字节数。
5. **WebView 配置**：取消"桌面 Chrome UA + 1×1 视口"异常组合，第一轮用系统默认移动 UA + 正常移动布局尺寸（约 360×800，attach 且正常 layout，被 Flutter 界面覆盖不展示）；不在加载中修改 UA。
6. **安全桥**：不在加载第三方网页的主 WebView 中常驻暴露 `addJavascriptInterface`；本轮主页面 DOM 提取用 `evaluateJavascript` 同步小体积返回值，图片文档（纯资源、无第三方脚本）阶段也用 `evaluateJavascript` 读取；后续按 Spike 结论再评估 `WebViewCompat.addWebMessageListener`（来源受限、ArrayBuffer、nonce/大小限制）作为正式二进制回传通道（`androidx.webkit` 依赖待引入）。
7. **请求隔离**：每次抓取使用唯一 requestId/generation，所有延迟任务、DOM 轮询、页面回调、JS 消息、图片下载、超时、写盘回调都必须核对当前请求，防止重定向、多次回调或上一任务迟到回调污染下一次导入；取消/超时执行 `stopLoading()`、清除全部 Handler/Runnable、终止图片队列、丢弃过期回调、最后销毁/重置 WebView。
8. **小红书回退策略**：对已知小红书 CDN 不再执行 Dart 原生直连回退（已被证实只会重复 403、增加耗时并混淆日志）；其他普通站点保留直连快速路径。
9. **隐私与登录态**：默认匿名导入仅处理无需登录的公开内容；不读取/复用用户 Chrome Cookie；遇到登录墙或风控明确提示截图、视频、粘贴正文或手动录入；不在本轮实现应用内登录平台；后续确有必要时再评估可见 WebView + 独立 Profile + 应用内登录与数据清理入口。

### 原因

- 阶段状态机把"45s 到底停在哪个阶段"变成可观测问题，避免超时定义掩盖真实故障。
- 顶层导航使图片文档与图片 URL 同源，规避页面内跨域 fetch 的 CORS、credentials×ACAO、Fetch Metadata、页面 CSP 与 Promise.all 慢请求拖累等多重限制，同时保留 Chromium 网络栈的浏览器特征。
- 不引入 `shouldInterceptRequest` 作为取图主方案，避免退回已被拒绝的应用网络栈。
- 逐张串行 + 单张超时 + 最多 9 张，保证正文成功时图片失败只产生"配图部分失败"，不再整体失败为"网页加载超时"。

### 影响与代价

- Kotlin `WebViewFetchMethodHandler` 将整体重构（状态机、阶段超时、逐张顶层导航取图、新脚本集）；移除 `addJavascriptInterface` 桥。
- Dart Adapter 对小红书/抖音平台不再回退远程直连；错误码映射按新分类调整；测试定义同步更新。
- 顶层图片文档的同源读取、Canvas 导出与 JS 执行可用性依赖 Android WebView 具体实现，需 SPK-007 真机验证；若不可行，按 `修复方案.md` 决策分支处理（正文成功 + 提示手动补图，或评估服务端真实浏览器方案）。
- 日志规范：统一带 requestId 与单调时钟耗时；禁止记录 Cookie、Token、完整签名 URL 查询参数、图片 Base64 与完整正文。
- 本次不引入 `androidx.webkit` 依赖（Web Message Bridge 留待 Spike 成功后按需评估）。

### 验证方式

- SPK-007 Spike（`research/spikes/SPK-007-top-level-image-nav.md`）：10–20 个真实公开链接，覆盖不同 WebView 版本、Wi-Fi/移动网络、单图/九图以上、带参数图片 URL、无登录/登录墙/风控页；验证顶层图片显示、同源 fetch 与 Canvas 导出可行性。
- 状态机与分类验证：`tests/acceptance/IMPORT-008-webview-import-2026-08-03.md` 更新为分阶段复测，Logcat 按阶段核对。
- 验收原则：正文提取成功时，图片失败/超时/风控只能产生"配图部分失败"，不得让整个导入变成"网页加载超时"。

## ADR-0020 冰箱作为第四个一级导航，分区库存 UI，本地选择食材推荐不依赖 AI

- 日期：2026-08-03
- 状态：生效
- 关联任务：FRIDGE-001、FRIDGE-002、RECO-001、FRIDGE-003、RECO-002、DESIGN-005、SPK-008
- 关联风险：R-019

### 背景

产品需要从“保存和执行菜谱”扩展到“管理家中食材并决定现在做什么”。如果继续把添加、购物清单或推荐都放进一级导航，会造成入口膨胀；如果推荐每次依赖 LLM，则离线、游客、成本、稳定性和可解释性都不符合 Local-first 原则。库存还涉及同名多批次、日期、数量未知和扣减错误，必须在数据与交互上保留用户确认。

### 决策

1. 底部一级导航固定为“首页 / 菜谱库 / 冰箱 / 我的”。添加和导入继续使用全局 FAB；购物清单是二级页面，不增加第五个 Tab。
2. 冰箱内部使用“库存 / 推荐”二级切换。库存按批次建模，支持同名多批次、存放位置、可选数量/单位、可选购买/到期日期、分类和备注。
3. 冰箱库存 UI 采用轻拟物真实冰箱心智：默认按冷藏区、冷冻区、常温区和其他区展示，区域内使用层架、抽屉和食材 chip / 卡片表达，但保持移动端卡片化可用性。
4. 首版本地推荐只读取本地正式菜谱，排除草稿和回收站；使用确定性离线匹配，不依赖登录、网络或 LLM。
5. 推荐页先由用户选择本次想优先使用的库存食材，支持单选、多选、全部、临期和按分区快捷选择；已选食材代表推荐意图，未选择但冰箱已有的食材可在卡片中标注为“冰箱已有”。
6. 推荐分为“已具备 / 现在就能做”“缺 1 样”“缺 2 样”“优先清库存”，缺失超过 2 样默认收起为更多缺失；排序依次考虑缺失食材更少、临期食材命中更多、匹配比例更高。
7. 数量为空或单位无法换算时，只能提示“有该食材，数量是否足够需确认”，不得把名称命中解释为数量一定足够；中文同义词、标准化和单位换算由 SPK-008 验证后再固化。
8. 缺失食材可以加入购物清单；已购食材是否转为库存批次必须由用户确认。
9. “自动消耗”定义为完成烹饪后自动生成预计消耗清单，用户逐项确认、调整、换批次或取消后才扣减；同名多批次默认选择到期更早批次，但提交前必须可见、可改，不产生负库存。
10. “用现有食材生成新菜谱”作为后续独立 AI 入口，仅在存在可用 LLM Provider 时开放；结果进入草稿确认，不与本地推荐混排。
11. 首版不包含条码扫描、拍照/小票识别、未确认自动扣减、后台到期通知和家庭实时共享库存。

### 原因

- 四栏导航让冰箱获得稳定一级入口，同时避免添加和购物清单占用过多 Tab。
- 轻拟物分区符合用户对冰箱的生活心智，能降低“食材放在哪里”和“从哪里选来推荐”的理解成本。
- 确定性本地推荐符合游客完整可用、离线可用和结果可解释的 Local-first 决策。
- 批次模型可以正确表达同名食材的不同到期时间、位置和数量，支持优先清库存和可追溯扣减。
- AI 生成与本地推荐分离，可以避免把不确定生成结果伪装成“家里已有食材就能做”。

### 影响与代价

- Flutter 现有三栏导航在实施 FRIDGE-002 前需要调整为四栏，并保持 FAB 行为。
- 需要新增库存批次、库存变更记录和推荐结果模型，以及对应领域/API/SQLite 迁移契约。
- 购物清单与烹饪完成流程需要新增显式确认边界。
- 名称标准化和单位换算未完成 SPK-008 前，推荐必须采用保守降级，不得宣称数量精确满足。

### 验证方式

- 先按 `tests/acceptance/FRIDGE-001-fridge-recommendation-planning-2026-08-03.md` 完成文档走查。
- `DESIGN-005` 完成低保真状态走查后，才能开始库存、推荐和扣减的业务实现。
- `SPK-008` 使用真实中文样本记录命中、误判、数量可判定率和失败边界。

## ADR-0021 食材统一标准 ID 与本地别名词典（按项目负责人提供的食材标准化解决方案）

- 日期：2026-08-04
- 状态：生效（SPK-008 同义词部分落地）
- 关联任务：RECO-001、FRIDGE-002、FRIDGE-003、SPK-008
- 关联风险：R-019

### 背景

推荐复测发现“库存：西红柿 / 菜谱：番茄”无法匹配。仅靠字符串格式标准化不能解决语义别名。按项目负责人提供的《解决方案.md》落地：库存与菜谱都统一到标准食材 ID，搜索、推荐、扣减共用同一标准化器。

### 决策

1. 新增业务组件 `IngredientCanonicalizer`（统一标准化器）+ `IngredientAliasRepository`（系统别名词典）：输入原始名称 → 输出 `canonicalIngredientId`（如 `ingredient.tomato`）、`canonicalName`、`matchType`（exact/alias/format/unknown）。
2. 匹配规则三层：①精确/别名匹配（词典内同义词如 番茄=西红柿=蕃茄 视为同一食材，matchType=alias）；②格式标准化匹配（trim、去括号备注、全半角、去标点、简繁轻映射、数量单位拆分，matchType=format）；③未知名称不自动命中，保留原名称并进入“待确认”，不把近似名称当命中。
3. 明确区分同义词与相近食材：本阶段只实现 alias（番茄=西红柿）；小番茄≠番茄、鸡蛋≠鸡蛋液、辣椒≠小米椒、白菜≠娃娃菜、猪肉≠五花肉 等一律不默认等价（variant/substitute/category 留待 P2）。
4. 推荐逻辑“已选食材作为偏好而非唯一限制”：默认用户选中的食材必须参与，但冰箱中未选择的其他可用食材也可补齐菜谱（卡片标注“冰箱已有·可补选”）；提供开关“仅使用已选食材”（默认关闭）。
5. 缺 1 样/缺 2 样按标准食材 ID 去重计算，同一菜谱内相同 canonicalId 只计一种。
6. 数量状态与“完全没有”区分：命中食材分为 充足/不足（显示“库存不足：还需要 X”）/数量未知（提示需确认）；单位不一致视为无法判定（需确认）。库存不足的菜谱不进入“现在能做”。
7. 推荐卡片展示匹配依据，例如“西红柿 → 番茄（同义词匹配）”，避免用户认为推荐逻辑不稳定。
8. 老数据即时回填：读取时即时标准化，不要求用户重新录入；未识别项保留原名称。
9. 用户个人别名词典（来源 user）与“小番茄是否替代番茄”的确认流程放入 P1/P2，本轮不实现。
10. 搜索与推荐共用 `IngredientCanonicalizer`：搜索“西红柿”可命中库存“番茄”与菜谱标题“番茄炒蛋”。

### 原因

- 语义别名无法靠格式标准化解决，需要规范食材 ID。
- 本地静态词典满足离线、游客完整可用、可解释；不依赖 LLM。
- “已选偏好 + 冰箱补齐”最符合“我有这个食材帮我推荐能做什么”的使用习惯。
- 数量与“有没有”区分，避免把库存不足误报为“能做”。
- 只实现 alias 避免把小番茄/番茄酱等相近食材误判为同一种造成误推荐。

### 影响与代价

- 推荐用例、库存搜索、推荐卡片 UI 需按 canonicalId 重构；新增词典与标准化器。
- 词典覆盖面有限，未收录名称退化为格式匹配或待确认。
- 单位换算仍不做（P2），单位不一致时仅提示需确认。

### 验证方式

- 新增用例：同义词命中（西红柿↔番茄）、格式标准化（括号/全半角）、相近食材不误配（小番茄≠番茄）、标准 ID 去重、数量不足与数量未知、strictSelected 开关、搜索同义词命中。
- 真机按 `tests/acceptance/RECO-001-recommendation-2026-08-04.md` 复测：库存“西红柿”+ 菜谱“番茄炒蛋”应匹配并在卡片显示同义词解释。

## ADR-0022 冰箱推荐升级为“基础食材 + 属性规格 + 三值匹配”的渐进式语义食材系统

- 日期：2026-08-04
- 状态：生效
- 关联任务：RECO-001、FRIDGE-002、FRIDGE-003、SPK-008
- 关联风险：R-019
- 前置：ADR-0021（标准 ID + 别名词典）在本 ADR 中升级，不再作为推荐唯一依据

### 背景

按项目负责人提供的《解决方案.md》走查结论：仅靠“标准食材 ID + 别名词典”无法表达“精瘦肉 ⊂ 猪肉”“五花肉 = 猪肉 + 腹部 + 肥瘦相间”“肉末 = 肉 + 绞碎（物种未知）”这类上下位与属性约束关系，也无法区分“库存更具体可满足菜谱宽泛要求”与“库存宽泛面对菜谱具体要求”这两个不对称方向。推荐必须从“名称是否相等”升级为“库存实际规格是否满足菜谱要求规格”。

### 决策

1. 食材统一采用“基础食材概念（baseConcept）+ 可选属性分面（facet）”模型：部位 cut、肥瘦 fatLevel、形态 form、加工状态 processing；每个属性可为未知，未知不等于缺失。
2. 本地受控知识库在 ADR-0021 别名词典基础上增加“规格条目”：例如 精瘦肉=pork+veryLean、五花肉=pork+belly+mixed、半肥半瘦=pork+mixed、肉末=meat+minced；保留 alias 同义词条目（番茄=西红柿）。不依赖 LLM 参与每次匹配。
3. 匹配改为三值逻辑 `YES / MAYBE / NO`：
   - 基础食材一致且属性满足，或库存规格比菜谱要求更具体 → YES。
   - 基础食材一致但关键规格未知或库存比菜谱更宽泛（如猪肉→精瘦肉、肉末→猪肉末）→ MAYBE，进入“可能可以做”，不计为确定缺失。
   - 基础食材冲突或属性明确冲突（肥肉→精瘦肉、牛肉→猪肉）→ NO，不算缺失但阻断“现在能做”。
4. 推荐分组升级为：现在就能做 / 可能可以做 / 缺 1 样 / 缺 2 样 / 优先清库存 / 可替代尝试（MVP 仅标记）。排序依次为缺失更少、MAYBE 更少、临期命中更多、匹配比例更高。
5. 库存批次持久化可选规格（base_concept_id、cut、fat_level、form、processing、spec_source），录入采用渐进式：只输名称 → 即时解析给候选规格（可跳过）。
6. 菜谱食材保存时由本地规则解析名称得到规格并落库（base_concept_id、facets、spec_confidence、spec_source）；读取时对旧数据即时回填解析，不强制用户重新导入。
7. 导入菜谱时不打断用户：解析为 unknown/低置信的食材只在确认页显示轻量标识（如“肉末 · 种类待确认”），推荐真正受影响时再让用户确认。
8. MAYBE 确认交互：卡片提供“仅本次视为可用”或“去修改库存规格”，不直接改写全局词典。
9. 用户个人别名词典（来源 user）与“小番茄是否替代番茄”确认流程继续放入 P1/P2。
10. “只清空菜谱数据”作为本轮数据重置方式：清空 recipes 及其子表，保留库存、分类与设置，便于重新导入菜谱验证新解析链路。

### 原因

- 属性模型能表达上下位与加工形态，而固定树或纯别名都无法同时表达“五花肉是猪肉”与“肉末不是猪肉的下级品种而是加工形态”。
- 三值匹配避免两个极端错误：把可能有的食材算成缺失、把规格不符的食材算成能做。
- 渐进式录入与导入不打断，把人工成本控制在“真正影响本次烹饪的少数歧义”上，符合产品使用角度。

### 影响与代价

- 领域模型（Ingredient/InventoryBatch）、数据库 v6 迁移、匹配引擎、推荐分组与卡片 UI、库存录入页、草稿确认页轻量标识均需同步升级。
- 知识库覆盖面有限，未收录名称退化为格式匹配或待确认；上下位关系仅覆盖 MVP 常见肉类/水产/蔬菜。
- 单位换算仍不做（P2），单位不一致仅提示需确认。
- 用户确认只改批次规格或本次会话，不写全局词典。

### 验证方式

## ADR-0023 食材家族与模糊匹配：宽泛概念→具体要求的“可能匹配”通用化

- 日期：2026-08-04
- 状态：生效
- 关联任务：RECO-001、SPK-008
- 关联风险：R-019
- 前置：ADR-0022（基础食材 + 属性规格 + 三值匹配）。本 ADR 在 ADR-0022 之上增加“食材家族”与“菜谱食材要求强度”，将 辣椒→青椒 这类“宽泛概念 vs 具体概念”的处理通用化，不作为单一食材特例。

### 背景

按项目负责人《解决方案.md》走查结论：仅靠“别名 + 上下位”无法处理 冰箱“辣椒”→菜谱“青椒”这类问题。辣椒与青椒不是别名，也不是上下位，而是“同一家族（辣椒类），具体品种/颜色/状态未知”。如果直接写“辣椒=青椒”会污染词库；如果判 NO 又会误报缺失。通用解法是：**精确匹配依赖标准概念，模糊匹配依赖食材家族和未知属性，替代判断结合菜谱上下文，个人叫法通过用户确认逐渐学习**。同理适用于 蘑菇→香菇、鱼→鲈鱼、青菜→小白菜、奶酪→马苏里拉、肉→猪肉。

### 决策

1. **食材家族（family）**：为常见食材增加粗粒度家族标识（capsicum 辣椒类 / mushroom 菌菇 / fish 鱼 / leafy_vegetable 叶菜 / meat 肉 / cheese 奶酪 等）。家族只表示共同归属，**不代表互为别名**；宽泛概念（辣椒、蘑菇、鱼）与具体概念（青椒、香菇、鲈鱼）可以属于同一家族。
2. **匹配规则升级（通用，非针对单一食材）**：
   - 基础概念相同 → 按 ADR-0022 属性判定（YES/MAYBE/NO）。
   - 基础概念有上下位 → 按方向判定（具体满足宽泛=YES，宽泛面对具体=MAYBE）。
   - 基础概念不同但**家族相同**：菜谱要求属性与库存属性无明确冲突 → MAYBE（“同类食材，具体规格待确认”）；存在明确属性冲突（如 干辣椒=dried 对 青椒=fresh）→ NO。
   - 家族不同 → NO。
3. **菜谱食材要求强度（importance）**：区分 核心（core，菜名中的食材）/ 必需（required，默认）/ 可选（optional，原文含“可选、没有可以不放、按个人口味”）。调味品按常备策略处理。推荐计缺失时：core 与 required 缺失计入“缺 N 样”；optional 不计；未来配菜/偏好（supporting）阶段再引入（由 AI 提取角色，本地规则兜底）。
4. **确认交互延续**：MAYBE 卡片提供“视为可用”（仅本次会话，ADR-0022）；“更新库存身份/记住叫法”作为后续阶段（P1/P2），不写全局词典。
5. **AI 的角色**：本地规则先判 → 语义候选召回 → AI 在固定候选中判断关系（SAME_FAMILY/SUBSTITUTABLE/CONFLICT 等）→ 用户一次性确认形成个人偏好；AI 不得直接写永久全局别名。本轮 AI 联动仍属 SPK-008 范畴，本地先落地家族与模糊匹配。

### 原因

- 家族匹配能把“辣椒→青椒”这类问题通用化，避免为每一种食材单独写别名导致词库污染。
- “宽泛概念与具体概念产生可能匹配”符合用户心智：冰箱有辣椒时菜谱要青椒，应提示“可能可以使用”而不是直接判缺失或误判命中。
- 要求强度避免把配菜/装饰食材误计为“缺 N 样”导致菜谱被过滤，同时保留菜名核心食材的严格性。

### 影响与代价

- `IngredientSpec`/匹配引擎需增加 family 维度；词典新增宽泛概念与家族条目（辣椒/尖椒/彩椒/小米辣/干辣椒、蘑菇/香菇/平菇/金针菇、鱼/鲈鱼、青菜/小白菜/菠菜 等）。
- `Ingredient` 增加 importance 字段；菜谱保存时按本地规则（菜名包含 / 可选关键词）解析，推荐按 importance 计缺失。
- 家族覆盖面有限，未覆盖家族退化为现有规则（家族不同按 NO）；确认与个人学习继续延后。
- 单位换算仍不做（P2）。

### 验证方式

- 新增用例：辣椒→青椒 MAYBE（同家族无冲突）、干辣椒→青椒 NO（加工状态冲突）、小米辣→青椒 MAYBE、蘑菇→香菇 MAYBE、鱼→鲈鱼 MAYBE、肉→猪肉 MAYBE、青菜→小白菜 MAYBE、菜名核心食材缺失计缺失、可选食材不计缺失。
- 真机按 `tests/acceptance/RECO-001-recommendation-2026-08-04.md` 复测：库存“辣椒”+ 菜谱“青椒炒肉”应进入“可能可以做”并提示“冰箱中有辣椒，可能可以使用”。

## ADR-0024 UI 视觉 1:1 复刻：主题级像素基建先行，页面逐层对齐

- 日期：2026-08-04
- 状态：生效（实施中）
- 关联任务：UI-002
- 前置：ADR-0013（HTML 原型为唯一视觉事实源，仅 Flutter 原生实现）。项目负责人反馈当前界面“与原型类似但非 1:1”，要求按 `design/prototypes/index.html`、`prototype.css`、`app.js` 复刻；原型有而实际没有的组件/界面按原型风格补齐。

### 背景

现状与原型（CSS v4.3）的核心差异：按钮/输入/卡片使用 Material 圆角与模糊投影，而原型是**阶梯缺角（pxc-lg/sm/xs）+ inset 墨色描边 + 硬边像素投影（drop-shadow 无模糊）**；页面背景缺少 8px 圆点纹理与米白渐变；底部导航是 Material 指示器而非等分 tab；空状态图标块偏小、缺浮动动画；分隔线为实线而非虚线。

### 决策

1. **主题级基建先行**（本轮）：改造 `PixelCutClipper` 为 CSS 精确阶梯（lg 8px/2px 台阶、sm 4px/2px、xs 3px/3px）；新增 `PixelCutShape`（按钮/输入缺角 ShapeBorder）与 `PixelDashedDivider`、`PixelSectionTitle`、`PixelFloat`、`PixelTabBar` 共享组件；主题按钮/输入框/Chip/FAB 全部像素缺角化；页面背景改为透明 Scaffold + 全局米白渐变圆点纹理（MaterialApp.builder）；底部导航替换为自绘等分 tab（选中 greenSofter 底 + 深绿 inset 描边，顶部虚线）。
2. **页面逐层对齐**（后续轮次）：在基建基础上逐个页面核对间距、字号、卡片结构、状态标签与原型截图，直至 1:1。
3. **原则**：能用主题/共享组件解决的不在页面重复实现；原型有但产品未实现的组件按原型风格实现；不引入 WebView。
4. **验收**：构建 Android 后按原型逐页截图对比；差异逐条记录并修正（UI-002）。

### 原因

- 像素风的关键在“形状与阴影”，必须从主题层统一，否则逐页修永远不齐。
- 透明 Scaffold + builder 纹理与 CSS body 背景等效，一处生效全应用共享。

### 影响与代价

- 主题按钮/输入/Chip 形状变化会影响所有页面视觉（预期内）；个别页面若有自定义 shape 会覆盖主题，需逐页核对。
- `PixelCutClipper` 阶梯算法变化可能影响既有截图断言，无自动化视觉测试，以真机截图验收。
- 动效（浮动静止）尊重系统“减少动态”偏好：本版未接入 MediaQuery.disableAnimations 开关，后续补充。

### 验证方式

- 全项目 IDE 诊断无错误；`flutter run` 后按 `tests/acceptance/UI-002-visual-1v1-2026-08-04.md` 逐页截图对比原型。

## ADR-0025 冰箱拖拽以最终提交为动效边界，冷冻采用二维离散逐格动画

- 日期：2026-08-04
- 状态：生效（待实施）
- 关联任务：UI-002、FRIDGE-002
- 关联设计：`design/flows/FRIDGE_DRAG_AND_FROST_ANIMATION_HANDOFF.md`

### 背景

现有冷冻动效虽然把水平进度量化，但仍绘制不断增长的整高矩形，视觉上仍是横向扫过；同时跨区移动以食材名称和短时间窗口标记待播动画，分区级与 chip 级嵌套 `DragTarget` 可能重复接收，正常组件、拖拽 feedback 与占位组件又共享带动画控制器的实现，导致长按、拖动经过区域、重建或同名批次操作时可能提前、错播或重复播放。

### 决策

1. 拖拽生命周期统一为 `idle → pressing → dragging → accepted → committing → mountedAtTarget → arrivalAnimation → idle`。手势开始、候选区进入/离开、`onMove`、`onWillAccept`、无效释放、同区排序和 Widget 重建均不是冷冻/解冻触发点。
2. 唯一触发边界为：最终目标区域正式接收、库存移动保存成功、目标 chip 已挂载，并成功消费该次移动的唯一到达事件；四项缺一不可。
3. 冷冻视觉使用二维独立网格，每格约 12–14dp、至少两行；从图标侧中部冰核按曼哈顿距离向外排序，每个 tick 只切换一个完整格子，约 450–650ms 完成。解冻按相反顺序逐格消失。
4. 禁止使用增长矩形、整列/整行批量填充、透明度扫过、连续 `Color.lerp` 或延长时长来伪装逐格动画；描边、投影和图标只在明确离散节点切换，避免另一层平滑扫过。
5. 正式目标 chip、拖拽 feedback 和原位占位拆分职责；feedback 与占位必须是无 `AnimationController`、无 mount 动画、无 `didUpdateWidget` 动画副作用的静态组件。
6. 动画事件至少包含 `dragSessionId`、`moveEventId`、`stableItemId`、`sourceZone`、`targetZone` 和 `animationKind`，并只能消费一次。同名食材名称不能作为事件身份。
7. 优先让每个分区只有一个最终 `DragTarget`，chip 只提供落点索引；若短期保留嵌套目标，则使用 `dragSessionId + handled` 一次性消费，删除“名称 + 250ms”时间窗口去重。
8. 保存失败时恢复原位置且不播放成功动画；系统启用减少动态时直接显示最终状态，不创建逐格过程动画。

### 原因

- 动画表达的是“数据迁移成功后的到达结果”，不应表达“用户正在按住或经过某区域”。
- 二维离散格和单格推进才能在视觉上明确区别于横向填充或渐变扫过。
- 稳定实体 ID 与移动事件 ID 能隔离同名多批次、快速连续拖动和页面重建，避免依赖时间竞态。
- 单一落点所有者和静态拖拽反馈可显著缩小 Widget 生命周期触发副作用的范围。

### 影响与代价

- 需要重构 `fridge_page.dart` 中 `_pendingFrostAnim`、嵌套 `DragTarget`、`_FoodChip` 与 `_FrostFillPainter` 的职责，不能只调动画时长或格子尺寸。
- 工程师需要在保存成功与目标组件挂载之间传递一次性到达事件，并覆盖失败回滚、同名批次、连续拖动和重建场景。
- 本决策不改变库存数据字段、推荐算法和其他分区的静态颜色规则。

### 验证方式

- 工程师实施后，由项目负责人按 `tests/acceptance/UI-002-fridge-drag-frost-animation-2026-08-04.md` 录屏验证触发时点、逐格顺序、失败恢复、同名批次、快速连续操作、重建和减少动态。
- Codex 本轮只完成方案与验收定义，未修改应用代码，未执行 Flutter/Dart 测试、静态分析、构建、模拟器或真机验证。

## ADR-0026 本地 OCR 模型下载源采用 RapidAI/RapidOCR 官方 ModelScope 仓库（真实清单）

- 日期：2026-08-04
- 状态：生效
- 关联任务：OCR-003、OCR-001、OCR-002、SPK-002
- 前置：ADR-0009（本地 OCR 首选 PaddleOCR PP-OCRv5 mobile + ONNX Runtime Mobile）

### 背景

OCR 设置页此前 `installManifest` 恒为空，页面显示"正式模型包尚未发布"，本地 OCR 模型无法下载安装，用户无法用"测试 OCR"验证识别效果。项目负责人要求附带真实安装地址。

### 候选方案

1. 继续不配置 Manifest，等待自建服务器托管模型。
2. 使用 PaddleOCR 官方 Paddle 推理包（.tar，含 .pdmodel/.pdiparams）——与项目 ONNX Runtime 运行时不匹配，且 Manifest 强制要求 `.onnx`。
3. 使用 RapidAI/RapidOCR 官方在 ModelScope 上发布的已转换 ONNX 模型（`PP-OCRv5 mobile` 检测/识别 + `ppocrv5_dict.txt` 字典），把真实下载地址、SHA-256 与字节大小写入 Manifest。

### 决策

采用方案 3：

- 新建 `lib/app/ocr_model_catalog.dart`，定义 `ocrPpocrV5MobileZhManifest`（schemaVersion 2、engine `onnxruntime`、platforms `[android]`、languages `[zh]`、version 1.0.0、license Apache-2.0）与 `ocrTrustedModelHosts`（`www.modelscope.cn`）。
- 三个文件的下载地址、SHA-256 与字节大小均来自 2026-08-04 对 ModelScope 直链的真实下载与实测：`ch_PP-OCRv5_det_mobile.onnx`（4,819,576 B）、`ch_PP-OCRv5_rec_mobile.onnx`（16,631,306 B）、`ppocrv5_dict.txt`（74,012 B，18383 行，首行全角空格为 blank）。
- 运行时参数与 RapidOCR PP-OCRv5 官方默认一致：检测端 `limit_side_len=960`、normalize bgr `[0.485,0.456,0.406]/[0.229,0.224,0.225]`；识别端输入 `[3,48,320]`、normalize bgr `[0.5,0.5,0.5]`、blank 索引 0。
- `app.dart` 在组合根传入 `trustedOcrModelHosts`；`profile_page.dart` 把 Manifest 传入 OCR 设置页，使"下载本地模型"按钮真正可点。
- 安装仍按字节数与 SHA-256 双重校验（`DeviceOcrModelPackageService`），不允许伪造或占位。

### 原因

- 官方 .tar 推理包与 ONNX Runtime 运行时不匹配；自建托管当前不现实。
- RapidOCR 是 PP-OCRv5 社区官方维护的 ONNX 转换来源（Apache-2.0），ModelScope 直链稳定、国内可访问，且 ONNX 文件与项目运行时契约（OCR_PLUGIN.md）一致。
- 真实哈希与大小保证安装校验可信，不破坏"不伪造下载地址/校验值"的安全边界。

### 影响与代价

- 模型来源是第三方仓库镜像，属于**开发期可用依赖**；正式发布时如自建托管，仅需替换 URL/哈希并保留相同契约。
- 模型文件（约 21.5 MB）由设备首次下载；真机网络可达性与识别质量仍需 `SPK-002` 验证。
- Android 原生运行时桥若未完全实现，模型可安装但识别可能报"运行时不可用"，属既有 `SPK-002` 范围，不因本 ADR 改变。
- 字典/模型由 RapidOCR 打包，其推理配置已按官方默认对齐；如模型更新版本需重新实测哈希并升级 Manifest。

### 验证方式

- 项目负责人按 `tests/acceptance/OCR-003-ocr-settings-test-2026-08-04.md` 复测：下载安装、状态推进、测试 OCR 选图识别输出文本与耗时。
- 哈希与大小已在本机实测并与下载文件一致；真机下载时安装器再次校验。

## ADR-0028：多模态连接诊断分层，OCR 与视觉理解独立结算并融合证据

- 日期：2026-08-05
- 状态：生效（2026-08-05 已由低级工程师实施 P0-1/P0-2，代码进入 VERIFY）
- 关联任务：BUG-006、IMAGE-001、OCR-003、IMPORT-007
- 详细方案：`docs/architecture/VISION_RECOGNITION_STRATEGY.md`

### 背景

多模态“测试连接”当前等待一次图片请求的完整响应，并把地址、鉴权、模型、图片协议、首字节、正文结束和解析失败统一包装为“链接超时”。项目负责人确认实际故障并非普通网络超时。此前“使用表单当前配置”和“发送 1×1 PNG”只排除了旧配置复用与纯文本探测两个因素，不能证明最终根因，也无法提供可操作诊断。

同时，现有自动识图采用“多模态优先，失败后 OCR”的串行二选一语义，会在其中一路失败时放弃另一类可能有价值的证据，并混淆 OCR 原文和视觉观察的职责。

### 决策

1. 多模态配置测试拆成“检查基础连接”“检查图片能力”“用我的图片测试”三类。
2. 图片能力探针使用固定 256×256 标准图，要求同时识别文字“AI RECIPE 314”和红色方块；1×1 无语义图片不再作为视觉能力证明。
3. 诊断按配置、地址解析、连接、鉴权、模型、请求接收、首字节、正文完成、响应解析和图片断言分阶段记录；至少区分连接失败、无首字节、正文卡住、HTTP 408/504、SSE 未终止、客户端取消和 Schema 错误。
4. OCR 只负责忠实文字提取；多模态 LLM 只负责菜品、食材外观、动作、器具、步骤场景和图文关系观察；结构化菜谱 LLM 负责带来源合并。
5. 自动模式改为 OCR 与多模态独立执行、分别结算和部分成功：任一路成功均保留；两路成功时按证据优先级合并并显式标记冲突。
6. 两路失败但有正文、字幕或 ASR 时继续生成；两路失败且无其他证据时不生成空草稿，提供重选图片、粘贴正文和手动创建。
7. 用户禁止上传图片时不得发送云 OCR 或多模态请求；诊断和质量日志必须脱敏，并设置图片数量、大小、并发、耗时和费用上限。

### 与既有决策的关系

- ADR-0027 的页面命名、三种识图模式入口和多模态独立配置继续生效。
- 本 ADR 替代 ADR-0027 / IMAGE-001 中“自动：多模态优先，失败后 OCR”的串行语义，改为“独立执行 + 部分成功 + 证据融合”。
- 本 ADR 不改变菜谱生成 LLM 的独立配置，也不把多模态视觉 Provider 合并进 OCR Provider。

### 原因

- “超时”是结果而非根因；只有分阶段观测才能让用户和工程师判断配置、网络、协议、Provider、流式传输或解析问题。
- OCR 与视觉理解擅长的信息不同，互相替代会丢失文字坐标、视觉动作或场景证据。
- 部分成功能避免一次辅助调用失败导致整个导入失败，并为确认页提供可审计来源。

### 影响与代价

- Transport 需要支持响应头、首字节、正文空闲和总时限的分层观测，现有 `client.post(...).timeout(...)` 黑盒路径需重构。
- 导入内容、执行计划、Prompt/Schema 和确认页需要统一证据模型与冲突展示。
- 自动模式可能增加调用次数和费用，必须受用户许可、网络策略和预算限制。
- OpenAI-compatible 服务的图片字段、MIME、data URL 和 SSE 行为并不完全兼容；不兼容必须归类为协议问题，不能继续显示网络超时。

### 验证方式

- 低级工程师按方案先实施 P0-1 诊断修复，再实施 P0-2 证据融合，最后处理 P1 兼容性增强。
- 项目负责人按 `tests/acceptance/BUG-006-multimodal-diagnostics-and-vision-fusion-2026-08-05.md` 分别在 Android 与 iOS 回传结果和证据。
- 真实样本的 OCR/视觉/结构化质量写入 `tests/ai-quality/AI_QUALITY_LOG.md`。
- Codex 本轮未修改应用代码，未执行 Flutter/Dart 测试、静态分析、构建、模拟器、真机或真实 Provider 测试。

## ADR-0029：多图多模态识别，多模态只做文字转录，纯 LLM 分组判断并生成多草稿

- 日期：2026-08-05
- 状态：生效（IMAGE-002 实施中）
- 关联任务：IMAGE-002、IMAGE-001、IMPORT-007、OCR-003
- 详细方案：`docs/architecture/VISION_RECOGNITION_STRATEGY.md` 第 15 章

### 背景

项目负责人确认多图链接内容存在两种真实形态：①一张图片即一份完整步骤（多张图片
＝多份独立菜谱）；②每张图片是一个步骤（所有图片整合才是一份完整菜谱）。同时决定
放弃把本地 OCR 作为链接图片识别的自动路径，图片识别统一使用多模态 LLM。

### 决策

1. 多模态 LLM 的识别提示词改为“忠实转录图片中所有文字”，不再做视觉观察描述；
   转录文本与 OCR 原文同属文字证据（`sourceType=ocr`），保留 `sourceMediaOrder`
   用于按图分组。
2. 是否“每张图独立成谱”由纯文本 LLM 先做一次轻量分组判断（`independent` /
   `combined`），再按分组拆分证据、逐组执行既有结构化生成。
3. `independent` 时一次导入产出多个独立菜谱草稿；`combined` 时合并为一个草稿。
4. `ImportRecipeDraftResult` 与 `ImportTask` 支持多草稿（任务关联 1..N 个草稿），
   确认页逐个确认与保存。
5. 链接导入的图片一律走多模态转录；手动选图/拍照导入同样**默认多模态转录优先**
   （视觉理解 + 文字转录，直接识别图片内容），多模态未配置或不可用时回退本地 OCR
   （2026-08-07 修订，原为“本地 OCR 优先、未安装或失败时回退多模态”）。
   用户显式选择「仅 OCR」时尊重该选择。

### 2026-08-07 修订说明

- 项目负责人反馈：拍照选图导入被展示为“网页链接”且给了本地占位链接，期望直接交给
  多模态 AI 识别图片内容，而不是复用旧链接导入操作。
- 修订内容：`_resolveLocalImagePlan` 自动（auto）模式改为与链接导入一致——多模态
  优先，多模态未配置/不可用时回退本地 OCR；用户显式选择某一路时尊重选择。
- 同步修复：排队（queued）占位任务允许以本地图片/文本内容直接运行（跳过网页抓取）；
  导入进度页对占位任务展示真实来源语义（“本地图片导入/文本整理导入”），不再暴露
  内部占位链接。

### 与既有决策的关系

- 修订 ADR-0028 第 4/5/6 条：识图不再默认“OCR+多模态融合”；自动路径按来源区分
  （链接→多模态，手动图→OCR 优先回退多模态，2026-08-07 改为手动图同样多模态优先）。
- ADR-0027 的识图引擎设置页与多模态独立配置继续生效；`ImportImageRecognitionRoute`
  中 `ocrAndMultimodal` 融合语义让位于 ADR-0029 的多图转录与分组。
- OCR-003 的“测试 OCR”与本地模型管理保留，服务对象是手动选图/拍照导入。

### 原因

- 链接多图内容的“独立 vs 合成”无法用规则可靠区分，交给语义 LLM 判断最直接。
- 多模态转录保证文字不被丢弃，纯 LLM 只做合并/结构化，避免多模态“视觉观察”编造
  作者未给出的用量与时间。
- 多草稿让“一份链接＝多个菜谱”以用户可逐个确认的形态落地。

### 影响与代价

- 多图独立时多次结构化生成会消耗多次 LLM 调用，必须受图片数量上限（默认 9）与
  总成本预算约束；取消语义沿用导入链路。
- `ImportTask` 增加多草稿持久化（SQLite 新列），草稿确认页需支持多草稿切换。
- 本地 OCR 仍保留但不再是链接导入的自动路径，避免一次导入触发两路云端识别。

### 验证方式

- 项目负责人按 `tests/acceptance/IMAGE-002-multimodal-multi-image-2026-08-05.md`
  在 Android/iOS 复测：每图独立链接产出多个草稿、多图合成链接产出单草稿、手动
  选图在未配置多模态时回退本地 OCR、成本上限与取消。
- 2026-08-07 修订后：手动选图/拍照导入默认直接多模态识别；复测见
  `tests/acceptance/BUG-007-local-image-import-task-save-2026-08-07.md`（拍照选图
  不再显示为网页链接、直接多模态识别）。
- 真实样本质量（转录准确率、分组判断正确率、多草稿人工修改数）写入
  `tests/ai-quality/AI_QUALITY_LOG.md`。

## ADR-0030：菜谱列表与推荐性能优化（PERF-001）

- 日期：2026-08-06
- 状态：生效（代码已实施，等待项目负责人真机验收）
- 关联任务：PERF-001
- 依据：《解决方案.md》（列表摘要查询 / 消除 N+1 / 分页 / 虚拟化 /
  推荐轻量数据 / Isolate / 限量展示 / 防抖与最新请求优先）

### 背景

项目负责人反馈“菜谱库加载几分钟、推荐时死机”。静态分析确认根因：
①`listRecipes` 逐条调用 `_loadRecipe`，1000 条菜谱约 5001 次串行 SQL；
②列表页读取完整聚合（步骤/全部食材/图片/分类）但卡片只用十几个字段；
③`Wrap + map().toList()` 一次性构建 1000 张卡片；
④推荐前再次全量读取完整聚合，且三值匹配在 UI 主线程同步执行；
⑤候选批次查找逐键扫描全部库存。

### 决策

1. **列表摘要模型**：新增 `RecipeSummary`（id/标题/封面/收藏/时间/难度/
   食材数/更新时间/标签）与 `RecipeSummaryPage`；列表页只读摘要，
   详情页打开时再按 id 加载完整聚合。
2. **消除 N+1**：`listRecipeSummaries` 单条 SQL（LEFT JOIN ingredients +
   GROUP BY 聚合食材数），从约 5001 次降为 1 次；首页分类计数改用
   `countRecipesByCategory` 一条 SQL；`getRecipeSummariesByIds` 按 id 批量取摘要。
3. **keyset pagination**：支持 updated/created/title 三种排序，
   `RecipeCursor(timestamp|title, id)` 续读，不用 OFFSET；`countRecipes` 供页头总数。
4. **虚拟化渲染**：菜谱库页改为 `SliverGrid` + 滚动到底自动加载下一页（40 条/页），
   只构建屏幕附近卡片；加载期间保留旧列表顶替，不闪整页动画。
5. **推荐专用轻量数据**：`listRecipesForRecommendation` 只加载主记录 + 全部食材
   （2 次 SQL），不含步骤/图片/分类。
6. **匹配移入后台 Isolate**：新增 `RecommendationExecutor`
   （生产 `IsolateRecommendationExecutor` 用 `Isolate.run`，Web 回退直算；
   测试注入 `DirectRecommendationExecutor`，避免 FakeAsync 下 Isolate 挂起）。
7. **推荐结果限量展示**：每组首批 Top 10，剩余通过“查看更多”增量展示。
8. **防抖 + 最新请求优先**：选择变化 250ms 防抖；每次计算递增 requestId，
   旧请求迟到结果直接丢弃。
9. **算法优化**：`IngredientCanonicalizer` 增加有界结果缓存；
   别名/规格词典改 Map 查找；库存候选查找改家族/上下位哈希索引（O(1) 直取）。
10. **数据库索引**：schema v10 迁移新增复合索引
    （status/favorite+updated_at+id、ingredients(base_concept_id, recipe_id)、
     recipe_category_relations(category_id, recipe_id)），幂等。

### 与既有决策的关系

- 不改变 ADR-0021/0022/0023 的食材匹配语义，只让同样的判断更快。
- 页面仍只通过 `AiRecipeBackendFacade` 访问业务能力（ADR-0012/0013 边界不变）。
- 数据库 schema v9 → v10，仅新增索引，无数据/列结构变化。

### 影响与代价

- 菜谱库页从“一次全量加载”改为“分页加载”：排序/筛选由 SQL 承担，
  前端不再全量排序；同 `updated_at` 的菜谱排序从 id ASC 变为 id DESC（文档化）。
- 首页 `HomeSnapshot` 类型从 `List<Recipe>` 改为 `List<RecipeSummary>`，
  首页卡片与打开详情均按 id 传递。
- `IngredientCanonicalizer`/词典类不再是 const 构造（需要实例缓存/索引 Map），
  相关默认值与测试构造同步调整。
- 每次推荐会新建一次 Isolate（约几十 ms 开销）；长期 Worker Isolate 与
  食材倒排索引、两阶段匹配留待后续（见解决方案.md 第二/三批）。

### 验证方式

- 项目负责人按 `tests/acceptance/PERF-001-recipe-list-recommendation-performance-2026-08-06.md`
  Android 复测：首屏速度、滚动加载、搜索/排序/筛选、首页、推荐计算期间可操作、
  连续勾选、Top 10 与查看更多、收藏乐观更新；并回传两个性能测试的
  `[Perf][RecipeLibrary]` / `[Perf][Recommendation]` 输出。
- 性能测试：`flutter test --no-pub test/performance/recipe_library_perf_test.dart`
  与 `test/performance/recommendation_perf_test.dart`。

## ADR-0031：图片导入链路性能优化（PERF-002）

- 日期：2026-08-06
- 状态：生效（代码已实施，等待项目负责人真机验收）
- 关联任务：PERF-002
- 依据：《解决方案.md》（消除重复下载 / 有限并发流水线 / 识别前压缩 /
  深度思考开关）

### 背景

图片导入链路存在三处结构性瓶颈：①识别阶段下载远程图片后删除临时文件，
封面保存阶段对同一 URL 再次下载（重复下载）；②图片逐张串行“下载 → 识别”，
下一张要等上一张完全结束；③原图未经压缩直接 base64 上传给多模态识别，
大图导致上传慢、Provider 解码开销大。此外，所有 LLM 调用统一跟随用户对
最终结构化生成的推理深度预设，无法让“忠实转录/轻量分组”这类任务保持快速。

### 决策

1. **任务级图片缓存（消除重复下载）**：新增 `TaskScopedImageCache`（实现
   `OcrRemoteImageStager`），按“升级后的 https URL”缓存下载结果；一次导入内
   同一远程图片只下载一次，识别与封面保存共用同一份临时文件。缓存由
   `DeviceImportTaskRunnerFactory.create()` 创建并同时注入多模态处理器 stager
   与 `LlmRecipeGenerationProcessor` 的 `remoteCoverImageStager`，处理器链
   执行结束（成功或失败）后统一 `disposeAll()` 释放。缓存返回的
   `StagedOcrImage` 的 dispose 为 no-op，避免消费方提前删除共享文件。
2. **有限并发流水线（P0-2）**：多模态识别从串行 `for` 改为并发 2 的
   `_runConcurrent` 工作池（图片 1 下载完立即识别、图片 2 同时下载形成流水线），
   结果按下标顺序返回；单张识别失败（非取消）折叠为 null 不拖垮整批，仅标记
   “部分内容”；取消错误原样上抛立即终止整批。全部失败时给出可重试提示。
3. **识别前压缩重编码（P0-3）**：新增 `ImageRequestCompressor`（基于 `image`
   包）：`decodeImage` → `bakeOrientation`（EXIF 修正）→ 超过长边上限按需等比
   缩放 → `encodeJpg`（质量 85）。普通照片长边上限 2048px；长宽比 ≥2.5 的文字
   密集截图保留更高分辨率（长边上限 4096px）。压缩失败或体积无收益时保留原图，
   只影响上传给识别的字节，不改动磁盘原图（原图仍用于封面）。
4. **深度思考开关（ReasoningMode）**：领域新增 `LlmReasoningMode {fast, deep}`
   与 `LlmReasoningCapability`；`LlmConnectionConfig` 增加 `reasoningMode`
   （默认 fast，`toJson/fromJson` 兼容旧配置）；`LlmProvider` 增加
   `reasoningCapability` 能力。OpenAI-compatible 用 `reasoning_effort`
   （deep → `high`），Gemini 用 `thinkingConfig {includeThoughts: true}`。
   图片转录（多模态）始终快速；多图分组判断显式 `fast`；最终结构化生成跟随
   用户开关（`RecipeGenerationPromptBuilder.build` 接收 `reasoningMode`，
   `LlmRecipeGenerationProcessor` 传入 `config.reasoningMode`）。

### 与既有决策的关系

- 不改变 ADR-0027/0028/0029 的识图路由与证据类型语义，只让同一链路更快。
- 复用 OCR-002 安全暂存层做底层下载与校验，缓存只做“去重”，不弱化安全边界。
- 页面仍只通过 Import 流水线访问能力，不新增 UI 侧直连。

### 影响与代价

- 多图识别从“单张失败整批失败”改为“部分失败继续”，多草稿/分组语义不变，
  但失败图片会以 `partialContent` 标记，需项目负责人确认 UI 提示可接受。
- 压缩引入 `image` 纯 Dart 依赖（含传递依赖 archive/xml/petitparser/posix），
  增加少量包体积；编解码在 Dart 侧进行，大图可能短暂占用内存。
- 深度思考开关当前由 `LlmConnectionConfig` 持久化，尚未在设置页露出 UI 开关
  （图片转录/分组已固定 fast，最终结构化用配置默认 fast）；后续如需用户可配置
  需扩展 `LlmSettingsInput` 与设置页。

### 验证方式

- 项目负责人按 `tests/acceptance/PERF-002-import-pipeline-performance-2026-08-06.md`
  Android 复测：多图导入网络请求去重、识别并发与进度、部分失败、压缩后上传
  体积、深度思考开关对最终生成的影响。
- 未运行测试/构建/真机（ADR-0015）；返回结果后归档并决定进入 `DONE` 或
  返回 `DOING`。iOS 未验证。

## ADR-0032：WebView 抓取生命周期与竞态加固（并入 IMPORT-008）

- 日期：2026-08-06
- 状态：生效（代码已实施，等待项目负责人 Android 真机验收）
- 关联任务：IMPORT-008（并入）
- 依据：《解决方案.md》（针对 WebView 抓取不稳定，第一阶段：生命周期与竞态）

### 背景

"网页加载失败"实际混合多类故障：前一个请求的迟到回调污染后一个请求；新请求
启动时旧请求未真正终止（仍 stopLoading 前残留回调）；Dart 传入的总超时未成为
真实上限（各阶段固定常量可累计超过）；图片阶段总/单图超时共用同一 timer 互相
覆盖；renderer 崩溃后继续复用已失效 WebView；图片目录全局共享导致任务间互相
污染。

### 决策

1. **RequestContext 请求隔离**：新增 `RequestContext` 承载每次抓取独立状态
   （requestId/platform/originalUrl/result/deadline/navigationGeneration/
   imageGeneration/cancelled/payload/resolvedUrl/图片队列与计数/图片目录）。
   所有异步入口（WebView 回调、evaluateJavascript 回调、Handler 延迟任务、
   图片写盘 worker）在回调开始处统一校验 `ctx === activeRequest && !ctx.cancelled`，
   以身份比较实现隔离；`navigationGeneration` 每次主框架导航递增、`imageGeneration`
   每张图片递增，DOM 探测与图片回调只接受创建时代次，旧导航/旧图片迟到回调一律丢弃。
2. **新请求正确终止旧请求（superseded）**：`handleFetchPage` 启动新请求前对旧请求
   执行 `terminate(old, "superseded")`——标记取消、取消计时器、stopLoading、清理
   专属目录、完成旧 result（不显示"网页超时"）。区分 cancelled/superseded/timeout。
3. **原生取消 API**：通道新增 `cancelFetch`；Dart `WebViewContentFetcher` 增加
   `cancel()`，Adapter 在导入取消令牌触发时调用，原生立即停止导航/JS/图片下载写盘。
4. **真实总超时（P0-4/P0-5）**：以 Dart 传入 timeoutMs 建立请求级绝对截止
   `requestDeadlineMs`；`armDeadline` 每次取 `min(请求剩余, 阶段剩余, 单图剩余)`
   调度单一 timeouter，阶段/单图不再能累计超过总预算。
5. **renderer gone 重建（P0-7）**：`onRenderProcessGone` 后 `destroyWebView()`
   （移除父容器、stopLoading、destroy、置空），下一次请求重建；错误分类
   `rendererGone`，不归入普通网络不可用。
6. **请求专属图片目录**：图片写入 `filesDir/webview-imports/<requestId>/images/`，
   迟到 worker 只写回旧请求自己的目录，不污染新请求；失败/取消/superseded 删除
   该请求目录，成功保留供 Dart 读取，App 退出（dispose）清理全部。

### 影响与代价

- 显著降低"A 回调写进 B"类竞态与"超时掩盖真实故障"；renderer 崩溃后重试可恢复。
- 行为变化：用户取消现在记为 `cancelled`（不再被误记为超时）；错误分类新增
  `cancelled/superseded/rendererGone`，Dart 侧映射到对应的 ImportContentAdapterErrorKind。
- 代价：单个 WebView 实例仍串行（符合既有调度）；成功请求的图片目录保留到
  dispose，会话内可能累积少量目录。

### 未做（后续阶段）

- 第二/第三阶段（readiness 重构、小红书/抖音特化 readiness 与指纹、JSON-LD、
  登录墙增强识别、可观测性上报）按《解决方案.md》暂缓，另行排期。

### 验证方式

- 项目负责人按 `tests/acceptance/IMPORT-008-webview-lifecycle-race-2026-08-06.md`
  Android 复测：旧请求回调不污染新请求、取消不被记为超时、总超时确为请求上限、
  renderer gone 后重试可恢复、正文成功后图片失败不整单失败、请求专属目录隔离。
- 未运行测试/构建/真机（ADR-0015）；返回结果后归档并决定进入 `DONE` 或返回
  `DOING`。iOS（WKWebView）未验证。

## ADR-0033：WebView 内容就绪与平台提取 + 可观测性（并入 IMPORT-008）

- 日期：2026-08-06
- 状态：生效（代码已实施，等待项目负责人 Android 真机验收）
- 关联任务：IMPORT-008（并入）
- 依据：《解决方案.md》第二、第三阶段

### 背景

在 ADR-0032（请求隔离/竞态）之上，仍需解决"网页存在文字 ≠ 目标内容就绪"的
误判（壳页/登录/验证/删除/App 拉起页可能被当正文），并让"网页加载失败"具备
可解释性（需要记录每次导入的故障分类与阶段数据）。

### 决策

1. **平台 readiness 分流（第二阶段的 ReadinessDetector）**：`probeContent` 改用
   `probeScript(platform, targetId)`，按平台加载探测脚本，返回
   `ready`/`readyReason`/`fingerprint`/`risk`/`login`/`gone`/`targetIdMatch`：
   - 小红书：命中 `__INITIAL_STATE__` 或有效正文 DOM，且非登录/验证/删除/受限；
     提取目标笔记 ID 做 URL 一致性校验（记录 `targetIdMatch`，不硬性阻断，
     避免重定向 ID 格式差异误伤）。
   - 抖音：命中 `__RENDER_DATA__`/`RENDER_DATA` 或有效正文 DOM，识别视频 ID。
   - 通用：优先主正文候选（`article/main/[role=main]` 长度≥200），其次 JSON-LD，
     再正文达标；区分登录/验证/错误提示与导航/页脚。
2. **平台特化提取（ContentExtractor）+ 校验（ResultValidator）**：
   - 抖音：优先解析 `__RENDER_DATA__` 中 `videoInfoRes.item_list[0]` /

     回退页面 DOM 与 meta。
   - 通用：优先 JSON-LD Recipe/Article（`headline/name`、`description`、
     `recipeIngredient`、`recipeInstructions`、`articleBody`），回退主正文候选，
     再整页文本。
   - 小红书：保留既有 note 数据/选择器提取，补输出 `fingerprint`。
   - `validateResult`：无有效文本且命中登录/验证/删除标记 → 归为
     `loginWall/verification/gone`；回填 `bodyLength`/`bodyFingerprint`。
3. **正文与图片彻底解耦（P0-8 收尾）**：图片阶段（FETCHING_IMAGES）的

   `httpStatusCode`。
4. **可观测性（第三阶段）**：`RequestContext` 增加 `redirectCount`/`finalHostPathHash`/
   `httpStatusCode`/`readinessReason`/`bodyFingerprint`/`bodyLength`/`imageAttempted`/

   `finalErrorClassification`/`stageStartedAt`；请求结束（terminate/completeSuccess）
   输出 `OBS req=... platform=... stage=X=..ms redirect=.. http=.. readiness=.. fp=..
   bodyLen=.. imgAttempt=.. imgOk=.. imgFail=.. imgFailReasons=.. rendererGone=..
   final=.. totalMs=..` 汇总日志。

### 影响与代价

- WAITING_CONTENT 由"有文字即稳定"改为平台 readiness 决策，减少壳页误判导致的
  脏正文进入 LLM。

  未做预算上限）。

## ADR-0034：全量菜谱备份采用版本化可迁移归档包

- 日期：2026-08-06
- 状态：生效（方案待项目负责人验收，尚未实施）
- 关联任务：BACKUP-001
- 关联故事：US-014
- 关联风险：R-006、R-016、R-020

### 背景

项目采用 Flutter + SQLite 的 Local-first 架构。菜谱结构和数据库迁移会持续变化，图片当前又以设备文件路径保存。如果直接把 SQLite 数据库文件交付给用户，恢复会绑定数据库引擎、schemaVersion、平台文件路径和运行中的写入状态；如果把所有数据和图片塞进一个 JSON/Base64 文件，则内存占用、流式处理、媒体去重、哈希验证和后续增加新数据集都会变得困难。

用户要求每次备份全量导出所有菜谱，并能安全导入，同时希望未来可以任意扩展库存、购物清单、制作记录和新格式。

### 候选方案

1. **直接复制 SQLite + 图片目录**：实现最短，但强绑定内部表、迁移和设备路径，难以安全跨版本/跨平台恢复，也无法把数据库与媒体放进同一事务。
2. **单个 JSON + Base64 图片**：对外结构可控，但超大文件需高内存，图片膨胀且难以去重或增量校验，新增数据集会让一个 Schema 持续膨胀。
3. **版本化 ZIP 容器 + Manifest + NDJSON Dataset + 内容寻址媒体**：结构可流式、可校验、可分数据集迁移，媒体与业务记录解耦，便于以后增加可选模块。

### 决策

采用候选方案 3：

1. 用户文件扩展名为 `.airecipe-backup`，内部使用标准 ZIP；首版包含：
   - `manifest.json`
   - `data/recipes.v1.ndjson`
   - `data/categories.v1.ndjson`
   - `media/index.v1.ndjson`
   - `media/sha256/<prefix>/<sha256>.<ext>`
2. 归档格式版本、每个 Dataset 的 Schema 版本和 SQLite `schemaVersion` 分离。应用通过 Dataset Adapter、Migration Registry 和逐版本 Migrator 链读取旧包；领域模型/导出 DTO 不直接序列化数据库行。
3. 每次用户创建的备份都是全量菜谱库：正式、草稿、归档、回收站、分类和关系、食材、步骤、标签、收藏、时间/版本/软删除字段，以及全部菜谱封面和配图。首版排除库存、购物清单、制作记录、最近浏览、运行中会话/任务、设置、密钥、模型、缓存和临时文件。
4. 必需媒体缺失或不可读时，导出失败，不交付不完整包。Manifest 记录 Dataset/媒体数量、字节数、SHA-256、requiredFeatures 和 optionalFeatures。
5. 导入默认“合并”。同 UUID 且内容一致可跳过；同 UUID 内容不同必须进入冲突处理，禁止静默覆盖。仅标题或名称相似不能自动覆盖。
6. “替换当前库”属于高级恢复，执行前必须创建并验证当前库回滚备份；无法创建回滚备份时不得开始。
7. 导入先在 staging 中完成路径、数量、大小、压缩比、版本、哈希、媒体引用和空间预检，再生成 ImportPlan；数据库和媒体采用带清理账本的两阶段提交，失败后保证当前库未改变或已回滚。
8. 未知 required feature 阻止导入；未知 optional feature 只有在展示跳过内容和影响并获得确认后才能继续。
9. API Key、Token、Cookie、secure storage 引用和设备绝对路径不得进入备份。归档加密只预留能力，首版不作为已承诺功能。

### 影响与代价

- 后续新增库存、购物清单、制作记录时，可以添加独立 Dataset 和 Adapter，而不修改既有菜谱 Dataset 的语义。
- 需要新增稳定媒体资产契约（`mediaAssetId`、SHA-256、MIME、大小、稳定相对存储键、引用关系、导入会话清理账本），不能继续把设备路径当成跨设备引用。
- 需要维护版本兼容矩阵、迁移器、恶意归档限制、空间估算和失败恢复流程；实现成本高于直接复制数据库，但长期可维护性和数据安全更好。
- 本地备份、云同步和 Markdown/PDF/图片内容导出必须保持为独立产品能力。

### 验证方式

- 项目负责人按 `tests/acceptance/BACKUP-001-recipe-backup-restore-plan-2026-08-06.md` 走查全量边界、格式扩展性、导出/导入流水线、冲突、替换/回滚、安全和 UI 状态。
- 本轮未编写代码，未执行测试、静态分析、构建、模拟器或真机验证。方案通过后再建立实施任务；在项目负责人反馈前 `BACKUP-001` 保持 `VERIFY`。

- 项目负责人已完成方案走查，7 项维度全部通过，附 3 项实施前细化建议：①统一媒体失败语义（必需媒体缺失/不可读/哈希不一致时备份失败并清理半成品）；②回滚备份保留期限定值（登记到 BACKUP-006 验收）；③阐明 minimumReaderVersion 与 formatVersion 关系（已写入 `backup_archive_constants.dart` 注释）。BACKUP-001 进入 `DONE`。

## ADR-0035：备份导出首版实现的技术边界（BACKUP-002/003）

- 日期：2026-08-06
- 状态：生效（导出半边已实施，等待项目负责人验收）
- 关联任务：BACKUP-002、BACKUP-003
- 关联决策：ADR-0034

### 背景

ADR-0034 确定归档格式与导出/导入流水线。本轮实施导出半边时需要确定若干实现级边界：输出位置、取消语义、写入并发、原子发布与错误分类。

### 决策

1. **输出目录**：首版备份写入应用文档目录下 `backups/`（`getApplicationDocumentsDirectory()/backups`），由组合根提供 `backupOutputDirectoryProvider` 可注入替换；暂不提供系统文件选择器「另存为」出口（归后续任务）。文件名 `ai-recipe-<UTC 时间戳>.airecipe-backup`，两次创建必然产生不同文件，天然幂等。
2. **归档组装在 Isolate 中执行**：`DeviceBackupArchiveWriter` 用 `Isolate.run` 完成 ZIP 组装与重读复核，避免大库哈希/压缩阻塞 UI 线程。
3. **原子发布与失败清理**：先写 `<name>.partial`，重读复核（必需条目齐全、dataset 哈希与 manifest 一致、媒体 SHA-256 与路径一致、无多余条目）通过后原子重命名为最终文件名；任何失败/取消路径 best-effort 清理 `.partial` 与临时目录，不残留半成品。
4. **取消语义**：`BackupCancellationToken` 只做协作式取消；导出各阶段检查点在 `throwIfCancelled()` 处抛 `BackupOperationCancelledException`，由 Facade 映射为 `backupCancelled`，UI 关闭弹窗回到预估态且不写文件。
5. **媒体失败即失败**：必需媒体缺失 → `mediaMissing`、不可读 → `mediaUnreadable`、哈希不一致 → `mediaHashMismatch`，均为可重试失败；不交付缺媒体的包。
6. **Facade 错误映射**：`BackupOperationCancelledException` → `backupCancelled`；retryable `BackupException` → `storageUnavailable`；其余 → `backupFailed`；未知兜底 → `storageUnavailable`。UI 只读 `message` 与 `code`，不暴露底层路径。

### 影响与代价

- 备份文件在应用私有文档目录，普通用户不易直接访问；已提供「另存为」出口（见 ADR-0036），Android 不再必须 adb 取走文件。
- Isolate 内不能直接访问 sqflite 连接，快照读取在主 isolate 完成后再传入写入器，媒体字节经 `readMediaBytes` 读入内存/文件句柄传递；超大媒体仍待 BACKUP-006 规模验收。

- 「另存为」出口按 `test/features/backup_page_test.dart` 4 项通过（ADR-0036）。

## ADR-0036：备份「另存为」出口（BACKUP-002/003 用户可达性）

- 日期：2026-08-07
- 状态：生效（已实施，等待项目负责人真机验收）
- 关联任务：BACKUP-002、BACKUP-003
- 关联决策：ADR-0035

### 背景

项目负责人反馈"备份可以创建了但不知道保存在哪"。首版备份落在应用私有文档目录（Android `app_flutter/backups/`），普通文件管理器不可见，只能靠 adb 取出。为给用户可操作出口，创建成功后提供「另存为」把备份复制到用户可选位置（如下载）。

### 决策

1. **「另存为」按钮**：备份页「上次备份已创建」区域新增「另存为（导出到其他位置）」按钮，调用系统文件选择器（file_picker `saveFile`，Android 走 SAF `ACTION_CREATE_DOCUMENT`）选择目标位置，把备份写入该位置。成功提示「备份已另存到：<路径>」，用户取消不提示，写入失败提示「另存失败，请重试。」。
2. **成功摘要展示完整路径**：上次备份结果展示文件名、体积与完整文件路径。
3. **可注入回调**：`BackupPage` 新增 `saveBackupFile`（另存为回调，默认 file_picker 实现，测试注入 fake）、`estimateBackup`（预估回调，默认走 backend 真实预估；widget 测试注入 fake 避免触发真实 SQLite）、`initialResult`（最近备份结果展示，测试注入用）。上次备份结果区域移到 ListView 底部，独立于预估状态始终展示。
4. **无新增依赖**：复用导入侧已有的 file_picker。
5. **2026-08-07 修正**：file_picker 8.x 在 Android/iOS 上 `saveFile` 必须传 `bytes`（插件只把传入的 bytes 写入用户所选文件，不传则 Dart 端抛 `ArgumentError`）→ 默认实现改传 `File(source).readAsBytes()`，并移除对返回路径执行 `File.copy` 的错误做法。另因 Android 返回路径是插件拼接的 `Downloads/<文件名>` 伪路径（与实际所选目录可能不符），Android 上成功提示改为「备份已保存到所选位置」，其余平台仍显示完整路径。

### 影响与代价

- ADR-0035 中"Android 上需 adb 或后续入口"的限制解除；用户可直接把备份导出到「下载」等可访问目录。
- file_picker `saveFile` 的 `bytes` 经平台通道整体传输，超大备份（数百 MB）存在平台通道传输上限，属 BACKUP-006 大规模导出已知限制（后续可评估 SAF 原生实现或分块写入）。

### 验证方式

## ADR-0037：烹饪模式无时长步骤支持自定义计时，自定义时长同步保存到菜谱步骤

- 日期：2026-08-07
- 状态：生效（已实施，等待项目负责人复测）
- 关联任务：COOK-001
- 关联决策：ADR-0012/0013（页面只通过 `AiRecipeBackendFacade` 访问业务能力）

### 背景

烹饪模式中，菜谱步骤的 `durationSeconds` 是可空字段：AI 导入或手动创建的部分步骤没有设置时长，页面只显示"本步骤未设置时长"且无法启动计时器。项目负责人反馈："有一些没有计时的东西，所以加一个自定义的吧，如果这个时候用户自定义了也请同步到菜谱中。" 即用户应能在下厨时为无时长步骤手动设置时长并启动计时器，且该时长应持久化到对应菜谱步骤，下次烹饪时可直接一键启动。

### 决策

1. 无时长（`durationSeconds == null` 或 0）的步骤在烹饪模式显示「自定义本步计时」按钮，点击弹出像素风输入弹窗（分钟/秒两个输入框），确认后创建计时器。
2. 自定义时长同时写入菜谱步骤：领域新增 `updateRecipeStepDuration(recipeId, stepId, durationSeconds)`，只重建目标步骤、保留其他字段，避免为改一个字段走整份菜谱更新造成覆盖；Facade 透传（`_recipeOperation` 包装），页面仍然只通过 `AiRecipeBackendFacade` 访问。
3. 同步成功后菜谱刷新为更新后的对象，计时器标签沿用既有「步骤 N」关联规则（`CookingTimer` 尚无步骤索引字段，不伪造数据关系）。
4. 弹窗校验：时长必须大于 0（分钟/秒任一为 0 时仍可组合为合法秒数，两者都为 0 或非法输入时提示"请输入大于 0 的时长"且不关闭弹窗）；取消不产生任何副作用。
5. 弹窗遵循全项目像素风规范（透明 Dialog + `PixelSurface` 切角/描边/投影 + `AppColors`），输入控制器由弹窗自身 StatefulWidget 持有并在 dispose 释放（沿用 `_PasteTextDialog` 样例，避免 overlay 断言）。

### 原因

- 无时长步骤是常见数据形态，用户下厨时需要计时但不该被"未设置时长"卡住。
- 同步到菜谱能避免用户每次重复输入，符合"自定义一次、长期复用"的预期。
- 只更新目标步骤而不是整份草稿，避免覆盖用户在同一菜谱其他字段上未保存的本地修改，且无需重新走完整 `RecipeDraftInput` 校验。

### 影响与代价

- 领域 `Recipe` 不可变，更新步骤时长需要重建 `RecipeStep` 与 `Recipe` 对象并递增 `localVersion`（持久化写一次 upsert）。
- 同步是写操作：写入失败时通过 SnackBar 提示，不静默；计时器只在实际同步成功后创建（保证菜谱与计时器时长一致）。
- 非法时长（≤0）与不存在的步骤 ID 抛出 `RecipeLibraryValidationException`，Facade 映射为稳定 `invalidInput`。

### 验证方式

- domain 用例测试：只更新目标步骤、时长 0 抛异常、步骤不属于菜谱抛异常。
- Facade 测试：更新时长持久化、非法输入映射为 `invalidInput`。
- 烹饪页 Widget 测试：无时长步骤显示「自定义本步计时」按钮且不显示一键启动按钮；输入 2 分 30 秒确认后创建「步骤 2」计时器（150 秒）且菜谱步骤时长同步为 150；取消弹窗后一切不变。
- 项目负责人按 `tests/acceptance/COOK-001-custom-timer-sync-2026-08-07.md` Android 复测。

## ADR-0038：推荐匹配采用「全局批次分配 + 精确库存优先」，同家族只召回候选

- 日期：2026-08-08
- 状态：生效（已实施，等待项目负责人验证）
- 关联任务：RECO-001
- 前置：ADR-0021（标准 ID + 别名词典）、ADR-0022（基础食材 + 属性规格 + 三值匹配）、ADR-0023（食材家族与模糊匹配）
- 关联风险：R-019

### 背景

按项目负责人反馈，原有推荐匹配在多个规格并存时会把同一份库存重复匹配给多个菜谱需求，例如一份「辣椒」同时满足青椒、红椒、甜椒，或「五花肉」既顶替五花肉又抢占普通猪肉。即使继续扩充别名词典（青椒/红椒/甜椒）也无法解决——因为缺少**库存占用（批次全局分配）**与**精确库存优先**，同一批次仍会被重复匹配。项目负责人给出以下最终默认原则。

### 决策

推荐匹配（单道菜谱内）采用以下六条默认原则：

1. **同家族只负责召回候选，不代表已拥有**：家族/替代（MAYBE，如 辣椒→青椒）只进入「可能可以做」，不计入命中、不计入缺失、不触发临期标记，数量视为需确认（不统计）。
2. **一份身份不明确的库存不能同时满足多个不同规格**：单道菜谱内用 `usedBatchIds` 做**全局批次分配**，同一批次最多满足一个需求（含 MAYBE 占用）。
3. **精确库存优先**：身份分配按需求属性分面数量从多到少排序（最具体优先），避免「五花肉也属于猪肉」抢占普通猪肉的匹配——五花肉批次优先满足五花肉需求，普通猪肉满足猪肉需求。
4. **库存身份与兼容关系分离**：只有 `matchIngredientSpec` 返回 YES（基础一致 / 库存更具体且属性无冲突）才算“身份满足”；猪肉可“兼容”五花肉需求（MAYBE），但不等于被识别成五花肉（身份）。
5. **菜谱内猪肉/五花肉不能仅按基础 ID 去重**：需求去重键 = 基础食材 ID + 属性分面（`_requirementKey`），使同基础不同规格成为独立需求。
6. **数量只统计最终分配的批次**：命中数量只累加 `assignedBatches`（阶段 A 身份分配结果），MAYBE 的候选批次不计入，杜绝“把所有候选批次数量都算进去”的虚高。

未收录基础食材的需求（如「鸡蛋」不在词典）退化为同名精确匹配：其候选批次只来自同一 `name:规范化名` 键，按身份命中（YES）处理。

### 原因

- 全局批次分配是「同一份库存被重复匹配」问题的根因修复，比继续扩充别名词典更重要。
- 精确库存优先符合用户心智：冰箱有五花肉和普通猪肉时，菜谱同时要五花肉和猪肉应两者都命中，而不是五花肉抢走普通猪肉的匹配。
- 数量只统计最终分配批次，避免把候选批次数量混入导致“看起来够、实际可能被别的需求占用”。

### 影响与代价

- `inventory_use_cases.dart` 的 `InventoryRecommendationUseCases.recommend()` 主循环重写为三阶段：A 身份匹配（YES，按分面多→少分配并占用批次）→ B 家族/替代（MAYBE，占用单一批次）→ C 缺失/规格冲突。
- 删除了原 `_bestMatch()`/`_BestMatch`，新增 `_RecipeRequirement`、`_isYesFor`、`_requirementKey`、`_facetCount`、`_unitOf`。
- 需求去重由按基础 ID 改为按「基础 + 分面」；未收录基础食材的需求规格需用名称解析结果补全（否则 `matchIngredientSpec` 误判为 MAYBE）。
- 现有部分测试断言需随新语义修正（未收录食材且无批次 → 缺失，而非“冰箱未选”）。

### 验证方式

- 单元测试：同一批次不能同时满足多个规格；精确库存优先（猪肉/五花肉各就位）；数量只统计最终分配批次；既有三值/家族/别名/去重用例保持通过。
- 项目负责人按推荐页复测：冰箱同时有五花肉与普通猪肉、或同一份辣椒面对多个辣椒类需求时，卡片不再重复命中/数量不再虚高。

## ADR-0039：正式产品名称与官方 IP 像素化渲染边界

- 日期：2026-08-10
- 状态：生效
- 关联任务：DESIGN-008、BRAND-001
- 关联资产：`design/assets/IP.png`、`design/assets/封面图.png`

### 背景

项目负责人确认 App 正式名称为「巴食」，并指出上一版 Image 2 美术结果过度 3D，未服从已经落地的 UI。项目已有水豚主厨 IP 原图，但原图采用柔滑插画、渐变和体积化处理；若把原图同时当作角色身份和渲染风格参考，生成模型会持续把资产做成黏土、塑料、贴纸或柔滑伪像素风。

3. 官方 IP 原图不承担渲染风格定义。不得继承其平滑抗锯齿、渐变、柔光、体积光、厚涂、圆润塑料感或类 3D 处理。
4. Flutter/HTML 已落地 UI 是美术渲染的权威事实源：正式色板、米白纸张底、8/4/3px 阶梯缺角、深墨绿描边、2–3px 右下硬投影、实色块、硬边和可见方形像素台阶。
5. 官方生成型美术统一采用**严格二维像素风**：正面正交、无透视深度、最近邻像素渲染、有限色板、无平滑色彩过渡；UI 风格与严格像素约束的优先级高于 IP 原图画法。
6. 下列任一偏差出现即整张淘汰：3D、等距视角、黏土/塑料、倒角、挤出、渐变、环境光、体积光、AO、软阴影、喷枪/厚涂、平滑抗锯齿、柔和圆角矢量插画、贴纸、emoji、景深或写实摄影。

- 把“身份参考”和“渲染参考”拆开，才能在保留官方角色识别度的同时服从现有 UI。
- 明确一票否决项比使用宽泛的“像素风”描述更能抑制 Image 2 的柔滑和 3D 倾向。
- 将名称与视觉基准写入长期事实源，可避免后续资产、页面和宣传材料继续分叉。

### 影响与代价

- `DESIGN-008` 的旧 v0 提示词与上一轮样张不再作为正式方向，全部升级为 v1 并重新验收。
- 品牌与较大状态插图可以使用官方 IP；48px 入口、冰箱和分类图标仍优先使用清晰物体符号，避免复杂角色挤压小尺寸语义。
- 仓库中既有「拾味」文字不会在本轮静默批量修改，需由 `BRAND-001` 按产品文档→任务→设计/代码→验收的流程处理。

### 验证方式

- 出现任何一票否决项时直接淘汰并返工提示词，不进入 Flutter。

## ADR-0040：图片型图标的激活态资产边界

- 日期：2026-08-10
- 状态：生效
- 关联任务：DESIGN-008
- 关联文档：`design/assets/prompts/00-bottom-navigation-icons.md`、`design/assets/prompts/05-category-icons.md`、`design/assets/prompts/06-active-state-supplements.md`

### 背景

项目负责人认可严格二维像素导航 glyph 方向后，要求补充激活态，并确认其他存在长期选中状态的图标也需要统一规则。若所有图片都机械制作 active，会造成资产数量膨胀、短暂交互状态不一致；若 active 由生成模型从零重画，又会出现轮廓、位置、像素矩阵和投影漂移。

### 决策

1. 底部导航首页、菜谱库、冰箱、我的四项制作独立 default / active，共 8 枚 24×24 单色像素 UI glyph。
2. 导航图片只负责 glyph 的状态差异：default 为 `#8F978F` outline，active 为 `#476B52` filled / strong；上下两态必须同外轮廓、同尺寸、同位置、同重心、同基线。`#EDF2EA` 激活容器、外框、文字颜色和点击反馈由 Flutter 绘制，不烘焙进图片。
3. 默认分类家常菜、快手菜、早餐、主食、汤羹、烘焙、甜品、饮品、素菜、肉类、水产、轻食十二项制作独立 default / active。
4. 分类 active 必须使用已通过的同一张 default 原图作为 Image 1 编辑，只调整深绿色视觉权重；外轮廓、像素矩阵、构图、位置、基线、描边、右下硬投影和透明区域必须保持不变，禁止根据分类名从零重画。
5. 品牌资产、状态插图、功能入口、冰箱分区、库存与推荐图标不制作独立 active 图片。品牌与状态图非长期选中控件；功能入口的 pressed / busy / disabled / focus，以及库存和推荐的选中、缺失、数量与等级，由 Flutter 容器、透明度、描边、文字、标签和进度状态统一处理。
6. 返回、关闭、搜索、收藏、勾选、删除、箭头、更多、开关等 16–24px 高频操作符号继续使用 Flutter 原生图标与组件状态，不生成位图版本。

### 原因

- 长期导航/筛选选中状态需要稳定且有品牌一致性的双状态视觉；短暂交互状态更适合由代码统一控制。
- 导航 glyph 与分类食物图标的状态机制不同：导航可使用 outline / filled，分类必须保留食物语义色，只提高深绿色权重。
- 由 Flutter 绘制容器和反馈，可避免图片重复携带底板、边框、文案或进度状态，并支持主题、无障碍和交互一致性。
- 分类 active 基于原图编辑，可最大限度避免生成模型重画导致的视觉跳动。

### 影响与代价

- DESIGN-008 的正式产物在原 48 条基础 Prompt 外，增加导航 8 枚最终 glyph 与分类 12 枚 active 图片。
- 导航需先生成 2×4 双状态确认稿；该网格只用于校准，不作为最终 sprite sheet。
- 分类需先验证早餐 default / active，叠放无位移且 40px 可辨后，才继续其余 11 组。
- Flutter 实施时需继续负责选中容器、边框、文字、点击反馈、进度、禁用和错误等组件状态。

### 验证方式

- 按 `tests/acceptance/DESIGN-008-image2-icon-prompts-2026-08-10.md` 检查导航 2×4 双状态稿。
- 将 `category-breakfast-v1.png` 与 `category-breakfast-active-v1.png` 以 50% 透明度叠放，确认只有颜色权重变化，没有轮廓、像素位置、描边、投影或基线漂移。
- 导航在约 21px、分类在 40px 下检查可识别性；任何 3D、透视、厚度、渐变、软阴影或抗锯齿均直接淘汰。
## ADR-0041：非品牌美术资产禁止使用官方 IP

- 日期：2026-08-10
- 状态：生效
- 关联任务：DESIGN-008
- 关联文档：`design/assets/IMAGE2_ICON_PROMPTS.md`、`design/assets/prompts/`、`tests/acceptance/DESIGN-008-image2-icon-prompts-2026-08-10.md`

### 背景

项目负责人确认上一版其他图标不应使用官方 IP。即使较大的状态插图有足够空间容纳角色，水豚主厨、厨师帽、墨镜、五官和拟人表情仍会抢占功能语义，并诱导 Image 2 延续柔滑、体积化或类 3D 的角色画法。需要把“品牌身份资产”和“普通功能资产”的使用边界固定下来，避免后续批次因复用 `IP.png` 再次混入角色。

### 决策

1. `design/assets/IP.png` 只允许用于以下 4 项品牌资产：App 启动图标、品牌核心符号、欢迎页 Hero、通用菜谱无封面。
2. 所有非品牌资产禁止上传、参考或生成 `IP.png` 与 `封面图.png`，范围包括：状态插图 12 项、功能入口 10 项、冰箱 / 库存 / 推荐 10 项、分类 default 12 项、底部导航 default / active 4 组共 8 枚、分类 active 12 项。
3. 非品牌资产只使用最简洁的功能物体、食材和符号表达语义，不得出现水豚、人物、动物角色、厨师、厨师帽、墨镜、脸、五官、手脚、四肢、拟人姿态、拟人表情、吉祥物、角色轮廓或任何官方 IP 特征。
4. 非品牌资产的固定优先级为：**巴食 UI 风格与严格像素约束 > 单项功能语义**。当前「巴食」Flutter / HTML UI、页面截图与纯色板卡是唯一允许的视觉参考。
5. 任一非品牌样张出现角色、拟人化或 IP 特征，整张直接淘汰，不以“可爱”“识别度高”或“符合食谱主题”为保留理由。
6. ADR-0040 的 active 状态职责继续有效：导航与分类保留独立双状态，但两类状态资产也必须无 IP；其他资产的短暂或业务状态继续由 Flutter 组件表达。

### 原因

- 品牌资产需要官方角色识别度，普通功能资产需要优先保证语义清晰、尺寸适配和批次一致性，两者不应共用角色机制。
- 不向 Image 2 提供 IP 参考图，可以降低模型自动补充水豚、厨师、五官、柔光和体积塑形的概率。
- 用物体、食材和符号表达状态，更容易在小尺寸、空状态和极限内容下维持与现有 UI 一致的严格二维像素语言。

### 影响与代价

- 本决策收紧 ADR-0039 中“品牌与较大状态插图可以使用官方 IP”的旧边界：从 v1.3 起，状态插图也属于非品牌资产，不再允许 IP。
- ADR-0039 关于正式产品名「巴食」、官方 IP 身份与画法分离、现有 UI 为渲染事实源、严格二维像素一票否决项的其他内容继续有效。
- ADR-0040 关于导航 / 分类 active 的生成与 Flutter 状态职责继续有效，但所有相关图片均不得出现 IP。
- DESIGN-008 的基础 Prompt 总数仍为 48 条，其中品牌 4 条允许 IP、其他 44 条禁止 IP；另有无 IP 导航 8 枚和无 IP 分类 active 12 张。

### 验证方式

- 首轮生成时不向导航、早餐分类和冰箱空状态上传 `IP.png` 或 `封面图.png`。
- 按 `tests/acceptance/DESIGN-008-image2-icon-prompts-2026-08-10.md` 检查 `bottom-navigation-glyph-state-proof-v1.3.png`、早餐 default / active 与 `state-fridge-empty-v1.png`。
- 非品牌样张出现任一角色、五官、手脚、拟人姿态、拟人表情、吉祥物或 IP 特征时直接淘汰；其余严格二维像素与双状态标准继续按 ADR-0039、ADR-0040 执行。

## ADR-0042：LLM 与识图设置重分类

### 背景

项目负责人反馈：LLM API 设置与识图引擎两个页面的项目需要重新打散排列——多模态 LLM 与普通 LLM 本质都是 LLM；识图引擎的 OCR 与多模态 LLM 都是图片识别能力。希望重新分类入口与页面内容。

### 决策

「我的」页保持两个入口，但内容重新划分（SETTINGS-001）：

1. **「LLM 模型」入口**：集中管理两类 LLM 配置。
   - 菜谱生成 LLM（普通文本 LLM，结构化生成）。
   - 多模态 LLM 图片识别（独立配置，从识图引擎页迁入）。
   - 两类 LLM 各自独立保存 API 地址 / Key / 模型 / 超时。
2. **「识图引擎」入口**：只保留 OCR 相关——图片识别方式（自动 / 仅 OCR / 多模态 LLM）、本地 OCR 模型、云端路线；不再内嵌多模态 LLM 配置表单。

### 影响

- 页面标题：「本地 LLM API」→「LLM 模型」；「我的」页入口同步改名。
- 图片识别方式仍可选「多模态 LLM」，其配置读取「LLM 模型」页保存的图片识别 LLM。
- 代码：多模态配置类从 `ocr_settings_page.dart` 迁至 `llm_settings_page.dart`；识图引擎页清理相关依赖。

### 状态

生效（待验收）。Codex 未执行 `flutter analyze`/构建/真机（ADR-0015），由项目负责人按 `tests/acceptance/SETTINGS-001-llm-ocr-restructure-2026-08-11.md` 验收。

## ADR-0043：Gitee 在线更新数据源与安装方式

### 背景

项目负责人要求新增在线更新功能，使用 Gitee 平台。检查更新页显示当前版本 + 检查更新按钮；有新版本时弹窗提示版本号与更新说明，按钮「以后再说」/「立即升级」。

### 决策（UPDATE-001，项目负责人选定）

1. **数据源**：Gitee 公开仓库 `https://gitee.com/eb-Dog/delicious-food`（owner=eb-Dog, repo=delicious-food）。**2026-08-11 项目负责人指定改用仓库根目录 `version.json`**（`…/raw/master/version.json`，branch=master）作为更新配置来源，不再使用 Release API。公开仓库匿名读取，无需 Token。
2. **version.json 字段**（宽容解析，支持候选键）：
   - 最新版本号（必填）：`version` / `latest_version` / `tag_name` / `latestVersion`（支持 v 前缀，语义化比较）。
   - 更新说明：`note` / `changelog` / `update_note` / `release_notes` / `body` / `description`。
   - APK 下载直链：`apk_url` / `apkUrl` / `download_url` / `downloadUrl` / `url` / `apk` / `apk_link` / `apkLink`。
   - 发布页地址（可选）：`html_url` / `page_url` / `release_page` / `homepage` / `project_url`。
   - 最新版本严格大于当前版本才提示更新。
3. **平台范围**：仅 Android；「立即升级」= 应用内下载 APK 到临时目录 → FileProvider 暴露 → 系统安装器（ACTION_VIEW + `application/vnd.android.package-archive`），需要 `REQUEST_INSTALL_PACKAGES` 权限；Android 8+ 未授权时由系统引导「安装未知应用」。iOS 不提供应用内更新。
4. **入口**：「我的」页「数据与存储」下方新增「检查更新」入口。
5. **当前版本号来源**：`package_info_plus` 运行时读取（失败回退构建注入 `--dart-define=APP_VERSION`，再回退常量 1.0.0）。

### 影响

- 新增依赖 `package_info_plus`；新增 `domain/update/`、`features/update/`（service/page/apk_installer）与 Android 原生 `update/ApkInstallMethodHandler.kt`。
- 检查更新只读公开文件，不上传任何用户数据；下载仅写入应用临时目录，安装由系统接管。
- 404/403 时二次请求仓库详情区分「仓库存在但缺 version.json」与「仓库不存在/私有」。
- 风险：Gitee 仓库文件下载对直连网络要求较高，失败时页面提示网络不可用。

### 状态

生效（待验收）。Codex 未执行 `flutter pub get`/`flutter analyze`/构建/单元测试/真机（ADR-0015），由项目负责人按 `tests/acceptance/UPDATE-001-gitee-update-2026-08-11.md` 验收。

## ADR-0043：公开仓库的脱敏边界

- 日期：2026-09-18
- 状态：生效
- 关联任务：OPS-005、PROF-001、COMMUNITY-001、VID-001

### 背景

项目在 2026-07-28 首次发布到 GitHub 时仓库为私有（`zisjugoudan/ai-recipe`）。此后应用本体、设计资产和视频工程都只提交在本地，远端落后 15 个提交以上。项目负责人要求把仓库同步到 GitHub 并转为公开，同时要求先做数据脱敏。

盘点后确认仓库内存在三类不应公开的内容：

1. **个人数据**：`design/assets/收款码/`（微信 1213×1213、支付宝 1260×1890）与其应用资产副本 `code/apps/mobile/assets/payment/`；`design/assets/交流群.jpg` 与其副本 `code/apps/mobile/assets/community/qq_group.jpg`。这两组都是可直接被扫码识别、可被批量收集的个人收款与联系方式。
2. **本地产物**：`视频剪辑/`（约 1 GB，含本地开发环境录屏、node_modules 与成片）、`code/apps/mobile/android/*.hprof`（约 2 GB 的 JVM 堆转储，可能含运行期内存内容）、`.tmp/`、`.trae/`、`design/.workbuddy/`。
3. **第三方内容**：`design/assets/IP.png` 与 `design/assets/封面图.png` 是水豚主厨角色的身份参考图，使用边界已由 `design/assets/README.md` 限定为 4 项品牌资产。

### 候选方案

1. 全部文件原样提交，靠用户自行判断哪些不该公开。
2. 把收款码替换为占位图后提交，保持克隆即可构建。
3. 将个人数据与本地产物写入 `.gitignore` 排除，保持应用代码不变，并在文档中写明本地补齐方式。

### 决策

采用方案 3：

- 排除清单写入根目录 `.gitignore`：`design/assets/收款码/`、`design/assets/交流群.jpg`、`code/apps/mobile/assets/payment/*.jpg`、`code/apps/mobile/assets/community/*.jpg`、`视频剪辑/`、`.tmp/`、`.trae/`、`.workbuddy/`、`*.hprof`、`*.dill`、`*.apk`、`*.aab`、`*.ipa`。
- 不采用方案 2 的占位图：占位图与真实收款码同路径，一旦提交，本地真实文件会被 git 视为「已跟踪文件的修改」，反而制造误提交风险。排除真实路径可以从机制上保证真实收款码无法被 `git add` 命中。
- 应用代码保持不变，`pubspec.yaml` 仍声明 `assets/payment/*.jpg` 与 `assets/community/*.jpg`。新增 `code/apps/mobile/assets/payment/README.md` 与 `code/apps/mobile/assets/community/README.md` 说明所需文件、参考源图和补齐方式；根 `README.md` 增加「仓库内容边界」章节。
- 第三方角色参考图保留在仓库中，但沿用 `design/assets/README.md` 既有的 4 项品牌资产使用边界，并在根 README 中显式标注。
- 代码与文档不得内置任何真实 API Key、Token、账号或 Cookie（延续 `AGENTS.md` 第 4 节）。

### 原因

- 公开仓库一旦推送，被索引和缓存后即使删除也难以真正撤回，个人收款码属于不可逆暴露风险，必须在机制层面阻断而不是靠人工判断。
- 录屏与堆转储体积占仓库绝大多数（3 GB 以上），且包含本地环境画面与运行期内存，对代码库没有价值。
- 保持应用代码与 pubspec 不变，可以让项目负责人的本地开发环境完全不受影响；受影响的只有全新克隆者，且失败现象（缺资产）与修复方式都有就地文档。

### 影响与代价

- **全新克隆无法直接构建**：缺少 `assets/payment/wechat_qr.jpg`、`assets/payment/alipay_qr.jpg`、`assets/community/qq_group.jpg` 时 Flutter 构建报找不到资产。这是本决策接受的代价，必须按两个目录内的 `README.md` 补齐。
- 项目负责人本地仓库不受影响，真实收款码与群二维码仍保留在本机，且 `git status` 不再显示它们。
- `视频剪辑/` 与验收产物不再随仓库分发，`VID-001` 的成片与终检记录只存在于本地；相关记录仍保留在 `tracking/CHANGELOG.md` 与 `tracking/CURRENT.md`。
- 后续如需公开分享视频或设计源图，必须另建不含个人数据的分发渠道，不能直接放开忽略规则。

### 验证方式

- `git check-ignore` 逐项校验排除清单全部命中，且 `assets/payment/README.md`、`assets/community/README.md` 不被误伤。
- 全仓库文本扫描确认无 `sk-`、`AIza`、`ghp_`、私钥块等凭证格式，无手机号与个人邮箱。
- 推送到 `origin/main` 后通过 GitHub API 读取仓库可见性为 `public`，并确认远端文件树不含排除项。
- 项目负责人按 `tests/acceptance/OPS-005-github-public-release-2026-09-18.md` 复核。
