# 全量菜谱备份与恢复架构方案

> 状态：v0，等待项目负责人方案走查  
> 日期：2026-08-06  
> 关联任务：`BACKUP-001`  
> 关联决策：`ADR-0034`  
> 产品事实源：`docs/product/AI食谱应用产品需求文档.md` 5.12.2、5.12.3  
> 用户故事：`docs/product/USER_STORIES.md` US-014

## 1. 结论

最适合本项目的方案是：**使用版本化、可迁移、可流式处理的 ZIP 归档包作为菜谱库备份格式**，对用户显示专用扩展名 `*.airecipe-backup`。备份操作始终导出完整菜谱库；导入先生成只读预检计划，再由用户选择“合并导入”或“替换当前菜谱库”。

首版不备份原始 SQLite 文件，也不把图片编码进单个巨型 JSON。归档包内使用：

- `manifest.json` 描述格式、能力、数据集、数量、版本和校验值；
- NDJSON 数据集按记录流式读写；
- 图片以 SHA-256 内容哈希命名并去重；
- 每种数据集独立版本化并通过 Migrator 链迁移；
- 未识别的必需能力阻止导入，未识别的可选能力只可在明确提示后跳过。

该方案把“长期备份格式”与“当前 SQLite schema”解耦，适合 Flutter + SQLite + Local-first，也为以后增加冰箱、购物清单、制作记录、账号数据或加密方式保留扩展点。

## 2. 目标

1. **全量**：一次备份覆盖当前设备中的全部菜谱，而不是用户选择的部分菜谱。
2. **可恢复**：数据、分类结构和本地媒体可以在另一台设备或未来版本中恢复。
3. **不静默丢数据**：损坏、版本不兼容、媒体缺失和冲突都必须在写入前暴露。
4. **高可扩展**：新增数据类型不要求重写归档核心；旧备份可以通过迁移器导入。
5. **低内存**：大量菜谱和图片使用流式读写，不把整个备份一次加载到内存。
6. **Local-first**：游客和登录用户均可离线备份与恢复，不依赖服务器或 AI Provider。
7. **可回滚**：导入失败不能破坏当前库；替换恢复必须先产生可用回滚备份。

## 3. 非目标

- 不把 Markdown、PDF、图片分享稿当作可恢复备份。
- 不把备份功能等同于云同步、账号迁移或家庭共享。
- 首版不备份冰箱库存、购物清单、制作记录、浏览历史、导入任务或运行中计时器。
- 不备份 API Key、Token、Cookie、登录凭证、Keychain/Keystore 内容、本地 OCR 模型包或临时缓存。
- 本方案不实现代码，不承诺当前 SQLite v11 已具备媒体原子恢复所需的全部数据契约。

## 4. 当前事实与约束

当前 Flutter 本地数据库 `schemaVersion = 11`，菜谱数据分布在 `recipes`、`recipe_images`、`ingredients`、`recipe_steps`、`recipe_categories` 和 `recipe_category_relations`。`Recipe` 聚合还包含标签、收藏、状态、时间、版本和软删除字段。

菜谱图片当前以绝对/应用私有路径字符串保存，文件位于：

```text
<应用文档目录>/recipe_covers/<containerId>/<index>.<ext>
```

正式菜谱当前只保存 `sourceId`，没有完整来源 URL、canonical URL 或不可变来源快照。备份实现前必须处理以下契约缺口：

- 备份不能直接复制数据库中的设备路径作为可移植引用；
- 需要稳定媒体资产引用和导入会话清理账本；
- 来源字段只能按当前已有数据导出，不能伪造不存在的来源证据；
- 未来来源元数据应作为可选、版本化字段扩展，关联 `R-016`。

## 5. 为什么不选其他方案

### 5.1 不备份原始 SQLite 文件

原始数据库快照与当前表结构、迁移顺序、平台路径和 SQLite 运行状态强耦合。它难以做逐实体预检、跨版本迁移、冲突展示、部分能力兼容和媒体路径修复，也可能把不应导出的设置或临时任务一并带出。

SQLite 文件可以作为应用内部灾难恢复手段研究，但不能作为对用户公开、长期承诺的数据可移植格式。

### 5.2 不使用单个巨型 JSON + Base64 图片

- Base64 通常增加约三分之一体积；
- 大库需要一次性解析时容易出现内存峰值；
- 单点损坏影响整个文件；
- 图片无法按内容去重；
- 后续增加独立数据集、增量校验和迁移器较困难。

### 5.3 不把 Markdown/PDF 当备份

Markdown/PDF 适合阅读和分享，但不能无损恢复稳定 ID、分类关系、收藏、草稿/归档/回收站状态、图片引用、时间戳和未来扩展字段。

## 6. 归档格式

### 6.1 文件名与容器

用户可见文件名建议：

```text
AI食谱-菜谱全量备份-2026-08-06-1430.airecipe-backup
```

`*.airecipe-backup` 内部是标准 ZIP。专用扩展名用于避免用户把它误认为普通压缩包；标准 ZIP 便于跨平台实现、离线检查和后续迁移。

### 6.2 首版目录结构

```text
manifest.json
data/
  recipes.v1.ndjson
  categories.v1.ndjson
media/
  index.v1.ndjson
  sha256/
    ab/
      <完整 sha256>.<ext>
```

未来数据集直接追加，不改变首版核心文件：

```text
data/inventory-batches.v1.ndjson
data/inventory-changes.v1.ndjson
data/cooking-history.v1.ndjson
data/shopping-list.v1.ndjson
extensions/<namespace>/<dataset>.ndjson
```

### 6.3 Manifest 最小字段

```json
{
  "format": "ai-recipe-backup",
  "formatVersion": "1.0",
  "minimumReaderVersion": "1.0",
  "backupId": "稳定 UUID",
  "createdAt": "ISO-8601 UTC 时间",
  "appVersion": "创建备份的应用版本",
  "platform": "android | ios",
  "scope": "full-recipe-library",
  "requiredFeatures": ["recipes-v1", "categories-v1", "media-index-v1"],
  "optionalFeatures": [],
  "datasets": [],
  "statistics": {
    "recipeCount": 0,
    "deletedRecipeCount": 0,
    "categoryCount": 0,
    "mediaCount": 0,
    "totalUncompressedBytes": 0
  },
  "compression": "zip-deflate",
  "encryption": {"algorithm": "none"}
}
```

每个 `datasets` 项至少记录：

- `name`：稳定数据集名称；
- `schemaVersion`：该数据集自身的整数版本；
- `required`：当前包是否要求读取器理解它；
- `path`：包内相对路径；
- `recordCount`、`byteSize`；
- `sha256`：未压缩逻辑文件的校验值；
- `dependsOn`：数据集依赖。

`formatVersion` 与 SQLite `schemaVersion` 完全独立。格式主版本表示不兼容变化，次版本只允许向后兼容的新增。每种实体再使用独立 `schemaVersion`，避免一个字段变化迫使整个归档格式升级。

### 6.4 菜谱记录

`recipes.v1.ndjson` 每行是一道完整菜谱聚合，至少覆盖当前领域真实存在的：

- 稳定菜谱 ID；
- 标题、描述、份量、准备/烹饪/总时间、难度和备注；
- 收藏状态；
- `draft`、`published`、`archived` 状态；
- `createdAt`、`updatedAt`、`localVersion`、`deletedAt`；
- 食材完整字段、排序和未来语义规格字段；
- 步骤完整字段和排序；
- 标签；
- 分类 ID 关系；
- 封面和配图的 `mediaId`/内容哈希引用；
- 当前已有的 `sourceId`；未来来源 URL、canonical URL、证据快照以版本化可选字段或扩展命名空间加入。

一条菜谱记录内嵌食材、步骤、标签和分类引用，便于逐菜谱校验、冲突比较和流式导入；媒体二进制仍独立存放。

身份字段不作为账号授权凭据。导入时菜谱所有权必须绑定到当前本地身份/登录身份，不能仅凭包内 `userId` 获得另一个账号的所有权。若保留原身份信息，只能作为非授权来源元数据。

### 6.5 分类记录

`categories.v1.ndjson` 必须包含全部分类，包括没有菜谱的空分类，才能恢复用户的整理结构。分类保留稳定 ID、名称、排序、时间和软删除字段（若当前/未来模型具备）。

### 6.6 媒体记录与内容寻址

`media/index.v1.ndjson` 每行描述一个媒体对象：

- 稳定 `mediaId`；
- SHA-256；
- MIME、扩展名、字节大小和可选像素尺寸；
- 包内相对路径；
- 被哪些实体引用只用于诊断，不作为唯一关系来源。

媒体文件按内容哈希命名和分目录：

```text
media/sha256/<前两位>/<完整哈希>.<ext>
```

相同图片只存一份。导入后数据库引用稳定媒体资产 ID，不引用包内路径，也不信任原设备的绝对路径。

## 7. “全量菜谱库”的强制边界

备份页面不提供菜谱多选；点击备份始终导出：

1. 所有 `draft`、`published`、`archived` 菜谱；
2. 回收站中的软删除菜谱；
3. 每道菜的全部主字段、食材、步骤、标签、分类关系、收藏状态、时间和版本字段；
4. 所有封面和配图；
5. 全部分类，包括空分类；
6. 当前确实存在的来源字段。

首版明确不包含：

- 冰箱批次和库存变化；
- 购物清单；
- 制作记录、最近浏览和运行中的烹饪会话/计时器；
- 导入任务、中间原文证据和临时草稿处理状态；
- 本地设置、Provider 配置、密钥、账号令牌、OCR 模型和缓存。

这些非菜谱数据以后作为独立可选数据集加入；不得修改或重新解释 `full-recipe-library` 的含义。

若数据库引用的任一必需图片在导出时不存在、不可读或哈希失败，本次“全量备份”不得显示成功。应删除未完成临时包并列出受影响菜谱，避免生成看似成功但无法完整恢复的备份。

空菜谱库也允许生成合法备份，计数为 0，便于验证格式和保存空分类结构。

## 8. 导出流水线

```text
用户选择“创建全量备份”
→ 读取一致性快照并统计数量/预估空间
→ 校验所有菜谱关系和媒体可读性
→ 流式写 categories / recipes NDJSON
→ 媒体按 SHA-256 去重后流式写入归档
→ 写入数据集摘要和 manifest
→ 重新校验归档结构与哈希
→ 通过系统文档创建器保存到用户选择的位置
→ 显示数量、大小、时间和文件位置
```

实现要求：

- 使用数据库只读事务或等价一致性快照，避免备份期间一半是旧值、一半是新值；
- 先写应用临时目录中的 `.partial` 文件，成功校验后再交付；
- 采用流式 ZIP/NDJSON，不把所有图片或菜谱加载到内存；
- 导出前预估临时空间和目标空间；
- 用户取消时停止读取并清理临时文件；
- Android 使用 Storage Access Framework，iOS 使用系统文档导出，不请求“全盘存储”或相册权限。

## 9. 导入模式

### 9.1 合并导入（默认）

适合在已有菜谱库中恢复或迁移：

- 相同 UUID 且规范化内容哈希相同：跳过；
- 相同 UUID 但内容不同：进入冲突列表，不静默覆盖；
- 不同 UUID 即使名称相同也不自动判定为同一道菜；
- 不同 UUID 但内容完全相同可标记“可能重复”，默认仍保留两份，用户可改为跳过；
- 分类同 ID 且一致时复用；同 ID 不一致时冲突；同名不同 ID 不静默合并，可在预检中映射；
- “两者都保留”时，为备份副本生成新 UUID，并在一个确定性映射表中重写分类、媒体和未来扩展引用。

每个冲突支持：

1. 保留当前版本；
2. 使用备份版本；
3. 两者都保留；
4. 对同类冲突应用到全部，但仍要显示影响数量。

### 9.2 替换当前菜谱库（高级恢复）

只替换第 7 节定义的菜谱库范围，不清除账号、密钥、OCR 模型、Provider 设置、冰箱或其他首版不在备份范围内的数据。

执行前必须：

1. 完成整个包的预检；
2. 显示将删除/替换的菜谱、回收站、分类和媒体数量；
3. 自动创建当前菜谱库的内部回滚备份；
4. 验证回滚备份可读；
5. 要求二次确认。

如果无法创建回滚备份，替换操作必须停止。导入失败时恢复原库；成功后保留最近一次回滚备份一段明确期限，并允许用户主动删除。

## 10. 导入预检与执行流水线

```text
系统文档选择器选择文件
→ 复制到应用 staging 目录
→ ZIP 安全检查
→ 读取 manifest 并进行版本/能力判断
→ 校验数据集和媒体 SHA-256
→ 逐行 Schema 校验
→ 按数据集 Migrator 链升级到当前导入 DTO
→ 建立引用图并验证分类/媒体引用
→ 与当前库比较，生成 ImportPlan
→ 展示新增、跳过、可能重复、冲突、缺失媒体和预计空间
→ 用户选择合并/替换和冲突策略
→ 媒体写入内容寻址存储
→ SQLite 事务应用计划
→ 完整性复核与提交标记
→ 清理 staging；失败则回滚数据库并清理本次新增的无引用媒体
```

预检必须只读。用户看到并确认 `ImportPlan` 前，不能改变当前菜谱库。

`ImportPlan` 至少包含：

- 包概要和兼容性结论；
- 新增、完全相同、可能重复、冲突、无法导入的数量；
- 每个冲突的当前/备份摘要；
- 媒体新增、复用、缺失和所需空间；
- 将被跳过的可选数据集或扩展；
- 替换模式的删除影响；
- 最终选定策略和可复现的 ID 映射。

## 11. 扩展架构

归档核心只负责容器、Manifest、安全、流、进度和提交协议。每种业务数据通过 `BackupDatasetAdapter` 概念契约接入：

- 数据集名称与 schemaVersion；
- 是否为必需数据集；
- 依赖的数据集；
- 流式导出记录；
- 逐行验证；
- 旧版本 Migrator 链；
- 生成导入计划与冲突；
- 在导入会话中应用计划；
- 输出计数、哈希和诊断。

建议模块边界：

```text
BackupCoordinator
├─ ArchiveReader / ArchiveWriter
├─ BackupManifestValidator
├─ DatasetRegistry
│  ├─ RecipeDatasetAdapter
│  ├─ CategoryDatasetAdapter
│  ├─ MediaDatasetAdapter
│  └─ future adapters...
├─ MigrationRegistry
├─ ImportPlanner
├─ ConflictResolver
├─ MediaAssetRepository
└─ ImportCommitCoordinator
```

未来新增库存数据时，只注册 `InventoryDatasetAdapter` 并在 Manifest 声明依赖，不修改菜谱数据集结构和归档读写核心。

### 11.1 版本兼容规则

- 旧数据集：必须按顺序执行 `v1 → v2 → ... → current` Migrator，不允许在 Repository 内散落版本判断。
- 新增可选字段：旧读取器可忽略，但导入结果必须提示是否有数据未保存。
- 未识别的可选数据集：允许用户在明确知情后跳过。
- 未识别的必需数据集、必需 Feature 或更高不兼容主版本：停止导入。
- 字段删除/语义改变：只能提升数据集 schemaVersion，并提供迁移规则。
- 枚举新增：不得默认映射成任意现有值；应迁移、保留未知值或阻止受影响记录。

### 11.2 扩展命名空间

业务插件或未来模块使用反向域名/稳定命名空间，例如：

```text
extensions/app.airecipe.nutrition/...
extensions/app.airecipe.household/...
```

扩展不得覆盖核心字段。若扩展是恢复菜谱完整语义所必需，必须进入 `requiredFeatures`；否则只能作为 `optionalFeatures`。

## 12. 数据库与文件系统原子性

SQLite 事务不能自动回滚已经写入的文件，因此需要“两阶段 + 清理账本”：

1. `staging`：所有包内媒体先在隔离目录解压并校验；
2. `prepare`：按哈希确认复用或复制到不可变内容寻址媒体库，记录本次新建对象；
3. `database commit`：单个 SQLite 事务写入菜谱、分类、关系和媒体引用；
4. `finalize`：写入导入会话完成标记并删除 staging；
5. `rollback`：事务失败时，删除本次新建且没有其他引用的媒体对象；启动时清理没有完成标记的过期会话。

为可靠实现该协议，建议在编码前新增稳定媒体资产契约，而不是继续让领域层只持有裸文件路径。至少需要：

- 稳定 `mediaAssetId`；
- SHA-256、MIME、字节大小、相对存储键；
- 引用计数或可查询引用关系；
- `pendingImportSessionId`/清理账本；
- 不可变文件写入和重复哈希复用。

在该契约完成前，`BACKUP-001` 只能是设计交付，不能宣称已经具备可靠恢复能力。

## 13. 安全与隐私

导入包视为不可信输入，必须防御：

- Zip Slip：拒绝绝对路径、盘符、`..` 和归档根目录外路径；
- Zip Bomb：限制压缩比、总解压大小、单文件大小和文件数；
- 媒体伪装：同时校验扩展名、MIME 和 magic bytes，并限制像素尺寸；
- JSON 资源消耗：限制单行大小、嵌套深度、字符串长度和记录数；
- 哈希不一致：任何必需文件失败都停止导入；
- 重复/大小写冲突路径：按规范化路径拒绝；
- 错误信息不得泄露设备绝对路径、账号 ID、Key 或包内敏感原文。

首版包可以是未加密本地文件，但导出完成页必须提示“备份包含菜谱、备注和图片，请妥善保管”。SHA-256 只提供完整性检查，不提供保密性或来源真实性。

格式预留 `encryption` 能力。未来密码备份应使用经过认证的现代加密方案（例如 Argon2id 派生密钥 + AES-256-GCM 的版本化加密信封），不得使用传统 ZIP 弱密码。加密能力一旦启用必须进入 `requiredFeatures`。

## 14. 性能与资源预算

实现验收时至少覆盖：

- 0、1、100、1,000 道菜谱；
- 大量图片、重复图片和单张大图；
- 导出/导入过程中取消；
- 临时空间不足和目标空间不足；
- App 被系统杀死后的 staging 清理；
- Android 与 iOS 系统文档选择器；
- 低内存设备上流式处理，不出现与总备份大小等量的内存峰值。

进度按可解释阶段展示，不只显示一个百分比：统计、校验、写数据、写媒体、校验归档；读取、预检、冲突、写媒体、写数据库、复核、回滚。

## 15. 稳定错误分类

建议使用稳定内部错误码并映射中文文案：

| 分类 | 示例 |
|---|---|
| `backup_source_incomplete` | 菜谱引用的图片不存在，无法生成全量备份 |
| `backup_space_insufficient` | 临时空间或目标空间不足 |
| `backup_cancelled` | 用户取消 |
| `backup_write_failed` | 系统文档写入失败 |
| `archive_invalid` | 不是受支持的备份包或结构损坏 |
| `archive_checksum_mismatch` | 文件损坏或被修改 |
| `archive_version_unsupported` | 备份来自当前应用无法读取的新主版本 |
| `archive_required_feature_unknown` | 当前应用不支持包内必需数据能力 |
| `archive_security_limit` | 文件数、大小、路径或压缩比触发安全限制 |
| `import_conflict_unresolved` | 仍有冲突未选择策略 |
| `import_space_insufficient` | 恢复所需空间不足 |
| `import_commit_failed` | 写入失败且已回滚 |
| `rollback_backup_failed` | 无法创建替换恢复所需的回滚备份 |

用户文案不展示数据库表名、堆栈或绝对路径。

## 16. 页面和入口建议

入口：

```text
我的 → 数据与存储 → 菜谱备份与恢复
```

页面分区：

1. **创建全量备份**：显示菜谱总数、回收站数、分类数、图片数和预计大小；明确“始终备份全部菜谱，不能只选部分”。

游客和登录用户页面相同；登录状态只可额外说明“本地备份独立于云同步”。

完整状态见 `design/flows/RECIPE_BACKUP_RESTORE_FLOW.md`。

## 17. 分阶段实施建议

方案走查通过后，再拆成独立任务：

1. **媒体与来源数据契约**：稳定媒体资产 ID、内容哈希、引用和来源元数据扩展；
2. **归档核心与全量导出**：Manifest、NDJSON、媒体去重、文档创建器、空间/取消；
3. **导入预检与合并**：安全检查、Migrator、ImportPlan、冲突 UI、原子提交；
4. **替换恢复与回滚**：内部回滚备份、二次确认、启动清理；
5. **跨平台与规模验收**：Android/iOS、大库、损坏包、未来版本和空间故障。

不得把这些合成一个无法单独验收的大任务。

## 18. 方案级验收标准

- 明确备份与 Markdown/PDF 分享导出的边界；
- 明确“全量”包含正式、草稿、归档、回收站、分类和媒体；
- 明确首版排除项和敏感数据；
- 格式与 SQLite schema 解耦；
- 数据集可独立版本化、迁移和扩展；
- 导入有只读预检、合并/替换模式和不静默覆盖的冲突规则；
- 说明 SQLite + 文件系统两阶段提交和失败回滚；
- 覆盖损坏包、未来版本、权限、空间、取消、大库、游客和登录状态；
- 明确当前媒体路径和来源契约是实现前置，不把设计表述为已实现。
