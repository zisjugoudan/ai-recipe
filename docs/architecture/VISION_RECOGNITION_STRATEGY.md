# 多模态 LLM 连接诊断与多图识谱方案

> 状态：P0-1/P0-2（诊断与融合）已实施进入 VERIFY；第 15 章多图多模态识别为已确认方向（ADR-0029），IMAGE-002 实施中  
> 日期：2026-08-05  
> 关联任务：`BUG-006`、`IMAGE-001`、`IMAGE-002`、`IMPORT-007`、`OCR-003`  
> 关联决策：`ADR-0027`、`ADR-0028`、`ADR-0029`

## 1. 问题结论

当前多模态配置的“测试连接”不是可靠的连接诊断。它把地址、鉴权、模型存在性、图片协议、视觉能力、首字节、完整响应和响应解析合并成一次黑盒请求，并对整个 `client.post(...).timeout(...)` 只设置一个总时限。只要在时限内没有拿到完整 `http.Response`，无论真实原因是网关排队、模型冷启动、流式响应未结束、图片协议不兼容、响应正文卡住还是服务端没有及时返回 4xx，最终都会被包装成“请求超时”。

因此本 Bug 的直接根因是**诊断分类错误**，不是已经证实的网络超时。此前改用表单当前配置和 1×1 PNG 只能排除旧配置复用与纯文本探测问题，不能解决黑盒请求和总超时误分类。

现有实现还存在四个结构性问题：

1. “测试连接”实际发送图片，产品名称与检测内容不一致。
2. 1×1 无语义 PNG 不能证明模型真正看到了图片，部分视觉服务还会拒绝或异常处理过小图片。
3. Transport 等待完整响应，无法区分“未连接”“无首字节”“正文未结束”和“已响应但解析失败”。
4. HTTP 400/408/413/415/422/504、SSE 未结束、客户端取消等情况没有独立、可操作的错误分类。

## 2. 目标与非目标

### 2.1 目标

- 不再把所有“未完成”显示为“链接超时”。
- 分开验证基础连接、图片能力和真实图片质量。
- 每次诊断都能说明失败阶段、已完成阶段、耗时、HTTP 状态和下一步建议。
- 把 OCR 与多模态 LLM 定义为不同证据生产者，在“自动”模式中融合结果，而不是互相替代。
- 任一路成功时保留成功证据，不因另一路失败丢弃可用结果。
- 所有错误、日志和诊断结果遵守密钥、图片、Prompt 与响应脱敏要求。

### 2.2 非目标

- 本方案不替低级工程师编写 Flutter/Dart 实现。
- 不承诺所有 OpenAI-compatible 中转服务都支持统一图片协议；不兼容时应准确报告协议差异。
- 不把多模态 LLM 当成高保真 OCR 的替代品。
- 不在普通日志保存 API Key、Authorization、完整图片、完整 Prompt 或完整模型响应。

## 3. 产品层：把一个按钮拆成三类测试

识图引擎的多模态配置区提供以下三个动作：

1. **检查基础连接**
   - 校验 URL、协议、鉴权和模型可用性。
   - 优先读取模型列表；服务不支持模型列表时发送 Provider 对应的最小请求。
   - 不以图片能力作为基础连接成功的前提。
   - 如果视觉专用模型拒绝纯文本，但已明确返回合法的“需要图片/不支持文本”错误，应显示“服务与鉴权已通过，文本能力未确认”，而不是连接失败。

2. **检查图片能力**
   - 使用应用内置的标准诊断图验证图片协议和模型是否真正看到了图片。
   - 返回结构化断言，而不是只要求回复 `OK`。

3. **用我的图片测试**
   - 用户主动选择一张真实图片。
   - 展示识别文本/视觉观察、模型、总耗时和质量提示。
   - 该测试用于判断实际效果，不替代基础连接和标准图片能力诊断。

也可以保留一个“诊断配置”总入口依次执行前两项，但结果卡必须逐项展示，不能只返回一个成功/失败状态。

### 3.1 结果卡示例

```text
配置格式       通过
服务可访问     通过 · 183 ms
鉴权           通过
模型           通过 · vision-model-x
请求已接收     通过 · HTTP 200
首字节         通过 · 1.8 s
图片能力       失败

原因：服务返回 HTTP 422，当前 OpenAI-compatible 图片字段不兼容。
建议：确认该服务支持 image_url data URL，或切换对应 Provider 协议。
诊断编号：本地随机 ID（不含 Key、URL 查询参数或图片内容）
```

## 4. 分阶段诊断状态机

一次诊断至少产生以下阶段记录：

| 阶段 | 说明 | 失败时的主要分类 |
|---|---|---|
| `config_validation` | URL、协议、模型、超时、Key 必填规则 | `invalid_config` |
| `endpoint_resolution` | URI 组合、DNS/主机解析 | `invalid_endpoint`、`dns_failed` |
| `connection_open` | TCP/TLS/HTTP 连接建立 | `connect_failed`、`tls_failed` |
| `authentication` | 服务明确接受或拒绝凭证 | `unauthorized`、`forbidden` |
| `model_validation` | 模型存在、可访问或模型列表不支持 | `model_not_found`、`model_list_unsupported` |
| `request_accepted` | 服务收到请求并返回 HTTP 头 | `bad_request`、`payload_too_large`、`unsupported_media_type` |
| `first_byte` | 收到首个响应正文数据 | `first_byte_deadline` |
| `body_complete` | 非流式 JSON 完整结束，或 SSE 收到终止标记 | `body_idle_deadline`、`stream_not_terminated` |
| `response_parse` | 响应符合 Provider Schema | `invalid_response`、`protocol_incompatible` |
| `image_assertion` | 标准图文字和红色方块断言通过 | `image_not_observed`、`vision_incorrect` |

每个阶段记录：

- `stage`
- `result`：`passed / failed / skipped / warning`
- `startedAt`
- `elapsedMs`
- `httpStatus`（如有）
- `providerErrorCode`（截断、脱敏）
- `messageKey`
- `nextAction`

UI 使用稳定中文 `messageKey` 映射，不直接显示任意服务端正文。服务端 message 只允许提取白名单字段，移除 URL、Key、Authorization、请求正文和可能的个人内容，并限制长度。

## 5. Transport 与时限契约

### 5.1 必须改用流式响应观察点

诊断 Transport 不应继续只等待完整 `http.Response`。工程实现需使用可观察响应头和数据块的流式请求，以便分别记录：

- 请求开始时间；
- 连接/响应头到达时间；
- 首字节时间；
- 最近一次正文数据时间；
- 正文完成或 SSE 终止时间。

生产多模态请求也应复用同一错误分类，否则设置页显示正常但真实导入仍可能只报“超时”。

### 5.2 时限分层

用户配置的“请求超时”是总上限，但内部至少拆分：

- 连接建立时限：建议默认 8 秒；
- 基础请求首字节时限：建议默认 15 秒；
- 图片请求首字节时限：建议默认 45 秒；
- 正文空闲时限：建议默认 15 秒，即已经开始返回后连续多久没有新数据；
- 总时限：沿用用户配置，建议默认 60 秒，上限不超过 120 秒。

达到某个时限时只报告对应阶段，例如“已连接但 45 秒内未收到首字节”，不能显示“链接超时”。HTTP 408/504 是 Provider/网关返回的超时，必须与客户端 `first_byte_deadline`、`body_idle_deadline` 分开。

模型冷启动不是自动无限延长的理由。诊断结果可以显示“疑似模型冷启动/排队”，并提供一次明确的“重新测试”，但不能静默重复消费额度。

### 5.3 非流式与 SSE

- OpenAI-compatible 请求显式发送 `stream: false`，并声明接受 JSON。
- 如果服务仍返回 `text/event-stream`，Adapter 应按 SSE 读取并以 `[DONE]` 或 Provider 明确终止事件结束。
- 已收到内容但流永不结束时，分类为 `stream_not_terminated` 或 `body_idle_deadline`，而不是连接超时。
- Gemini 使用对应非流式 endpoint；若返回的候选、parts 或 finish reason 不符合契约，分类为 `invalid_response`。

## 6. 标准图片能力探针

废弃 1×1 PNG。新增应用内置、离线、版本化的标准图，例如：

- 文件：`assets/diagnostics/vision_probe_v1.png`
- 尺寸：256×256；
- 白色背景；
- 黑色清晰文字：`AI RECIPE 314`；
- 右上角一个纯红色方块；
- 固定文件哈希，防止构建资产被误换。

固定提示词只要求完成探针，不做菜谱生成：

```text
只观察图片并返回 JSON，不要解释：
{"text":"图片中读到的英文字母和数字","redSquare":true或false}
```

通过条件：

```json
{"text":"AI RECIPE 314","redSquare":true}
```

可允许大小写、空白和常见 OCR 分隔差异，但文字和红色方块两个断言都必须通过。只返回 `OK`、空文本、通用描述或无法解析的 JSON 均不能判定图片能力通过。

## 7. 错误分类和用户动作

| 现象 | 分类 | 用户文案重点 | 建议动作 |
|---|---|---|---|
| URL/协议非法 | `invalid_config` | 配置格式错误 | 修正地址或协议 |
| DNS/TCP/TLS 失败 | `network_unreachable` | 未建立连接 | 检查地址、网络、证书 |
| 客户端取消 | `cancelled` | 测试已取消 | 不提示超时 |
| HTTP 400/422 | `request_incompatible` | 请求体、图片字段或模型能力不兼容 | 核对 Provider 协议和模型 |
| HTTP 401/403 | `unauthorized` | 鉴权失败/无权限 | 检查 Key 与模型权限 |
| HTTP 404 | `not_found` | endpoint 或模型不存在 | 检查 Base URL、路径、模型 |
| HTTP 405 | `method_not_allowed` | endpoint 类型错误 | 检查是否填到了网页或错误路径 |
| HTTP 408/504 | `provider_gateway_timeout` | 服务端/网关超时 | 查询服务状态或重试 |
| HTTP 409/423 | `model_busy` | 模型加载中或资源锁定 | 等待后重试 |
| HTTP 413 | `payload_too_large` | 图片或请求过大 | 压缩图片/降低上限 |
| HTTP 415 | `unsupported_media_type` | 图片 MIME 不支持 | 转为 JPEG/PNG |
| HTTP 429 | `rate_limited` | 限流或额度不足 | 等待/检查配额 |
| HTTP 5xx | `server_error` | 服务暂时不可用 | 稍后重试/切备用服务 |
| 有响应头、无首字节 | `first_byte_deadline` | 服务已接收但未开始返回 | 检查排队、冷启动、模型能力 |
| 已有正文、长时间无新数据 | `body_idle_deadline` | 响应中断或流未结束 | 检查流式兼容性 |
| HTTP 200 但 Schema 不符 | `invalid_response` | 响应协议不兼容 | 切换协议 Adapter |
| 标准图断言失败 | `image_not_observed` | 模型未正确读取图片 | 检查图片字段/视觉模型 |

## 8. OCR 与多模态 LLM 的职责边界

### 8.1 OCR

OCR 是**文字证据提取器**，负责：

- 尽量忠实地返回图片中文字；
- 返回文本块、坐标、顺序、语言和置信度；
- 保留原始文字，不擅自改写为菜谱；
- 适合菜单、截图、配料表、包装标签、字幕和步骤文字。

### 8.2 多模态 LLM

多模态 LLM 是**视觉语义观察器**，负责：

- 识别菜品、食材外观、烹饪动作、器具和步骤场景；
- 补充 OCR 看不到的非文字信息；
- 对版面、表格和图文关系进行语义说明；
- 输出“观察”和“不确定性”，不得静默覆盖 OCR 原文；
- 不得把画面推测伪装成作者明确给出的用量或时间。

### 8.3 结构化菜谱 LLM

结构化菜谱 LLM 只消费经过标注的证据：作者正文、OCR 原文、字幕/ASR、多模态观察和允许的模型推断。它负责合并、冲突标记和生成草稿，不负责伪造缺失事实。

## 9. 统一证据模型

每条证据至少包含：

- `evidenceId`
- `sourceAssetId / imageIndex`
- `sourceType`：`author_text / ocr / subtitle / asr / vision_observation / inference`
- `rawText` 或受控观察描述
- `bbox / order`（可用时）
- `confidence`
- `provider / model / promptVersion / schemaVersion`
- `elapsedMs`
- `privacyRoute`：`local / custom_cloud / managed_cloud`

证据优先级：

1. 作者明确正文、配料表和平台原始字幕；
2. 清晰 OCR 原文；
3. ASR 转写；
4. 多模态画面观察；
5. 模型推断。

当高优先级证据与低优先级证据冲突时，不静默覆盖：草稿字段标记低置信度，确认页展示冲突来源和原文/画面证据。多模态 LLM 可以指出“OCR 可能把 1 勺识别成 7 勺”，但最终仍要求用户确认。

## 10. 自动路由与降级

现有“自动：多模态失败后再 OCR”的串行替代策略改为**证据融合策略**。

### 10.1 模式语义

- **自动融合**：本地 OCR 可用时优先/并行运行；用户允许上传且多模态配置可用时，同时获取视觉语义；两路独立结算并合并证据。
- **仅本地 OCR**：只提取文字，不上传图片。
- **仅多模态 LLM**：只调用用户配置的视觉服务，明确提示图片会发往第三方 Provider。

### 10.2 按图片类型路由

| 图片类型 | 主路径 | 补充路径 |
|---|---|---|
| 菜谱截图、菜单、配料表、步骤文字 | OCR | 多模态补充版面/语义 |
| 实拍菜品、烹饪过程、食材照片 | 多模态 | OCR 提取包装/标签/字幕 |
| 图文混排 | OCR + 多模态 | 合并并标冲突 |
| 禁止上传/离线 | 本地 OCR | 无云端路径 |
| OCR 不可用但允许上传 | 多模态 | 提示缺少文字坐标/置信度 |
| 多模态不可用 | OCR | 有正文时继续结构化生成 |

单张图片的“自动融合”可以并行执行，减少总等待时间。链接包含多张图片时，为控制成本：先运行本地 OCR；多模态优先处理封面、步骤关键图、OCR 文本为空/低置信度或图像语义价值高的图片，并遵守单任务图片数和字节上限。

### 10.3 部分成功规则

- OCR 成功、多模态失败：保留 OCR 和正文，草稿可继续生成，显示“视觉补充未完成”。
- 多模态成功、OCR 失败：保留视觉观察，草稿可继续生成，显示“图片文字可能不完整”。
- 两者都成功：融合证据；冲突字段待确认。
- 两者都失败但有正文：基于正文继续。
- 两者都失败且无正文：进入截图重选、手动粘贴或手动创建，不生成空草稿。

## 11. 隐私、成本和日志

- 本地 OCR 明确标注“不上传图片”。
- 多模态调用前说明图片会发送到用户配置的第三方 Provider；首次使用或隐私策略变化时再次确认。
- 默认发送安全暂存后的图片字节，不把原始受限 URL交给第三方模型。
- 上传前移除 EXIF，限制格式、体积、像素、单任务图片数；支持“仅 Wi-Fi”和“禁止移动网络”。
- 取消后立即终止后续图片请求；已完成的本地 OCR 结果可以保留为当前任务证据。
- 普通日志只记录诊断阶段、耗时、状态码、脱敏错误码、Provider 类型和模型别名；不记录 Key、Authorization、完整 URL 查询参数、图片、完整 Prompt 或完整响应。
- 每次真实质量验收写入 `tests/ai-quality/AI_QUALITY_LOG.md`，记录 Provider/模型、Prompt/Schema 版本、字段准确性、人工修改数、耗时、失败阶段和降级路径。

## 13. 验收门槛

实施不能只验证“请求成功”，必须满足：

- 同一失败可准确区分未连接、无首字节、正文卡住、Provider 504、响应 Schema 错误和图片断言失败。
- 视觉专用模型不支持纯文本时，不误判为基础网络连接失败。
- 标准图必须证明模型读取到文字和红色方块。
- 取消不会显示超时。
- OCR 与多模态任一路失败时，另一路成功结果仍保留。
- 冲突字段在确认页可查看来源，不静默覆盖。
- 禁止上传时没有多模态网络请求。
- 诊断与质量日志不包含密钥、图片原文或完整敏感响应。

## 15. 多图多模态识别与多草稿（ADR-0029，IMAGE-002）

> 项目负责人 2026-08-05 决策：**放弃把本地 OCR 作为链接图片识别的自动路径**，
> 图片识别统一由多模态 LLM 完成；多模态只负责**忠实转录图片中的文字**，
> “每张图是独立菜谱还是多张图合成一个菜谱”由纯文本 LLM 判断后分组结构化。

### 15.1 职责划分（修订第 8 章）

- **多模态 LLM = 图片文字转录器**：对每张图片忠实提取其中所有文字（菜名、配料、
  步骤、用量），保留原文结构、标点和顺序；图片没有文字时输出“（图片没有文字）”。
  不翻译、不总结、不推测画面（不扮演“视觉观察器”）。证据标记为
  `sourceType=ocr`（多模态转录的文字与 OCR 原文同属文字证据），并保留
  `sourceMediaOrder` 用于按图分组。
- **纯文本 LLM（结构化菜谱）**：先判断多图关系（`independent`：每张图是一份完整
  菜谱；`combined`：多张图按顺序合成一份菜谱），再按分组各自结构化生成。
- **本地 OCR**：保留在“手动拍照/选图导入”路径作为回退——默认与链接导入一致，
  **多模态转录优先**，多模态未配置或不可用时回退本地 OCR（2026-08-07 修订，
  原为“本地 OCR 优先、失败回退多模态”）；链接导入的图片一律走多模态转录，不再
  自动启用本地 OCR。
- 修订 `ADR-0028` 中“自动融合/仅本地 OCR/仅多模态”三模式：识图方式改为
  **仅多模态（链接）** 与 **多模态优先→本地 OCR 回退（手动选图/拍照）**。

### 15.2 多图处理流程

1. 获取链接全部图片（沿用单任务图片数上限，默认 9 张；多图任务同样受字节上限约束）。
2. 逐张调用多模态模型转录文字，转录文本按 `sourceMediaOrder` 分组保存为独立证据。
3. 把“作者正文 + 每图转录文本（带图序标记）”交给纯文本 LLM 分组判断，返回：
   - `{"mode":"independent"}`：每张图转录文本分别是完整菜谱；
   - `{"mode":"combined","groups":[[0,1],[2],...]}`：支持按图分组合成（默认全部合成一份）。
4. 按分组把转录证据拆分为 N 份 `ImportContent`，逐份执行既有结构化生成（每份生成
   一个草稿、复用配图/封面与草稿保存逻辑）。
5. 产物：N 个菜谱草稿或 1 个菜谱草稿；导入任务关联全部草稿 ID，确认页逐份确认。

### 15.3 数据与契约变更

- `ImportRecipeDraftResult` 增加 `additionalRecipeIds`，支持一次导入产出多个草稿。
- `ImportTask` 增加多草稿关联（`additionalResultRecipeIds`，SQLite 新列 JSON 数组）；
  `needsReview` 任务可携带 1..N 个草稿；任务详情/确认页按多草稿列表逐个确认与保存。
- `ImportContent` 转录片段已具备 `sourceType` 与 `sourceMediaOrder`，可作为分组依据，
  无需新增字段；分组判断的 Prompt/Schema 版本随 `tests/ai-quality` 记录。

### 15.4 实施顺序（IMAGE-002）

1. 多模态识别提示词改为“忠实转录图片文字”，产物 `sourceType=ocr`。
2. `ImportRecipeDraftResult` / `ImportTask` 支持多草稿（含 SQLite 迁移与确认页切换）。
3. 新增分组判断（纯 LLM 一次轻量调用）与按组拆分、逐组结构化生成。
4. 手动选图/拍照导入：多模态优先 → 未配置/不可用回退本地 OCR（2026-08-07 修订，
   原为“OCR 优先 → 失败/未安装回退多模态”）。
5. 验收：真实多图链接（每图独立 vs 多图合成）、多草稿逐个确认/保存、成本上限与
   取消语义、多模态不可用时手动图回退本地 OCR。
