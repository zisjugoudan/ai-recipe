> 文档状态：草案

> 产品定位：将分散的菜谱内容转化为结构化个人食谱，并结合家中库存帮助用户决定“现在能做什么”、补齐缺失食材和减少浪费。

## 1. 产品概述

### 1.1 产品背景

用户经常在小红书、抖音等内容平台收藏菜谱，但这些内容通常存在以下问题：

- 菜谱分散在不同平台，难以统一管理。
- 视频内容较长，实际做菜时不方便反复拖动查看。
- 食材、用量、步骤隐藏在视频口播、字幕、图片或正文中。
- 原内容可能缺少明确用量、火候、时间或步骤顺序。
- 收藏内容可能失效、被删除或无法离线查看。

本应用通过导入内容链接，提取其中的文本、图片、字幕及语音信息，再利用 LLM 将内容整理为结构化食谱，帮助用户建立自己的数字菜谱库。

### 1.2 核心价值

1. **快速导入**：粘贴小红书或抖音链接，一键生成结构化食谱。
2. **统一管理**：将不同来源的菜谱归档到个人分类中。
3. **方便下厨**：食材、用量和步骤清晰展示，并提供烹饪模式。
4. **允许纠错**：AI 生成结果必须可编辑、可补充、可重新生成。
5. **持续沉淀**：收藏内容转化为真正属于用户的个人食谱资产。
6. **用好现有食材**：维护家中库存，根据已有和临期食材推荐本地菜谱，减少重复购买与食材浪费。

### 1.3 目标用户

- 经常在小红书、抖音寻找菜谱的人。
- 喜欢做饭，但不愿整理视频或图文菜谱的人。
- 需要为家庭规划日常饮食的人。
- 健身、减脂、控糖或有饮食限制的人。
- 希望建立个人菜谱库、美食笔记或家庭菜谱的人。

## 2. 产品目标与边界

### 2.1 第一阶段目标

第一阶段重点验证以下闭环：

> 粘贴链接 → 获取内容 → AI 解析 → 用户确认 → 保存菜谱 → 下厨查看

第一阶段闭环稳定后，P1 阶段增加：

> 家中食材 → 匹配本地菜谱 → 补齐缺失项 → 下厨 → 确认扣减库存

### 2.2 已确认的产品决策

- 产品采用**移动端优先、跨平台开发**，首要支持 iOS 和 Android。
- 核心菜谱数据采用 **Local-first（本地优先）** 设计，不登录也能完整使用本地菜谱库。
- 软件同时提供登录模式和游客模式，不强制用户注册后才能使用。
- 登录用户可以使用云端同步、云端备份和平台托管的 AI/OCR 服务。
- 游客不能使用平台托管的 AI 服务，也不能将数据保存到平台云端；但可以离线创建和恢复本地全量备份。
- 游客可以配置本地 LLM API、自有第三方 LLM API、本地 OCR 插件或自有云 OCR API。
- 登录后可以将游客时期的本地菜谱、分类、购物清单、冰箱库存批次和设置合并到账号。
- LLM、OCR 和后续 ASR 能力均采用供应商适配器设计，避免业务逻辑绑定单一平台。

### 2.3 平台范围

首版目标平台：

- iOS 手机和平板。
- Android 手机和平板。

后续可在复用业务层的基础上扩展：

- Web 管理端。
- Windows/macOS 桌面端。
- 微信小程序轻量入口。

跨平台不代表所有平台完全复用 UI；核心数据模型、业务逻辑、网络层和 AI/OCR 适配层应尽可能共享，各平台保留必要的系统能力适配。

## 3. 产品设计原则

1. **先生成，再确认**：AI 结果不能未经用户确认直接覆盖原数据。
2. **来源可追溯**：每份导入菜谱保留原始链接和来源平台。
3. **结构化优先**：食材、用量、步骤、时间、火候应使用独立字段。
4. **手动编辑永远可用**：链接解析失败时，用户仍可粘贴文字、上传截图或手动创建。
5. **适合厨房场景**：操作按钮大、步骤清晰、避免频繁返回和滚动。
6. **降低 AI 幻觉风险**：无法从原内容确认的信息应明确标记为“AI 推测”或“原内容未说明”。
7. **移动端优先**：主要使用场景是手机收藏和厨房查看。
8. **本地优先**：即使未登录或断网，用户仍可查看、创建和编辑本地菜谱。
9. **能力可替换**：LLM、OCR、ASR 和链接解析通过统一接口接入，不锁定单一服务商。
10. **隐私可选择**：用户可以明确决定图片、视频和菜谱文本是否允许发送到云端处理。

## 5.3 链接导入（浏览器内核抓取，通用网页）

### 5.3.1 用户流程

1. 用户复制链接（小红书、抖音或其他平台的网页链接）。
2. 打开应用，应用检测剪贴板中的链接。
3. 用户点击“立即导入”。
4. 应用在后台使用内置浏览器内核（Android WebView / iOS WKWebView）加载该网页，像真实浏览器一样执行页面脚本，不采用绕过平台风控的直连抓取。
5. 页面加载完成后，从网页 DOM 中提取标题、正文文本、图片、视频、作者和封面（文本与图片均来自网页真实内容，不是截图后识别）。
6. 对提取的图片执行 OCR 文本识别（本地 OCR 可用时）。
7. 将正文、OCR、字幕和语音文本合并为原始素材。
8. LLM 生成结构化菜谱。
9. 用户进入“导入确认页”进行检查和修改。
10. 用户选择分类后保存。

### 5.3.2 链接解析内容

系统应尽可能获取：

- 平台名称
- 原始分享链接
- 解析后的标准链接
- 内容标题
- 作者昵称
- 发布时间（能够获取时）
- 正文描述
- 标签或话题
- 封面图片
- 内容图片
- 视频文件或可访问的视频地址
- 平台字幕
- 音频转写文本

以上内容由内置浏览器内核（WebView/WKWebView）在用户设备上以真实浏览器方式加载页面后，从 DOM 与网络资源中提取：文本直接取自页面元素（标题、正文、`og:` 元数据、正文容器等），图片通过页面内的 `<img>` 或 JSON 数据中的地址收集，并由浏览器会话请求获得图片字节（与用户浏览器行为一致，不绕过平台访问控制）。后续其他平台的网页链接无需改造即可尝试抓取。

### 5.3.3 多模态内容提取

图片与视频素材必须按“证据生产—证据合并—结构化生成”处理，不把 OCR、多模态视觉理解和菜谱生成混成一次不可诊断的调用。

职责边界：

- OCR 负责忠实提取画面中的文字、阅读顺序、坐标、语言和置信度，不负责猜测未出现的食材或动作。
- 多模态 LLM 负责观察菜品、食材外观、烹饪动作、器具、步骤场景和图文关系；其输出属于视觉观察，不得伪装成 OCR 原文。
- 结构化菜谱 LLM 负责合并正文、OCR、ASR 和视觉观察，生成带来源证据的草稿，并标记冲突、低置信度和模型推断。

证据优先级：

1. 作者正文、明确配料表和平台原始字幕。
2. 清晰 OCR 原文。
3. 音频或视频 ASR。
4. 多模态视觉观察。
5. 模型推断。

当不同来源冲突时：

- 不静默覆盖，确认页显示冲突字段及每个候选值的来源。
- 优先采用更高等级且更明确的证据；无法判断时保持待确认。
- 用户可以查看正文、OCR、ASR 或视觉观察片段。
- AI 推断必须带提示标识，不得作为确定事实自动保存。

#### 图文内容的自动整合

“自动”模式不是“多模态失败后才做 OCR”的二选一回退，而是让 OCR 与多模态在权限、网络、能力和成本允许时独立执行，再合并成功证据：

- OCR 成功、多模态失败：保留 OCR，继续生成草稿并提示视觉观察缺失。
- 多模态成功、OCR 失败：保留视觉观察，继续生成草稿并提示文字提取缺失。
- 两路成功：合并证据；字段冲突进入确认页，不静默覆盖。
- 两路失败但存在正文或字幕：继续使用已有文本证据。
- 两路失败且没有其他证据：不生成空草稿，提供重选图片、粘贴正文和手动创建入口。
- “仅 OCR”和“仅多模态 LLM”严格只执行用户选择的识图路线。
- 用户禁止上传图片时不得发送多模态或云 OCR 网络请求，本地 OCR 仍可执行。
### 5.3.4 AI 结构化任务

LLM 需要完成：

- 判断内容是否属于菜谱。
- 提取菜名。
- 提取食材名称、用量和单位。
- 区分主料、辅料、腌料和酱汁。
- 按实际顺序整理操作步骤。
- 提取时间、温度和火候。
- 将口语化描述改写为清晰指令。
- 合并重复描述。
- 标记不确定信息。
- 生成简短菜品简介。
- 推荐分类和标签。
- 根据内容估算难度和总耗时。

### 5.3.5 AI 结果置信度

每个关键字段可包含置信度：

- 高：原内容明确出现。
- 中：结合多个来源可合理判断。
- 低：主要依赖 AI 推测。

低置信度字段在确认页突出显示，提醒用户核对。

### 5.3.6 导入确认页

确认页分为以下区域：

- 原内容预览
- 菜谱基础信息
- 食材列表
- 操作步骤
- AI 提示和待确认项
- 图片选择
- 分类与标签

主要操作：

- 保存菜谱
- 保存为草稿
- 重新解析
- 仅重新生成食材
- 仅重新生成步骤
- 查看原始文本
- 放弃导入

### 5.3.7 解析失败的降级方案

第三方平台链接可能因登录、反爬、内容删除、地区限制或接口变化而无法解析。浏览器内核抓取同样可能遇到：页面要求登录（小红书/抖音的帖子可能登录后才可见完整正文）、安全验证/验证码、页面本身无法加载、或网页内容为空。失败时按以下顺序提供方案：

1. 引导用户在系统分享菜单中选择“分享到本应用”。
2. 允许用户粘贴原帖正文。
3. 允许用户上传内容截图。
4. 允许用户上传已保存的视频。
5. 允许用户手动填写菜名后使用 AI 辅助整理。

不应只显示“解析失败”，必须告诉用户原因和下一步操作。

浏览器内核抓取失败时按原因分类提示：

1. 页面加载完成但内容为空（登录墙、需手动验证、或目标内容未渲染）：提示需要登录、平台正在验证或内容不可用，引导稍后重试或使用粘贴正文等降级方式，不直接透传平台英文错误。
2. 页面加载失败（网络错误、页面被拦截、超时）：提示网络或页面加载失败，允许重试或降级。
3. 提取到内容但缺少关键部分（如只有图片没有正文）：继续使用多模态流程（本地 OCR），必要时提示安装 OCR 模型或使用降级输入。
4. 正文提取成功但配图获取部分或全部失败：导入继续，草稿正常生成，按"配图部分失败"提示（可稍后手动补充），不得让整个导入失败为"网页加载超时"。

默认匿名导入仅处理无需登录的公开内容；应用不读取、不复用用户设备上浏览器（Chrome 等）的 Cookie 或登录态，也不在未登录情况下尝试绕过平台的登录墙与风控。后续如确需导入登录后才可见的内容，另行评估"应用内登录平台"方案（用户主动登录、明确 Cookie 保存范围、提供退出与清除入口），并在产品决策中单独确认。

### 5.3.8 导入任务状态

导入过程可能耗时，应显示明确状态：

- 等待解析
- 正在获取内容
- 正在识别图片文字
- 正在识别视频语音
- 正在生成菜谱
- 等待用户确认
- 已保存
- 失败

用户退出页面后，任务应在后台继续执行，并在完成后发送应用内通知。

首页存在未完成导入时，应显示持久化任务数量和“继续处理”入口。点击入口必须打开已经存在的导入任务，不得进入新建导入页，也不得再次调用任务创建接口或生成重复任务。当前版本按创建时间从新到旧继续处理：先打开最近创建的未完成任务；用户处理或退出后，首页重新读取剩余任务数量，可继续进入下一项。排队任务进入后继续执行，运行中断任务先恢复为可继续状态，待确认、失败任务分别进入确认或可操作的失败页面。

`failed` 是等待用户处理的未完成状态：页面必须保留真实错误、可用重试入口和人工降级入口。所有失败任务都提供“结束此导入”；点击期间显示“正在结束…”，结束成功后将原任务持久化为 `cancelled`。结束操作不删除原失败记录，不创建新任务，也不能通过未完成查询静默过滤 `failed` 来掩盖问题。`cancelled` 不计入首页未完成数量，强制停止并重启后仍应保持该结果。

### 5.3.9 待确认草稿重新生成

AI 生成的草稿不理想时，草稿确认页应提供“重新生成”：使用同一原文再次调用 AI 整理，避免用户放弃草稿后重新导入。

- 点击“重新生成”前必须二次确认，提示当前编辑会被替换。
- 重新生成期间按钮禁用并显示“正在重新生成…”，防止重复提交。
- 成功：新草稿替换旧草稿，任务保持“待确认”；旧草稿应被安全清理，不遗留孤立草稿。
- 失败：保留旧草稿和当前任务状态，显示稳定脱敏错误。
- 会话原文仅在本次会话内保留；App 重启后进入草稿确认页时，“重新生成”不可用并提示“原始内容已过期，请重新导入”。
- 重新生成不重新抓取链接、不重新执行 OCR/ASR；需要重新识别时走放弃草稿后重新导入。

## 5.8 冰箱与按食材推荐菜谱

冰箱为 P1 一级导航，游客和登录用户均可在本地离线使用。首版包含“库存”和“推荐”两个二级视图。冰箱 UI 采用轻拟物分区，而不是普通列表优先：顶部展示“我的冰箱”和临期提醒，主体按冷藏区、冷冻区、常温区和其他区组织食材。

### 5.8.1 库存批次

每个库存批次包含：

- 食材名称（必填，保存原始写法，例如“西红柿”“精瘦肉”）。
- 可选食材规格（渐进式语义食材系统，见下方说明）：基础食材、部位、肥瘦、形态、加工状态。全部可跳过，跳过保存为“规格未设置”。
- 数量，可为空。
- 单位，可为空。
- 分类。
- 存放位置：冷藏、冷冻、常温、其他。
- 购买日期，可为空。
- 到期日期，可为空。
- 备注。

同名食材允许存在多个批次。底层按批次存储，界面可以按食材名称聚合展示，但编辑、扣减和丢弃必须能定位到具体批次。

**渐进式规格录入**：录入时不强迫用户填写规格。第一步只输入食材名称，系统即时解析并给出可选规格候选（例如输入“猪肉”后给出“不确定 / 瘦肉 / 精瘦肉 / 五花肉 / 半肥半瘦 / 肥肉 / 肉末”），用户可跳过。之后推荐遇到具体规格要求时，再提示用户确认或补填。

库存首页按“冰箱层架 / 抽屉”视觉呈现区域：冷藏区强调日常高频食材，冷冻区强调长期保存和解冻提示，常温区承载米面粮油和无需冷藏食材，其他区用于用户不确定或自定义位置。每个区域可直接添加食材，空区域显示“把食材放进冷藏区”等生活化引导。

用户可以添加、编辑、删除、标记用完和标记丢弃。库存状态至少包括：正常、临期、已过期、未设置日期和数量未知。临期默认定义为到期日前 3 天，可在后续版本提供用户设置。

库存筛选至少包括：全部、临期、已过期、冷藏、冷冻、常温和其他。筛选不替代分区视图，分区视图是默认浏览方式。

**拖拽移动与冷冻动效**：食材支持长按后在同一区域排序或移动到其他区域。长按、拖拽开始、经过候选区域、无效释放、同区排序和非冷冻区域之间移动均不得触发冷冻/解冻颜色动画；候选区域只提供静态高亮。只有最终目标区域正式接收、库存移动保存成功且食材已显示在目标位置后，进入冷冻区才以二维独立小格逐个出现，离开冷冻区才按相反顺序逐格消失，且每次有效移动只播放一次。保存失败时恢复原位置、不播放成功动画；系统启用减少动态时直接切换最终视觉。详细交互规范以 `design/flows/FRIDGE_DRAG_AND_FROST_ANIMATION_HANDOFF.md` 为准。

### 5.8.2 本地菜谱推荐

首版推荐只读取本地正式菜谱；草稿和回收站菜谱不参与。匹配采用确定性离线规则，不依赖 LLM，也不要求登录或联网。

推荐不是默认把全部库存作为同等输入，而是先让用户从冰箱中选择本次想优先使用的食材。用户可以点选单个食材，也可以一键选择全部、临期食材或某个分区。已选食材代表本次推荐意图；未选择但冰箱已有的食材仍可在结果中标注为“冰箱已有，可补选 / 可用”。

示例：冰箱中有西红柿和鸡蛋；用户只选择西红柿时，系统可以推荐“西红柿炒鸡蛋”。如果鸡蛋也在冰箱中，卡片显示“已选命中：西红柿；冰箱已有：鸡蛋；缺失：无”；如果冰箱没有鸡蛋，则同一菜谱进入“缺 1 样”分组，显示“缺失：鸡蛋”。

**匹配采用“基础食材 + 属性规格 + 三值匹配”**（渐进式语义食材系统，决策见 `tracking/DECISIONS.md` ADR-0022）：

- 库存与菜谱食材都统一到“基础食材概念 + 可选属性”（部位、肥瘦、形态、加工状态），属性可未知。
- 匹配结果是三值之一：
  - **YES（确定满足）**：基础食材一致，且属性满足菜谱要求，或库存规格比菜谱要求更具体（例如库存“精瘦肉”可满足菜谱“猪肉”）。
  - **MAYBE（可能满足，需确认）**：基础食材一致但关键规格不明确或方向相反（例如库存“猪肉”面对菜谱“精瘦肉”；库存“肉末”面对菜谱“猪肉末”）。
  - **NO（明确不满足）**：基础食材冲突或属性明确冲突（例如“肥肉”面对“精瘦肉”，“牛肉”面对“猪肉”）。
- 匹配方向不对称：库存更具体、菜谱更宽泛时可自动匹配；库存更宽泛、菜谱更具体时只能进入“可能可以做”。
- **食材家族与模糊匹配（ADR-0023）**：为常见食材增加粗粒度家族（辣椒类 / 菌菇 / 鱼 / 叶菜 / 肉 / 奶酪 等）。基础概念不同但属于同一家族、且无明确属性冲突时，结果为 MAYBE（例如冰箱“辣椒”→菜谱“青椒”：同属辣椒类，具体品种/颜色/状态未知；冰箱“蘑菇”→菜谱“香菇”同理）。家族只表示共同归属，不代表互为别名，避免用别名污染词库。存在明确属性冲突（如“干辣椒”对“青椒”的新鲜状态冲突）→ NO。
- **菜谱食材要求强度（importance，ADR-0023）**：菜名中的食材默认为核心（core，缺少时明确计入缺失）；原文含“可选、没有可以不放、按个人口味”的食材为可选（optional，不计缺失）；其余默认为必需（required）。调味品按常备策略处理。

推荐分为：

1. **现在就能做**：主要必需食材均为 YES，且数量明确足够；数量未知时提示确认。
2. **可能可以做**：无明确冲突、无确定缺失，但存在 MAYBE（规格待确认）。卡片列出待确认食材与原因，例如“冰箱里有猪肉，但需要确认是否为精瘦肉”。
3. **缺 1 样**：确定缺少 1 项主要必需食材（MAYBE 不计为缺失）。
4. **缺 2 样**：确定缺少 2 项主要必需食材。
5. **优先清库存**：能够使用一个或多个临期食材，可作为横向筛选或结果标记，不与缺失数量冲突。
6. **可替代尝试**（MVP 仅标记，不默认混入前四组）：需要依赖菜谱记录的替代食材才能完成，必须提示可能影响风味。

缺失超过 2 样的菜谱默认不进入主推荐，可在“更多缺失 / 暂不优先”中收起展示。

推荐卡片展示：

- 已选命中食材、冰箱已有但未选择食材、缺失食材、规格待确认食材。
- 匹配食材数 / 主要必需食材总数。
- 使用到的临期食材。
- 匹配依据（例如“西红柿 → 番茄（同义词匹配）”“精瘦肉 → 猪肉（规格更具体，可满足）”）。
- 推荐原因、烹饪时间和难度。
- 查看详情、开始烹饪和“把缺失项加入购物清单”操作。

基础调味品可以标记为“常备”，不计入主要缺失数。同义词、上下位规格关系和单位换算由本地受控词典维护，未收录名称不自动命中并进入“待确认”。数量为空或单位无法换算时，不得宣称库存一定足够，统一提示“有该食材，数量是否足够需确认”。

默认排序优先级为：

1. 缺失食材更少。
2. 规格待确认（MAYBE）更少。
3. 使用临期食材更多。
4. 匹配比例更高。

**确认交互**：当 MAYBE 影响推荐分组时，卡片提供确认入口，用户可选择“仅本次视为可用”或“去修改库存规格”。用户的选择只作用于本次推荐或该批次规格，不直接改写全局词典。

### 5.8.3 根据库存生成新菜谱

后续提供独立的显式入口“用现有食材生成新菜谱”。只有存在可用 LLM Provider 时开放，结果进入可编辑草稿确认页，不与本地菜谱推荐混排，也不得自动保存为正式菜谱。

### 5.8.4 下厨后的库存扣减

用户完成烹饪后，系统根据菜谱用量和库存批次自动生成预计消耗清单。用户可以逐项确认、调整、换批次或取消；确认后才更新库存并记录变更，未确认不得扣减。

涉及同名多批次时，系统默认选择到期更早的批次，但提交前必须允许用户查看并修改目标批次。

### 5.8.5 首版非目标

- 高级“替换当前库”开始前必须创建并验证回滚备份；导入失败或取消时不得留下半完成数据库或孤立媒体。

## 5.13 用户账户、游客模式与数据同步

### 5.13.1 登录方式

建议支持：

- 手机号验证码。
- 微信登录。
- Apple 登录。
- 游客模式。

账号体系与本地设备身份分离：即使未登录，应用也要创建匿名的本地设备身份，用于管理本地数据、导入任务和插件配置，但该身份不能用于云端跨设备同步。

### 5.13.2 游客模式

游客模式不是试用页面，而是一种完整的本地使用方式：

- 无需注册即可创建、编辑、删除和搜索本地菜谱。
- 可以使用分类、标签、收藏、烹饪模式、计时器和购物清单。
- 可以导入小红书、抖音链接，也可以上传截图、视频或粘贴文本。
- 可以配置自定义 LLM API：选择协议后填写 API 地址和 Key；地址可以是本地服务或第三方云服务。
- 可以安装和使用本地 OCR 插件，或配置用户自己的云 OCR API。
- 本地菜谱数量原则上不做人为限制，仅受设备存储空间影响。
- 无法使用平台账号对应的云端同步、云端备份和跨设备自动恢复，但仍可离线创建和恢复本地全量备份文件。
- 无法使用由平台承担费用的托管 AI、托管 OCR 或托管 ASR 服务。
- 清除应用数据或卸载应用前，应提示用户导出备份或登录同步。

### 5.13.3 登录模式

登录用户在保留全部本地能力的基础上增加：

- 云端菜谱、分类、标签、购物清单和制作记录同步。
- 多设备数据恢复。
- 平台托管的 LLM、OCR 和 ASR 服务。
- 云端导入任务和后台处理。
- 服务端配额、订阅或积分能力。
- 家庭共享、只读分享链接等依赖账号的能力。

登录不应强制用户使用平台托管 AI。登录用户仍然可以选择本地模型或自有 API，并可针对不同任务分别配置服务来源。

### 5.13.4 游客与登录能力矩阵

| 功能 | 游客 | 登录用户 |
|---|---|---|
| 本地创建和编辑菜谱 | 支持 | 支持 |
| 分类、收藏、搜索、购物清单 | 支持 | 支持 |
| 链接、文本、截图和视频导入 | 支持 | 支持 |
| 自定义 LLM API（本地或云端地址） | 支持 | 支持 |
| 本地 OCR 插件 | 支持 | 支持 |
| 用户自有云 OCR API | 支持 | 支持 |
| 平台托管 AI/OCR/ASR | 不支持 | 按账号配额支持 |
| 本地内容导出、全量菜谱备份与恢复 | 支持 | 支持 |
| 平台云端同步 | 不支持 | 支持 |
| 多设备恢复 | 不支持 | 支持 |
| 家庭共享 | 不支持 | 后续支持 |

说明：用户自有 API 指用户自行提供服务地址和密钥，请求由客户端直接发送到对应服务商，不消耗平台托管 AI 配额。

### 5.13.5 游客登录后的数据合并

用户从游客模式登录时，提供以下选择：

1. **合并到云端**：本地数据与账号已有数据合并。
2. **仅保留本机**：登录账号，但暂不上传本地菜谱。
3. **使用云端数据**：保留本地数据备份后，以云端数据作为当前库。

合并规则：

- 菜谱使用稳定 UUID，避免仅以名称判断重复。
- 同一来源链接的菜谱提示用户选择合并、保留两份或覆盖。
- 分类同名时默认合并，用户可在导入前预览。
- 冲突数据不能静默覆盖。
- API 密钥默认不上传云端。

### 5.13.6 数据同步

- 本地数据库是移动端的主要读取来源，云端在后台进行增量同步。
- 所有可同步实体包含 `id`、`createdAt`、`updatedAt`、`deletedAt` 和 `syncVersion`。
- 自动保存草稿。
- 支持离线编辑，联网后上传变更。
- 编辑冲突时可按字段合并；无法自动合并时保留两个版本并提示用户。
- 删除操作使用软删除记录，防止离线设备将已删除内容重新上传。
- 云同步、本地全量备份与人类可读内容导出是三个独立能力：同步使用增量实体，备份使用版本化归档，Markdown/PDF/图片仅用于阅读和分享。
- 用户退出账号时可选择保留本机副本或清除账号数据。

## 5.15 AI 与 OCR 服务配置

### 5.15.1 服务来源选择

LLM 提供两类来源：

1. **平台托管服务**：由本产品服务端统一调用，仅登录用户可使用。
2. **自定义 API**：游客和登录用户均可选择协议，填写 API 地址和 Key，由客户端直接调用。地址可以是本地服务、局域网服务、自建服务器或第三方云服务，产品不把这些网络位置拆分成不同连接模式。

OCR 仍可选择本地插件、用户自有云 OCR 或登录后的平台托管 OCR。

用户可为不同任务选择不同服务，例如：

- 菜谱结构化使用本地模型。
- 图片理解使用支持视觉能力的云模型。
- 普通 OCR 使用离线插件。
- 扫描复杂菜单时临时使用云 OCR。

### 5.15.2 LLM 供应商配置

每个 LLM 配置项的核心输入为：

- 配置名称。
- 接口协议，例如 OpenAI-compatible 或 Gemini。
- API Base URL。
- API Key，本地无鉴权接口可为空。
- 模型名称，优先从接口读取，不支持时手动填写。

其余高级配置包括：
- 请求超时时间。
- 最大输出长度。
- 温度等生成参数。
- 是否支持图片输入。
- 是否支持 JSON Schema 或结构化输出。
- 是否允许移动网络调用。
- 是否为默认配置。

首版建议支持的协议适配器：

```text
LLMProvider
├── ManagedCloudProvider        平台托管服务
├── OpenAICompatibleProvider    OpenAI 及兼容接口，本地/云端均可
├── GeminiProvider              Gemini 原生内容协议
└── FutureProtocolAdapters      Anthropic 等后续协议
```

其中 OpenAI-compatible 接口覆盖大量本地和云端服务；Gemini 使用独立请求路径、鉴权 Header 和响应结构。页面只收集协议、API 地址、Key 和模型，差异全部由 Adapter 处理。详细契约见 [`docs/architecture/LOCAL_LLM_NETWORK_SECURITY.md`](../architecture/LOCAL_LLM_NETWORK_SECURITY.md)。

### 5.15.3 模型配置检测

多模态配置不得用一次黑盒图片请求同时代表“地址、鉴权、模型、图片协议和识图质量都正常”。设置页提供三类独立测试：

1. **检查基础连接**：校验配置格式、服务可达性、鉴权和模型是否存在；优先读取模型列表，不支持时使用 Provider 对应的最小请求。视觉专用模型明确拒绝纯文本时，显示“服务与鉴权已通过，文本能力未确认”，不误报网络超时。
2. **检查图片能力**：发送内置 256×256 标准图（白底、黑字“AI RECIPE 314”、红色方块），要求返回固定 JSON；只有文字断言与红色方块断言同时通过，才判定视觉链路成功。1×1 无语义图片不得作为能力证明。
3. **用我的图片测试**：用户主动选择真实图片，展示识别文本或视觉观察、模型、耗时和质量提示，用于评估真实效果。

诊断至少按以下阶段记录结果与耗时：

- `config_validation`
- `endpoint_resolution`
- `connection_open`
- `authentication`
- `model_validation`
- `request_accepted`
- `first_byte`
- `body_complete`
- `response_parse`
- `image_assertion`

每个阶段返回 `result`、`elapsedMs`、`httpStatus`、脱敏 Provider 错误码、中文 `messageKey` 和 `nextAction`。错误至少区分：URL/协议错误、DNS/TCP/TLS/连接失败、401/403、404/405、400/422 图片协议不兼容、413、415、429、5xx、HTTP 408/504、已连接但无首字节、已有正文但流未结束、SSE 未终止、响应 Schema 错误和客户端取消。客户端取消不得显示为超时。

测试失败时保留用户填写内容，但不能自动设为默认配置。日志和诊断结果不得包含 Key、Authorization、完整图片、完整 Prompt、完整响应或带敏感查询参数的 URL。
### 5.15.4 AI 任务路由

应用至少区分以下任务：

- `recipe_parse`：将已有证据整理为结构化菜谱。
- `recipe_chat`：围绕菜谱提问。
- `recipe_rewrite`：调整份量、设备或口味。
- `ocr_extract`：忠实提取图片文字、坐标、顺序、语言和置信度。
- `vision_extract`：理解菜品、食材、动作、器具、步骤场景和图文关系。
- `evidence_merge`：按来源和优先级合并正文、OCR、ASR 与视觉观察，输出冲突和低置信度字段。
- `translation`：菜谱翻译。

每种任务可以指定不同的模型配置，并支持以下路由策略：

1. 首选服务、失败重试次数和备用服务。
2. 是否允许从本地服务降级到用户自有云服务。
3. 是否允许上传图片或完整原文。
4. 图片数量、单图大小、并发数、总耗时和费用上限。
5. 取消后停止后续请求，不把取消包装成超时或失败重试。
6. 每个证据生产者独立结算；任一路成功不得因另一路失败而丢弃。

自动识图采用“独立执行 + 部分成功 + 证据合并”，不采用“多模态优先、失败后 OCR”的串行二选一语义。游客不能将备用服务设置为平台托管服务。
### 5.15.5 OCR 插件系统

OCR 采用插件化设计，插件包负责具体识别能力，主应用负责文件选择、图像预处理、任务调度和标准化输出。

本地 OCR 插件可按语言或能力下载，例如：

- 简体中文通用识别。
- 中英文混合识别。
- 手写文字识别。
- 表格与配料表识别。
- 轻量快速模型。
- 高精度大模型。

插件管理功能包括：

- 浏览可用插件。
- 查看版本、体积、支持语言和设备要求。
- 下载、暂停、继续、更新和删除。
- 下载文件哈希校验和签名校验。
- 显示占用空间。
- 设置默认插件。
- 插件不可用时切换备用 OCR 服务。

### 5.15.6 OCR 与视觉证据统一接口

OCR 与多模态视觉理解是两套独立契约：

```text
OCRProvider
├── LocalPluginProvider
│   ├── ChineseGeneralPlugin
│   └── FutureOCRPlugins
├── ManagedCloudOCRProvider
└── CustomCloudOCRProvider

VisionEvidenceProvider
├── OpenAICompatibleVisionProvider
├── GeminiVisionProvider
├── ManagedCloudVisionProvider
└── FutureVisionProtocolAdapters
```

OCR 统一输入：单张或多张图片、语言提示、识别区域、是否保留坐标、是否执行方向检测和图片增强。

OCR 统一输出：

- 完整原文。
- 文本块、阅读顺序和坐标。
- 每个文本块置信度。
- 识别语言、Provider/插件名称、模型版本、耗时和稳定错误。

视觉证据统一输入：单张或多张图片、任务目标、允许观察的字段、图片 MIME/尺寸信息、结构化输出 Schema 和取消信号。

视觉证据统一输出：

- 可见菜品、食材外观、动作、器具、步骤场景和图文关系。
- 每条观察的来源图片、置信度和是否为推断。
- Provider、模型、Prompt/Schema 版本、耗时和稳定错误。

两套结果统一转换为带 `sourceType`、`sourceId`、`fieldPath`、`value`、`confidence`、`evidenceText` 和 `inferred` 的证据项，再交给 `evidence_merge`；不得把视觉描述写入 OCR 原文，也不得把 OCR 文本伪装为模型视觉观察。
### 5.15.7 OCR / 多模态路由、隐私与成本

OCR 默认推荐顺序：

1. 已安装且支持当前语言的本地 OCR 插件。
2. 用户配置的自有云 OCR。
3. 登录用户可选择的平台托管 OCR。

多模态视觉理解独立选择 Provider，不作为 OCR Provider 的子类型。自动模式可以同时运行 OCR 与多模态，但必须满足用户上传许可、网络策略和任务预算。

隐私与成本设置包括：

- 仅本地处理，禁止上传图片；开启后云 OCR 和多模态请求均不得发送。
- 分别控制 Wi-Fi 和移动网络是否允许云端识图。
- 上传前去除 EXIF 和无关元数据，并在可能时裁剪无关区域。
- 明确告知实际接收图片的第三方 Provider、模型和数据用途。
- 任务完成后删除应用控制范围内的临时文件；第三方保留策略需在配置页说明，不能伪称应用可以代替第三方删除。
- 设置单图大小、图片数量、并发数、总调用次数、总耗时和费用上限。
- 超出预算时保留已成功的 OCR/视觉证据，停止未开始或可取消的请求，并提示用户选择继续、降级或手动录入。
- 普通日志不保存图片、完整 OCR 原文、完整视觉响应、Key、Authorization 或完整 Prompt；真实质量样本仅按项目测试规程进入受控 AI 质量日志。
### 5.15.8 密钥与配置安全

- API Key 使用 iOS Keychain、Android Keystore 等系统安全存储。
- 密钥不得写入普通数据库、日志、崩溃报告或导出的 Markdown。
- API Key 默认不参与云同步。
- 用户主动开启密钥同步时，应使用端到端加密；首版可以不提供该功能。
- HTTP 本地接口仅建议用于 `localhost` 或可信局域网，并向用户提示明文传输风险。
- 支持一键删除所有自定义模型和 OCR 凭证。

## 9. AI 输出结构建议

建议让 LLM 输出严格 JSON，再由前端转换为可编辑表单。

```json
{
  "isRecipe": true,
  "title": "番茄炒蛋",
  "description": "酸甜下饭的家常快手菜",
  "servings": 2,
  "prepTimeMinutes": 10,
  "cookTimeMinutes": 8,
  "difficulty": "简单",
  "categories": ["家常菜", "快手菜"],
  "tags": ["下饭", "新手友好"],
  "ingredients": [
    {
      "group": "主料",
      "name": "番茄",
      "quantity": 2,
      "unit": "个",
      "preparation": "切块",
      "optional": false,
      "confidence": "high",
      "evidence": "正文明确提到"
    }
  ],
  "steps": [
    {
      "stepNumber": 1,
      "description": "鸡蛋打散，番茄切块。",
      "durationSeconds": null,
      "temperature": null,
      "heatLevel": null,
      "tips": [],
      "confidence": "high"
    }
  ],
  "warnings": [],
  "uncertainFields": [],
  "sourceSummary": "根据正文、字幕和语音内容整理"
}
```

### 9.1 AI 生成规则

- 不要凭空补充精确用量。
- 原文只写“适量”时，应保留“适量”。
- 无法确定火候时填写空值，不强行生成。
- 推测内容必须写入 `uncertainFields`。
- 食材必须去重，但不同用途的同种食材可分别保留。
- 步骤必须按执行顺序排列。
- 不得改变原菜谱的核心做法。
- 如果内容不是菜谱，应返回 `isRecipe: false` 并说明原因。

## 11. 异常情况与处理规则

### 11.1 链接无效

提示内容：

- 未识别到有效链接。
- 链接可能已过期或复制不完整。
- 建议重新从平台的“分享”功能复制链接。

### 11.2 内容已删除或仅好友可见

- 告知用户应用无法访问内容。
- 提供上传截图、视频或粘贴正文入口。

### 11.3 内容不是菜谱

- AI 判断后提示“未发现完整菜谱内容”。
- 允许用户继续以笔记形式保存。
- 允许用户手动补充菜名、食材和步骤。

### 11.4 视频无字幕且语音不清晰

- 显示已识别出的原始文本。
- 标记低置信度段落。
- 支持重新上传清晰版本。
- 允许用户手动修改。

### 11.5 用量缺失

- 不自动编造精确数值。
- 显示“原内容未说明”。
- 用户可点击“请 AI 给出参考用量”，该结果标记为估算。

### 11.6 重复导入

检测依据：

- 标准化链接相同。
- 平台内容 ID 相同。
- 标题和作者高度相似。

发现重复时提供：

- 查看已有菜谱。
- 覆盖更新。
- 保存为新菜谱。
- 取消导入。

### 11.7 导入任务中断

- 自动保存任务状态。
- 排队或运行中的导入必须始终提供可点击的取消入口；AI 请求正在执行时不能因为全局加载状态而禁用取消。
- 取消请求提交期间短暂禁用重复点击，并显示明确的取消中反馈。
- 持久化取消优先于后到的 AI 成功、Schema 错误、网络错误或未知异常；取消后不得遗留未关联草稿。
- 网络恢复后允许重试。
- 可重试的失败保留“重新解析”；不可重试的失败仍保留真实错误和人工降级入口。
- 所有失败任务都提供“结束此导入”；提交期间显示“正在结束…”，成功后将原任务持久化为 `cancelled`，并从首页未完成数量中移除。
- 主动结束失败任务不得删除失败记录、生成重复任务或静默过滤 `failed`；强制停止并重启后不得重新计入未完成。
- 重试时复用已经成功完成的 OCR 或转写结果，避免重复消耗。

---

### 11.8 库存名称、数量或单位无法判断

- 库存存在同名或相近名称时，不静默合并到错误食材。
- 数量为空或单位无法换算时，推荐仍可显示名称匹配，但必须标记“有该食材，数量是否足够需确认”。
- 库存扣减无法确定批次或数量时，保持原库存不变并要求用户确认。
- 已过期批次默认不计入可用食材，用户仍可查看和处理。

## 12. 非功能需求

### 12.1 性能

- 首页首屏应快速展示本地缓存内容。
- 普通图文导入应尽快给出处理进度。
- 视频导入时间较长时必须后台执行。
- 图片使用缩略图和懒加载。

### 12.2 稳定性

- 导入、OCR、语音识别和 LLM 生成拆分为独立任务。
- 每个任务支持重试和错误记录。
- LLM 输出必须经过 JSON Schema 校验。
- 保存菜谱时使用事务，避免只保存了一半数据。

### 12.3 安全与隐私

- 登录凭证安全存储。
- 用户私有菜谱默认不可公开访问。
- 提供账号注销和数据删除能力。
- 上传的视频、图片和文本需说明用途及保存期限。
- 敏感数据传输使用 HTTPS。
- 日志中不记录完整登录凭证和不必要的个人内容。

### 12.4 可访问性

- 支持系统字体缩放。
- 关键按钮有足够点击区域。
- 颜色不能作为唯一状态提示。
- 烹饪模式支持高对比度。
- 图片提供可选说明文本。

### 12.5 国际化

首版以简体中文为主，但数据结构应预留：

- 多语言菜名和步骤。
- 公制与英制单位。
- 温度单位摄氏度与华氏度。
- 不同地区常用食材名称映射。

### 12.6 跨平台一致性

- iOS 与 Android 共用核心业务逻辑和数据结构。
- 菜谱、分类、导入任务和 AI/OCR 配置在两个平台上的字段含义保持一致。
- 系统分享、文件选择、通知、后台任务、安全存储和网络权限使用平台适配层实现。
- 同一功能在不同平台允许采用符合平台习惯的交互，不要求像素级完全一致。
- 同一 `.airecipe-backup` 文件必须能在受支持版本的 iOS 与 Android 之间创建、预检并恢复；平台文件选择器差异不能改变归档语义。
- 每次发布必须覆盖主流 iOS/Android 真机测试。

### 12.7 离线能力

离线时必须可用：

- 查看已缓存菜谱和图片。
- 新建、编辑和删除本地菜谱。
- 分类、收藏、购物清单和烹饪模式。
- 添加、编辑、筛选和标记本地冰箱库存批次。
- 根据本地库存匹配本地正式菜谱，并把缺失项加入本地购物清单。
- 已安装本地 OCR 插件。
- 可访问的本机或局域网 LLM API。

离线时不可用或受限：

- 新的第三方平台链接解析。
- 平台托管 AI/OCR/ASR。
- 公网自有 API。
- 云同步和多人共享。

### 12.8 插件兼容性与资源控制

- 插件清单必须声明最低应用版本、目标系统、CPU 架构、模型大小和所需内存。
- 下载前显示移动数据消耗和本地存储占用。
- 低内存设备应拒绝加载不兼容模型，避免应用崩溃。
- OCR 插件运行在受控接口内，不允许任意访问账号凭证和其他菜谱数据。
- 插件升级失败时保留上一可用版本。

## 13. 第三方平台与合规注意事项

链接导入功能需要重点考虑第三方平台规则及内容版权：

- 优先处理用户主动提供的单条分享链接。
- 避免未经授权的大规模抓取和批量搬运。
- 保留原作者、来源平台和原始链接。
- 分享或公开菜谱时明确来源。
- 不默认公开用户导入的第三方内容。
- 对图片、视频等原始媒体设置合理缓存期限。
- 如果无法合法、稳定地保存原视频，可只保存用户选择的封面、关键帧和结构化文字。
- 平台解析方式可能随平台策略变化，应设计独立的解析适配层。
- 上线前应根据实际运营地区咨询合规、隐私和版权专业意见。

## 14. 技术架构建议

### 14.1 跨平台客户端

移动端统一采用 **Flutter**，架构使用“跨平台 UI + 原生能力桥接 + 本地优先数据层”。框架选型已经确定，不再进行 Flutter/React Native 二选一；正式业务开发前仍需通过 `SPK-001` 验证以下关键能力，避免将资料可行误当成真机可行：

- 系统分享扩展和剪贴板读取。
- 大文件上传及断点续传。
- 后台导入任务和本地通知。
- SQLite 数据库与全文搜索。
- iOS Keychain 和 Android Keystore。
- OCR 原生插件或模型运行时接入。
- 手机访问本机、局域网和 HTTPS API 的网络策略。

客户端模块建议：

```text
MobileApp
├── Presentation
│   ├── RecipeLibrary
│   ├── RecipeEditor
│   ├── ImportReview
│   ├── CookingMode
│   ├── ShoppingList
│   └── Settings
├── Application
│   ├── RecipeUseCases
│   ├── ImportPipeline
│   ├── AIRouter
│   ├── OCRRouter
│   └── SyncEngine
├── Domain
│   ├── RecipeModels
│   ├── ProviderContracts
│   └── ValidationRules
└── Infrastructure
    ├── LocalDatabase
    ├── SecureStorage
    ├── NetworkClient
    ├── NativeBridges
    └── ProviderAdapters
```

### 14.2 本地数据层

- 使用 SQLite 或同等级嵌入式数据库保存结构化数据。
- 菜谱、食材、步骤、分类和标签使用关系结构，不只保存为一段 JSON。
- LLM 原始响应、导入中间结果等可使用 JSON 字段保存。
- 图片和视频使用文件系统保存，数据库只保存资源标识、路径和元数据。
- 搜索可使用 SQLite FTS 或独立本地全文索引。
- 数据库迁移必须版本化并支持失败回滚。
- 云同步是本地数据库之上的能力，不能成为读取菜谱的前置条件。

### 14.3 服务端

- 用户与鉴权服务。
- 菜谱同步服务。
- 分类与标签同步服务。
- 导入任务服务。
- 平台链接解析适配层。
- 平台托管 OCR 服务。
- 视频音频处理服务。
- 平台托管 ASR 服务。
- 平台托管 LLM 网关。
- 文件存储服务。
- 搜索服务。
- 通知服务。
- 配额、计费和使用记录服务。

服务端托管 AI 网关负责密钥隔离、供应商路由、限流、配额、审计和错误归一化，但不应阻止客户端使用本地或自有 API。

### 14.4 链接解析适配层

建议每个平台使用独立适配器：

```text
LinkImportService
├── XiaohongshuAdapter
├── DouyinAdapter
├── GenericWebAdapter
└── ManualUploadAdapter
```

统一输出标准内容对象，避免后续业务直接依赖某个平台的返回结构。游客可以使用链接导入；如解析过程需要临时经过服务端，原始媒体和提取结果应设置短期生命周期，不作为游客云端数据长期保存。

### 14.5 Provider 抽象

业务层不能直接调用某个供应商 SDK，而应调用统一接口：

```text
RecipeImportUseCase
├── ContentExtractor
├── OCRProvider
├── ASRProvider
├── LLMProvider
└── RecipeSchemaValidator
```

Provider 需要返回统一错误类型：

- `AUTH_ERROR`
- `NETWORK_ERROR`
- `RATE_LIMITED`
- `QUOTA_EXCEEDED`
- `MODEL_NOT_FOUND`
- `UNSUPPORTED_CAPABILITY`
- `INVALID_RESPONSE`
- `CONTENT_TOO_LARGE`
- `CANCELLED`

统一错误便于客户端提供明确的解决方案和自动降级。

### 14.6 LLM 接口建议

核心接口至少包括：

```text
listModels()
testConnection()
generateText(request)
generateStructured(request, schema)
analyzeImages(request)
getCapabilities()
cancel(requestId)
```

`LLMRequest` 应包含：

- systemPrompt 和 userPrompt。
- 图片输入引用。
- JSON Schema。
- 超时、重试和取消信号。
- 任务类型。
- 隐私级别。

Provider 返回值除了文本外，还应包含模型、耗时、Token 用量、供应商请求 ID 和结构化解析错误。

### 14.7 OCR 插件包建议

每个 OCR 插件包含标准 Manifest：

```json
{
  "id": "ocr.zh.general",
  "name": "简体中文通用 OCR",
  "version": "1.0.0",
  "manifestVersion": 1,
  "platforms": ["ios", "android"],
  "architectures": ["arm64"],
  "languages": ["zh-Hans", "en"],
  "capabilities": ["text", "boundingBoxes", "orientation"],
  "minAppVersion": "0.1.0",
  "sizeBytes": 0,
  "sha256": "",
  "entryType": "native-runtime"
}
```

首版本地 OCR 首选 **PaddleOCR PP-OCRv5 mobile + ONNX Runtime Mobile**，通过 Flutter federated plugin 封装为统一 `OCRProvider`；模型以带 Manifest 和 SHA-256 校验的资源包按需下载。该方案仍需通过 `SPK-002` 完成 Android/iOS 真机准确率、速度、内存、包体积和模型下载验证；若不可接受，可降级评估系统 OCR 或 Google ML Kit。详细架构见 [`docs/architecture/OCR_PLUGIN.md`](../architecture/OCR_PLUGIN.md)。

首版的“插件”主要指受应用控制的识别引擎和模型包，不建议开放任意第三方可执行代码。后续如开放插件市场，应增加签名、沙箱、权限声明和审核机制。

### 14.8 AI/OCR 处理流水线

```text
输入链接、文本、图片或视频
→ 内容抓取或本地读取
→ 媒体预处理
→ 根据隐私策略选择本地或云端 OCR
→ ASR 或字幕提取
→ 多来源文本合并
→ 根据任务路由选择 LLM
→ 结构化输出
→ JSON Schema 校验
→ 置信度与冲突检测
→ 用户确认
→ 保存到本地数据库
→ 登录用户后台增量同步
```

### 14.9 运行模式

```mermaid
flowchart TD
    A[用户发起菜谱解析] --> B{是否选择平台托管 AI}
    B -->|是| C{是否已登录且有配额}
    C -->|是| D[服务端 AI 网关]
    C -->|否| E[提示登录、配置本地模型或自有 API]
    B -->|否| F{本地或自有 Provider 是否可用}
    F -->|是| G[客户端直接调用 Provider]
    F -->|否| E
    D --> H[结构化结果回到客户端]
    G --> H
    H --> I[用户确认后保存本地]
    I --> J{是否已登录并开启同步}
    J -->|是| K[增量同步到云端]
    J -->|否| L[仅保存在设备]
```

### 14.10 推荐的代码边界

- UI 不直接保存 API Key。
- 页面不直接依赖具体供应商 SDK。
- 导入任务不直接判断用户是否登录，而是向能力策略服务查询当前可用 Provider。
- 云同步不能上传本地 API Key 和不必要的原始媒体。
- LLM Prompt 与 JSON Schema 需要版本号，以便回溯不同版本的解析效果。
- OCR、ASR 和 LLM 中间结果应可缓存，重新生成步骤时不重复执行全部前置任务。

## 16. MVP 验收示例

### 16.1 链接导入

- 给定一个可访问的小红书菜谱链接，系统能够识别平台并创建导入任务。
- 系统能够展示已提取的标题、图片、食材和步骤。
- 用户能够修改任意 AI 生成字段。
- 用户确认后，菜谱能够出现在指定分类中。
- 原始链接能够从菜谱详情页打开。

### 16.2 手动创建

- 用户不导入链接也能创建完整菜谱。
- 菜谱至少可以包含名称、食材和步骤。
- 未完成内容可以保存为草稿。

### 16.3 菜谱详情

- 食材和步骤正确按顺序展示。
- 调整份量后，数值型用量同步变化。
- 用户可以进入烹饪模式并逐步查看。
- 含计时信息的步骤可以启动计时器。

### 16.4 分类

- 用户可以新建、重命名和删除分类。
- 用户可以将菜谱加入或移出分类。
- 删除分类时不应默认删除分类中的菜谱。

### 16.5 异常处理

- 链接解析失败时提供至少一种替代导入方式。
- LLM 返回格式错误时系统自动重试或进入人工编辑页。
- 失败任务在用户处理前计入未完成；页面显示真实错误，并按能力提供重试和人工降级入口。
- 所有失败任务允许用户主动“结束此导入”；结束后持久化为 `cancelled`，不再计入未完成，应用重启后结果保持。
- 不得通过删除失败记录或查询过滤 `failed` 来隐藏异常。
- 重复链接导入时提醒用户已有记录。

### 16.6 游客与登录

- 游客不登录也能完成本地菜谱的创建、编辑、搜索和烹饪流程。
- 游客尝试使用平台托管 AI 时，系统说明限制并提供登录、本地模型和自有 API 三种选择。
- 游客登录后可以预览并确认本地数据合并结果。
- 登录用户关闭云同步后，仍能正常使用本地功能。
- 退出账号不会在未经确认的情况下删除本地菜谱。

### 16.7 LLM Provider

- 用户能够新增一个 OpenAI 兼容配置并执行连接测试。
- 用户能够配置 Ollama 地址并选择可用模型。
- 不支持 JSON Schema 的模型仍可通过文本 JSON 解析和校验流程使用。
- 当前模型不支持图片时，应用不会向其发送图片，并提示改用 OCR 或视觉模型。
- API Key 不出现在普通数据库、导出文件和错误日志中。

### 16.8 OCR 插件与云 OCR

- 用户能够查看、下载、启用、更新和删除 OCR 插件。
- 下载失败后可以继续或重新下载，损坏包不能被加载。
- 用户开启“仅本地处理”后，图片不会发送到云 OCR 或视觉 LLM。
- 本地 OCR 失败时，应用在获得用户允许后才能使用云端备用服务。
- OCR 结果包含文本、置信度和所使用的服务来源。

### 16.9 跨平台

- 同一账号在 iOS 和 Android 上可以同步相同的菜谱结构。
- iOS 和 Android 都能创建、预检并恢复同一版本的 `.airecipe-backup`；Markdown/PDF/图片导出不作为恢复格式。
- 系统分享入口能够将小红书或抖音链接传入应用。
- 后台解析完成后能够通过平台对应的通知能力提醒用户。

### 16.10 冰箱与按食材推荐

- 底部一级导航为“首页 / 菜谱库 / 冰箱 / 我的”，添加和导入仍可通过全局 FAB 到达。
- 游客和登录用户在离线状态下都可以新增、编辑、删除、标记用完或丢弃库存批次。
- 同名食材可以保存多个批次，并可区分存放位置、到期日期和数量未知状态。
- 推荐只包含本地正式菜谱，不包含草稿和回收站菜谱。
- 推荐页区分“现在就能做”“还差 1～2 样”“优先清库存”，并显示匹配数、缺失项、临期食材和推荐原因。
- 数量为空或单位无法换算时显示“有该食材，数量是否足够需确认”，不宣称一定够用。
- 缺失食材可以加入购物清单。
- 完成烹饪后只有用户确认才扣减库存；同名多批次默认选择更早到期者，但用户可以修改。
- “用现有食材生成新菜谱”作为后续独立 LLM 入口，不与本地推荐混排。

## 17. 待确认的产品决策

以下技术方向已确定，但仍需按对应 Spike 完成真机验收：

- 移动端统一采用 Flutter；`SPK-001` 验证 OCR 原生运行时、分享扩展、后台任务、数据库、安全存储和通知能力。
- 首版本地 OCR 首选 PaddleOCR PP-OCRv5 mobile + ONNX Runtime Mobile；`SPK-002` 验证性能、准确率、体积和两端集成。
- 自定义 LLM 统一使用“协议类型 + API 地址 + Key + 模型”；OpenAI-compatible 与 Gemini 由独立 Adapter 处理，`SPK-001` 先实现基础骨架，`SPK-003` 再做真实服务兼容性验证。
- 冰箱作为第四个一级导航；首版本地菜谱推荐不依赖 AI，中文食材标准化、同义词和单位换算由 `SPK-008` 验证。

以下产品与商业问题需要在开发前逐步确认：
- 首版是否内置设备端 LLM 推理，还是仅支持用户连接本机/局域网 LLM API？当前需求优先采用 API 方式。
- 游客链接解析需要经过服务端时，匿名任务的限流、缓存期限和隐私规则如何设置？
- 平台托管 AI 的免费额度、订阅价格和单次任务成本上限是多少？
- 原始图片和视频在本机及云端分别保存多久？
- 是否允许将第三方内容生成公开分享页？
- 链接解析服务采用自建能力、第三方服务，还是混合模式？
- 是否需要支持批量导入收藏链接？
- 是否需要审核公开内容？
- 是否优先实现营养估算？
- 是否需要家庭共享和多人编辑？
- 自有 API 配置是否允许端到端加密后跨设备同步？首版建议仅保存在设备安全存储中。

## 18. 建议的首版迭代顺序

### Sprint 4：登录与云端能力

### Sprint 7：上线准备

- 隐私与数据删除。

- 埋点和错误监控。
- iOS/Android 真机兼容性测试。
