# BUG-008 慢速 LLM 服务下「最终结构化生成」超时失败修复验收

> 日期：2026-08-07
> 状态：VERIFY（等待项目负责人复测）
> 关联：`tracking/BACKLOG.md`（BUG-008）、`tracking/CHANGELOG.md`（2026-08-07）

## 背景与根因

项目负责人反馈：链接只有一个图片，日志显示**单图识别成功（耗时 82 秒）**，随后
「最终结构化生成」失败：

```text
[AIRecipe][Http] LLM 请求耗时=82256ms status=200 bodyBytes=10688
[AIRecipe][Recognize] 单图识别耗时=82337ms order=0 uploadBytes=481798
[AIRecipe][Generate] 最终结构化生成失败 kind=timeout 耗时=120025ms
```

根因：

1. 用户配置的 LLM 服务响应本身较慢（单图识别就要 82 秒，很可能是本地 Ollama/
   LM Studio 等慢速模型）。
2. `LlmConnectionConfig.requestTimeout` 默认 **120 秒**；LLM 配置页与识图引擎
   多模态区的超时档位只有 `30/60/120` 秒，**无法调大**。
3. 「最终结构化生成」请求超出 120 秒未返回时，被 `HttpLlmTransport` 的
   `.timeout(request.timeout)` 主动中断，映射为 `ImportTaskErrorCode.timeout`。

本轮修复：

- 两处设置页超时档位扩展为 `30/60/120/180/300/600` 秒。
- 超时错误文案补充「在 LLM/识图引擎设置中调大『请求超时』后重试」指引。
- **诊断辅助**：LLM 设置页新增「测试结构化生成」区块——输入任意菜谱文本，
  走与真实导入完全相同的结构化生成 prompt 与 JSON Schema，直接测出 LLM 生成
  完整结构化 JSON 的真实耗时（毫秒 + 秒），用于判断「最终生成超时」是
  LLM 服务本身慢，还是图片识别等其他环节引入的延迟。

本轮追加修复（2026-08-07 晚，排查「测试 30 秒、实际 120 秒超时」）：

- **推理模式对齐（PERF-001 关键缺陷）**：`LlmSettingsUseCases._buildConfiguration`
  构造测试/保存用配置时未继承已保存的 `reasoningMode`，恒为 fast；「测试结构化
  生成」的 prompt 也未跟随存储配置。若存储配置为 `deep`（无设置页入口、不可见），
  实际导入会发送 `reasoning_effort: high` 等深度思考参数而明显变慢，测试却始终以
  fast 运行，造成「测试快、导入慢」的假象。现已修复：保存/测试均继承存储配置的
  `reasoningMode`，测试结果展示实际生效模式（fast/deep）。
- **输入量差异确认**：除推理模式外，测试输入是用户手输的短文本，实际导入的
  prompt 是「原文 + 整张图片 OCR 转录全文」（`sourceCharacterCount` 最大 40000
  字符）。长文本输入的生成耗时显著高于短文本，也属正常现象，不构成代码缺陷。

## 前置条件

1. 重新构建并安装 Android 版本（无数据库结构变化，可覆盖安装）。
2. 进入「我的 → 能力配置 → 识图引擎」与「我的 → 能力配置 → LLM 设置」（如入口
   名称不同，以实际 App 为准），确认能看到「请求超时」下拉。

## 复测用例

### 用例 1：识图引擎超时档位包含 600 秒

**步骤**：打开识图引擎设置页 → 找到「请求超时」下拉 → 展开。

**预期结果**：

- 下拉包含 `30/60/120/180/300/600 秒` 六档。
- 选择「600 秒」并保存，再次进入仍显示 600 秒（配置持久化）。

**回传**：下拉展开截图 + 保存后重新进入的截图。

### 用例 2：LLM 设置页超时档位包含 600 秒

**步骤**：打开 LLM 设置页 → 找到「请求超时」下拉 → 展开。

**预期结果**：

- 下拉包含 `30/60/120/180/300/600 秒` 六档。
- 选择「600 秒」并保存，再次进入仍显示 600 秒（配置持久化）。

**回传**：下拉展开截图。

### 用例 3：调大超时后重新导入单图链接成功（核心回归）

**步骤**：

1. 在识图引擎与 LLM 设置中把「请求超时」均调为 **600 秒**（慢速模型需要更长）。
2. 重新导入之前失败的那个单图链接（或相同类型的单图链接）。

**预期结果**：

- 单图识别 → 最终结构化生成全链路完成，不再报「超时」。
- 最终生成菜谱草稿并进入草稿确认页，食材/步骤/时长等字段正常。

**回传**：导入成功进入草稿确认页截图；如仍失败，回传完整 Logcat 片段（包含
`[AIRecipe][Recognize]`、`[AIRecipe][Generate]` 两行耗时日志）。

### 用例 4：超时错误文案包含调大超时指引（可选）

**步骤**：把「请求超时」调回 120 秒，用之前会超时的慢速模型再次导入。

**预期结果**（如再次超时）：

- 失败提示为「AI 服务响应超时，请在 LLM/识图引擎设置中调大『请求超时』后重试。」
  或「多模态识别超时，请在识图引擎设置中调大『请求超时』后重试。」，不再只说
  「请稍后重试」。

**回传**：失败提示截图。

### 用例 5：「测试结构化生成」诊断功能（新增）

**步骤**：

1. 打开 LLM 设置页 → 滚动到「测试结构化生成」区块。
2. 输入一段菜谱文本（例如之前单图识别出的转录文字，或任意菜品描述）。
3. 点击「测试结构化生成」。

**预期结果**：

- 等待期间按钮显示「正在生成…」。
- 成功后展示：耗时（毫秒 + 秒）与生成字符数，例如「耗时 82337 ms（82.3 秒）」。
- 该耗时与最终导入日志中的 `[AIRecipe][Generate] 最终结构化生成耗时=…` 同源，
  可直接对比：如果这里很快（几秒）而导入很慢，说明慢在图片识别/其他环节；
  如果这里也要几十秒以上，说明是 LLM 服务本身慢。

**回传**：点击按钮后的耗时截图 + 与导入日志的对比结论。

### 用例 6：空输入提示（新增）

**步骤**：不输入文本，直接点击「测试结构化生成」。

**预期结果**：显示「请先输入要测试结构化的菜谱文本。」，不发请求。

**回传**：提示截图。

### 用例 7：「测试结构化生成」显示实际生效推理模式（追加）

**步骤**：

1. 打开 LLM 设置页 → 滚动到「测试结构化生成」区块。
2. 输入一段菜谱文本，点击「测试结构化生成」。

**预期结果**：

- 耗时文本同时展示模式，格式如「耗时 82337 ms（82.3 秒）· 模式 fast」。
- 若显示「模式 deep」，说明存储配置开启了深度思考（PERF-001），实际导入会
  发送 `reasoning_effort: high`，耗时成倍增长属预期——请把该模式截图回传，
  并与导入日志 `[AIRecipe][Generate] … reasoningMode=deep` 对比。

**回传**：耗时 + 模式截图；如为 deep，附带导入日志的 `reasoningMode=` 字段。

### 用例 8：用真实 OCR 转录文本复现耗时（追加，定位输入量差异）

**步骤**：

1. 重新导入该单图链接，抓取日志中的 `[AIRecipe][Generate] 最终结构化生成耗时=…ms
   sourceChars=… reasoningMode=…`（含 `sourceChars=` 值）。
2. 回到「测试结构化生成」，把单图识别出的完整转录文本（可从导入草稿或 OCR 结果
   中复制）粘贴输入，再点一次测试。

**预期结果**：

- 测试耗时随输入文本变长而增长，接近实际导入的 `sourceChars=` 量级。
- 若长文本测试也需要 60 秒以上，说明是 LLM 服务对长输入本身慢，请调大超时
  （如 300/600 秒）并重试导入。

**回传**：`sourceChars=` 数值 + 长文本测试耗时截图。
