## 1. 用户价值

先选择本次想优先使用的冰箱食材，再确定性离线匹配本地正式菜谱，分组展示"现在就能做 / 可能可以做 / 缺 1 样 / 缺 2 样 / 优先清库存"，标注已选命中、冰箱已有·可补选、缺失项、规格待确认与规格不符，不依赖 LLM/网络。

## 2. 已实现

- **匹配（ADR-0022 三值逻辑）**：`InventoryRecommendationUseCases` 采用"基础食材 + 属性规格 + YES/MAYBE/NO"：库存规格更具体满足宽泛要求（精瘦肉→猪肉=YES）；库存宽泛面对具体要求进入"可能可以做"（猪肉→精瘦肉=MAYBE）；基础食材/属性明确冲突=NO（肥肉→精瘦肉、五花肉→精瘦肉）。未收录名称只允许完全相同名称匹配（鸡蛋=鸡蛋，鸡蛋≠鸡蛋液）。可选食材与常备基础调味品不计缺失；已过期批次不参与；数量未知提示确认。
- **排序**：缺失+规格冲突更少 → 待确认(MAYBE)更少 → 库存不足排后 → 临期命中多 → 匹配比例高。
- **规格解析与落库**：`IngredientCanonicalizer` 升级（规格条目：精瘦肉=pork+精瘦、五花肉=pork+腹部+半肥半瘦、肉末=meat+绞碎）；库存批次与菜谱食材在 v6 数据库落库规格字段；旧数据读取时即时回填。
- **渐进式库存录入**：`suggestInventorySpec` 名称→候选规格；录入页显示可跳过的规格 chip（不确定/精瘦肉/五花肉/…）。
- **Facade**：`recommendRecipesFromInventory(selectedNames, {strictSelected, confirmedBases})`（仅本地正式菜谱 published）；`suggestInventorySpec`、`isIngredientNameKnown`。
- **UI**：推荐页新增"可能可以做"分组；卡片显示"待确认：精瘦肉 — 库存未确认是否为精瘦"+"视为可用"（本次会话确认）；"规格不符"原因展示；草稿确认页未收录食材显示"种类待确认"轻量标识。
- 缺失项"加入购物清单"因购物清单模块未实现，本版仅展示缺失项不写入。

## 3. Android 人工复测步骤

### 3.1 基础推荐回归（ADR-0021 保留）

1. 冰箱-库存添加食材（如 番茄、鸡蛋；再设一个 2 天内到期的临期食材）。
2. 冰箱-推荐：点选番茄 → CTA 计数 → 点「用已选食材推荐」→ 结果分组出现。
3. 若库中有"番茄炒蛋"（番茄+鸡蛋，鸡蛋在库存但未选）→ 卡片应显示「已选命中·番茄」「冰箱已有·可补选·鸡蛋」。
4. 库存搜索框输入「西红柿」→ 应同时命中库存「番茄」（同义词命中）。
5. 库存添加「小番茄」，推荐/搜索不应把「小番茄」当作「番茄」。
6. 推荐页底部开关「仅使用已选食材」：打开时未选择的冰箱食材变为「缺失」。
7. 菜谱需求「番茄 3 个」、库存仅「番茄 1 个」→ 卡片显示「库存不足：番茄 还需要 2 个」；库存「番茄（数量未知）」→ 显示"有该食材，数量是否足够需确认"。

### 3.2 渐进式语义食材系统复测（ADR-0022 新增）

1. **库存录入规格**：冰箱-库存添加食材，名称输入「猪肉」→ 出现"识别为：猪肉"与规格候选（不确定/猪肉·精瘦/猪肉·五花/猪肉·半肥半瘦/…）。选择「猪肉·精瘦」保存；再添加一个「猪肉」不选规格（不确定）。
2. **现在就能做（YES）**：库中有「精瘦肉（猪肉·精瘦）」批次，库中正式菜谱含食材「猪肉」→ 推荐命中并进入「现在就能做」，卡片显示"精瘦肉 → 猪肉（规格识别）"。
3. **可能可以做（MAYBE）**：库存仅「猪肉（规格未设置）」，菜谱含「精瘦肉」→ 该菜谱进入「可能可以做」，卡片显示"待确认：精瘦肉 — 库存未确认是否为精瘦"与「视为可用」按钮。
4. **视为可用（会话确认）**：点击「视为可用」→ 该菜谱移到「现在就能做」；返回再进推荐页（会话重置）后恢复待确认。
5. **规格不符（NO）**：库存「五花肉（猪肉·五花·半肥半瘦）」，菜谱含「精瘦肉」→ 卡片显示"规格不符：精瘦肉 — 肥瘦冲突…"，进入「缺 1 样」并标注规格不符。
6. **宽泛→具体待确认**：库存「肉末」，菜谱含「猪肉末」→ 「可能可以做」，原因"库存「肉」较宽泛，需确认是否为「猪肉」"。
7. **草稿确认页轻量标识**：AI 导入草稿中未收录食材（如"小番茄"）显示"种类待确认"徽标，不弹窗打断。
8. 底部「仅使用已选食材」开关与上述三值分组叠加正常。
9. **AI 导入调料不计缺失**：导入"香干炒肉"这类 AI 把 水/花椒粉/小米辣/糍粑辣椒 等解析成食材的菜谱，库存有 瘦肉+豆干 时推荐应命中并只显示缺 青椒，不会因调料被计为缺 4 样而整个菜谱消失。
10. **规格未落库回退**：旧版本录入的库存（规格未设置）重新构建 App 后，名称可解析的批次（如"瘦肉"）仍应参与精确匹配（瘦肉→瘦肉=现在能做），不需要用户重新录入。

### 3.3 食材家族与模糊匹配复测（ADR-0023，通用）

1. **辣椒→青椒（可能可以做）**：库存添加「辣椒」（可跳过规格），菜谱含「青椒」（如 青椒肉丝）→ 推荐进入「可能可以做」，卡片显示"待确认：青椒 — 冰箱中的「辣椒」与「青椒」同属辣椒类，具体规格待确认"。
2. **蘑菇→香菇**：库存「蘑菇」+ 菜谱含「香菇」→「可能可以做」。
3. **鱼→鲈鱼**：库存「鱼」+ 菜谱含「鲈鱼」→「可能可以做」。
4. **青菜→小白菜**：库存「青菜」+ 菜谱含「小白菜」→「可能可以做」。
5. **干辣椒→青椒（规格不符）**：库存「干辣椒」+ 菜谱含「青椒」→ 卡片显示"规格不符：青椒 — 加工状态冲突：菜谱需要新鲜，库存为干制"，不进入"可能可以做"。
6. **可选食材不计缺失**：菜谱含"可选/没有可以不放"标记的食材（如 香菜）在库存没有时不计入"缺 N 样"。
