# PERF-002 图片导入链路性能优化验收方法

> 对应解决方案：`解决方案.md`（消除重复下载 / 有限并发流水线 / 识别前压缩 /
> 深度思考开关）
>
> 创建：2026-08-06　状态：VERIFY（等待项目负责人执行）

## 一、任务目标

按《解决方案.md》优化图片导入链路：

1. **任务级图片缓存**：一张远程图片在一次导入中只下载一次，识别阶段与封面
   保存阶段共用同一份临时文件，消除重复下载。
2. **有限并发流水线**：多张图片的下载与识别改为并发 2 并行，形成流水线；
   单张识别失败不拖垮整批（仅标记部分内容），取消立即终止。
3. **识别前压缩重编码**：上传给多模态识别的图片先缩边并重编码为 JPEG
   （普通照片长边 ≤2048px、质量 85；文字密集的长截图保留更高分辨率
   ≤4096px），降低上传体积与 Provider 解码开销；磁盘原图不改动，仍用于封面。
4. **深度思考开关**：图片转录（多模态）始终快速；多图分组判断固定快速；
   最终结构化生成跟随用户设置的推理深度（`reasoningMode`）。

## 二、测试平台与前置条件

- Android 模拟器或真机（Debug 构建）。
- 已在“识图引擎 → 多模态 LLM 图片识别”配置可用的多模态 LLM（Provider/
  API 地址/模型/Key），并已配置菜谱生成 LLM。
- 准备一条含多张配图（≥2 张，建议 3~5 张，其中至少一张大图）的小红书/抖音
  链接，或使用手动选图/拍照多次选择多张图片导入。
- 外部终端可用以查看 Logcat（`adb logcat`）。

## 三、测试方法（按步骤执行并记录结果）

### 1. 消除重复下载（网络请求去重）

1. 粘贴含多张配图的链接创建导入任务，让导入走多模态识别 + 封面保存全流程。
2. 观察 Logcat 中 `[AIRecipe][RemoteImage]` / 下载相关日志。
3. 预期：同一张图片的 URL 只出现一次下载；识别阶段与封面保存阶段共用同一
   份文件，不再对同一 URL 二次下载。
4. 记录：每个图片 URL 出现次数；是否仍存在重复下载。

### 2. 有限并发与进度

1. 导入多张图片，观察“正在识别图片内容”阶段。
2. 预期：进度能推进，多张图片并行下载/识别（并发 2），整体耗时短于逐张串行；
   结果按原图顺序进入草稿证据，不出现乱序。
3. 记录：识别阶段耗时；是否并发（可观察日志时间戳交叠）；草稿证据顺序是否
   与图片顺序一致。

### 3. 单张失败不拖垮整批

1. 构造或触发某一张图片下载/识别失败（例如临时断网、或一张图片地址失效）。
2. 预期：其余图片仍正常识别并生成草稿；失败图片以“部分内容”标记，不导致
   整单失败；全部失败时提示“所有图片识别失败，请检查图片后重试”。
3. 记录：失败张数、其余图片是否成功、草稿是否生成、提示文案。

### 4. 取消立即终止

1. 识别阶段点击“取消解析/取消”。
2. 预期：取消尽快生效，任务稳定为“解析已取消”，不继续等待剩余图片。
3. 记录：取消后任务状态、是否仍有下载/识别请求。

### 5. 识别前压缩（上传体积）

1. 选一张高分辨率大图（如 4000×3000 照片）导入。
2. 观察多模态请求体或上传日志。
3. 预期：上传给识别的图片被压缩（JPEG、长边 ≤2048px、质量 85），上传体积明显
   小于原图；封面仍使用原图。
4. 记录：原图尺寸/大小、上传图尺寸/大小；封面清晰度是否正常。

### 6. 深度思考开关对最终生成的影响

1. 在最终结构化生成阶段，确认其跟随 `reasoningMode`（默认 fast）。
2. 若 Provider 支持 `reasoning_effort`（OpenAI-compatible）或
   `thinkingConfig`（Gemini），观察请求体中字段是否按设置下发。
3. 预期：图片转录与分组判断始终为快速模式；最终结构化生成默认 fast，不发送
   `reasoning_effort=high` / 不开启 thinking；任务能正常生成草稿。
4. 记录：请求体是否包含深度思考相关字段；生成耗时与质量。

### 7. 回归

1. 单图导入、纯文本导入、只开 OCR、自动路由等既有导入路径不回归。
2. 确认多草稿（多图独立/合成）分组判断仍正确（`[AIRecipe][Grouping]` 日志）。
3. 强停重启后任务状态与草稿恢复正常。
